# The forge: screens written in the cloud, delivered without an app update

A Gradle build of its own, next to the app but not part of it. Four modules:

| Module | What it is | Where it runs |
|---|---|---|
| `screens` | Android library the coding agent writes screens into. The [Ketoy](https://ketoy.dev) compiler turns every `@KetoyEntryPoint` into one signed `.ktx` bundle | the worker machine |
| `contract` | DTOs of the gateway protocol (`ForgeProtocol.kt`), shared by `gateway` and `worker`; the app keeps a hand-written mirror | both |
| `gateway` | Ktor service: job queue, bundle store, two bearer tokens | Fly.io (or `./gradlew :gateway:run` locally) |
| `worker` | JVM app: the coding agent on Meta's Muse plus the Gradle runner | any machine with JDK 17 and the Android SDK |

Why a separate build: the app is on Kotlin 2.3 and does not carry the Ketoy compiler plugin; this
build pins Kotlin 2.0.21, the line the Ketoy 0.4.20-alpha plugin was released against. The app only
needs Ketoy's runtime artifacts, which are plain Maven dependencies.

## Build the template bundle

```bash
./gradlew :screens:ketoyBundle
```

Output: `screens/build/ketoy-bundles/agent.ktx`. The bundle holds every entry point in
`screens/src/main/kotlin`; the app picks one by name (`HelloForgeScreen` for the shipped sample).
The first build downloads Ketoy's embedded Kotlin compiler; later builds take a few seconds.

## Run the worker

```bash
./gradlew :worker:fatJar
FORGE_GATEWAY_URL=https://<gateway> FORGE_WORKER_TOKEN=...   java -jar worker/build/libs/worker-all.jar          # add --once to process one job and exit
java -jar worker/build/libs/worker-all.jar --self-test  # builds a sample screen, no model or gateway needed
```

The worker has no Meta key of its own. Each job carries the key of the person who asked for it (see
"Whose Meta key" below), and the worker makes a Meta client for that job only.

Optional: `FORGE_MODEL` (default `muse-spark-1.3`), `META_BASE_URL` (default `https://api.meta.ai/v1`),
`FORGE_DIR` (default: found from the working directory), `FORGE_REASONING_EFFORT` (default `medium`,
`off` omits the field). The agent's rules are in `AGENTS.md`.

## Keys

`keys/forge-private.key` is a 32-byte Ed25519 seed, generated by `ketoy init` and **never
committed** (see `.gitignore`); it lives only on the worker machine. `keys/forge-public.key` is the
matching 32-byte public key; the same bytes ship in the app as
`app/src/main/assets/ketoy/keys/forge-public.key`. A bundle signed with any other key renders the
app's native fallback, not the screen. To rotate: run `ketoy init` on any scratch Android project,
take the pair it generates, replace both files and rebuild the app.

## What the app and the bundle must agree on

- The Ketoy version: 0.4.20-alpha on both sides.
- The public key above.
- Capability ids: `ketoy-capabilities.json` lists the app-specific ones (none yet - screens are
  self-contained; Ketoy's built-in core capabilities are registered by the app).
- The entry point name: the worker reports it with the artifact; the app never hard-codes it.

## Protocol

See `contract/src/main/kotlin/dev/amuse/forge/contract/ForgeProtocol.kt`. In short:

```
app     POST /v1/jobs                       -> 202 {jobId}
app     GET  /v1/jobs/{id}                  -> {status, message?, question?, artifact?}
app     POST /v1/jobs/{id}/answer           -> the person answers a needs_info question
app     GET  /v1/bundles/{id}.ktx           -> the bundle bytes
worker  GET  /v1/worker/next?wait=25        -> the next queued job, or 204
worker  POST /v1/worker/jobs/{id}/status    -> accepted | working | needs_info | failed
worker  POST /v1/worker/jobs/{id}/artifact  -> done, with the bundle
```

Two bearer tokens: `FORGE_CLIENT_TOKEN` for the app, `FORGE_WORKER_TOKEN` for the worker.

### Whose Meta key

A screen is paid for by the person who asks for it. The app sends the Meta key the person entered in
Settings in the `X-Meta-Api-Key` header of `POST /v1/jobs` and of `POST /v1/jobs/{id}/answer` (a job
without it is a `400`). The gateway keeps the key in memory only while the job is queued or held by a
worker, hands it to the worker inside `WorkerJob.metaApiKey`, and drops it when the job asks a question,
finishes or fails; it is never written to `job.json` or any other file. A restart of the gateway
forgets every key: a queued job then fails with a sentence asking to try again, and a pending question
gets the key back with the answer. Neither the gateway's job queue nor the worker has a key of its own.

Limits (`ForgeLimits`): JSON bodies up to 64 KB (the artifact upload up to 32 MB), `Content-Length`
required, 20 new jobs per hour per IP (every job spends paid model calls), request text up to 4000
characters, an answer up to 2000. An artifact only lands on a job a worker holds (`409` otherwise).
On Fly (`FLY_APP_NAME` set) the client IP comes from the proxy's `Fly-Client-IP`.

It also serves the remote config (`GET /v1/config`, public; written with `FORGE_ADMIN_TOKEN`):
see `docs/remote-config.md`.

The one key the gateway may hold is the owner's, for the market only: with `META_API_KEY` the market also reviews every package with Muse Spark, draws covers with Muse
Image and answers plain-words search (see "AI features" in `docs/market-api.md`).

The same service also hosts the market (publish and install agents and skills): see
`docs/market-api.md` and, for the app side, `docs/market-app-integration.md`.
