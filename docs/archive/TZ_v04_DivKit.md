# ТЗ v0.4: Driven UI мини-аппы через DivKit

> ⏸️ **PARKED — отложено до v2 (решение 2026-06-15).**
> DivKit в v1 не используется. Driven UI в v1 = предзаполненные виджеты (`render_card` → `DrivenUiEngine`) + предзаполненные «апы» как **композиции этих виджетов**. Этот документ целиком — материал post-v1; держим как референс на случай возврата к серверной генерации UI.

## 1. TL;DR

Пользователь просит агента сделать мини-апп под свою задачу («напоминание о лекарствах», «учёт финансов», «карточки Anki», «счётчик калорий»). Интент уходит на **свой тонкий сервер**, где LLM со скиллом генерирует UI в **компактном промежуточном JSON-формате**. Сервер валидирует его в repair-цикле, детерминированно разворачивает в DivKit JSON и отдаёт клиенту. Клиент — тупой рендерер: `Div2View` в чат-бабле + словарь из 8 фиксированных экшенов (Room, WorkManager, уведомления).

Ключевые решения и их причины:

| Решение | Почему |
|---|---|
| DivKit (32.x), не Remote Compose | Зрелый production-фреймворк, JSON-формат, не alpha |
| Свой сервер обязателен | Граница доверия (валидация UI до рендера), скилл живёт на сервере и итерируется без релизов APK, ключи LLM не на клиенте |
| LLM пишет компактный формат, не сырой DivKit | В ~5 раз дешевле по токенам на каждый цикл repair-лупа, валидируется одной маленькой схемой, финальный DivKit генерирует наш код → недоверенного JSON в рендере не бывает |
| Одна карточка = один экран | Мини-апп, не суперапп. Без навигации, без связей между карточками |
| Словарь из 8 экшенов, без reflection | Карточка может *выглядеть* как угодно, но *делать* — только 8 вещей. Обычный `when` на клиенте |
| Repair loop, max 3 цикла | Целевые модели — Qwen/DeepSeek/Llama-класс (не топ-тир): первый проход ~85%, после repair ~97% |

## 2. Архитектура

```
┌─────────── КЛИЕНТ (Android, существующий код) ───────────┐
│ ChatScreen → агентский LLM-цикл (как сейчас)              │
│   ↓ tool_call: create_mini_app(intent)                    │
│ POST https://<server>/v1/generate  {intent}               │
│   ↓ ответ: {divkit_json} | {fallback_text}                │
│ MessageBubble → AndroidView { Div2View }                  │
│   ↓ тап: div-action://save_record?...                     │
│ DivActionHandler (when по словарю) → Room / WorkManager   │
└───────────────────────────────────────────────────────────┘

┌─────────── СЕРВЕР (Ktor, тонкий) ─────────────────────────┐
│ /v1/generate:                                             │
│   скилл (препромпт) + intent → LLM → компакт-JSON         │
│   → валидация → [repair loop ≤ 3] → маппер → DivKit JSON  │
│   кэш: hash(intent) → готовый DivKit JSON                 │
│   лог фейлов и упрощений → материал для итерации скилла   │
└───────────────────────────────────────────────────────────┘
```

Клиентский агентский цикл (LlmClient, ToolRegistry, Room, fallback chain) — уже существует в репозитории, переиспользуется. Новое на клиенте: рендер DivKit + ActionHandler + тул `create_mini_app`. Сервер — новый, минимальный.

## 3. Серверный флоу генерации (repair loop)

```
[intent] → препромпт v0 = скилл + intent → LLM → JSON
    ↓
Валидация (3 уровня):
  1. синтаксис — JSON парсится
  2. схема    — JSON Schema компакт-формата
  3. семантика — экшены ∈ словаря, var'ы объявлены,
                 source существует, квоты не превышены
    ↓
ошибок нет → маппер → DivKit JSON → клиенту ✓
ошибки     → препромпт v(n+1) = скилл + вывод модели +
             точечный список ошибок («исправь только их») → цикл
n == 3     → fallback_text клиенту + запись фейла в лог
```

Правила лупа:
- На retry модель получает **свой же вывод + список ошибок** — чинит адресно, не перегенерирует с нуля.
- Ошибки формулируются конкретно: `blocks[2].action = "track_food" — нет в словаре, доступны: save_record, increment, …`
- Temperature 0.2–0.3; можно поднять на 3-м цикле, если модель зациклилась на одной ошибке.
- Кэш по нормализованному intent: повторные/типовые запросы отдаются без LLM (важно на free-tier лимитах).
- Каждый fallback и каждое «упростил» логируются — это roadmap эволюции формата (§6).

## 4. Компактный формат (v1)

Одна карточка = один JSON-документ. LLM генерирует только его.

```json
{
  "app": "calorie_counter",
  "title": "Калории сегодня",
  "vars": {"kcal": 0},
  "blocks": [
    {"type": "counter", "label": "Съедено", "var": "kcal", "step": 100},
    {"type": "input",   "label": "Что съел", "var": "meal"},
    {"type": "button",  "text": "Записать",
     "action": "save_record",
     "args": {"collection": "meals", "fields": ["meal", "kcal"]}},
    {"type": "list",    "source": "records:meals:today"},
    {"type": "progress","label": "Цель 2000", "var": "kcal", "max": 2000}
  ]
}
```

### Типы блоков v1 (~9 штук)

| type | Параметры | DivKit-маппинг |
|---|---|---|
| `text` | text, style (title/body/caption) | `div-text` |
| `counter` | label, var, step, min?, max? | `div-container` + `div-text` + 2 кнопки, variable |
| `button` | text, action, args | `div-text` c action `div-action://…` |
| `checkbox` | label, var | `div-container` + variable-toggle |
| `input` | label, var, hint? | `div-input` |
| `list` | source (`records:<collection>:<period>`) | `div-container` items (данные подставляет клиент) |
| `progress` | label, var, max | `div-slider`/кастом, read-only |
| `image` | url (только whitelist-домены) | `div-image` |
| `row` | blocks[] (1 уровень вложенности) | горизонтальный `div-container` |

Состояние карточки — DivKit **variables** (счётчики, чекбоксы живут в карточке без round-trip); персистенция — только через экшены.

### Квоты (проверяет валидатор)

- блоков ≤ 30, вложенность ≤ 2 (только `row` внутри корня)
- переменных ≤ 10
- один экран, никакой навигации
- `image.url` — только whitelist доменов

## 5. Словарь экшенов (v1, фиксированный)

Реализация на клиенте: один `DivActionHandler`, обычный `when`. Без reflection.

| Action | Args | Реализация |
|---|---|---|
| `save_record` | collection, fields/values | INSERT в `records` |
| `query_records` | collection, period | SELECT из `records` → обновить `list`-блок |
| `increment` | var, by | DivKit variable + опц. персист |
| `set_value` | var, value | DivKit variable |
| `schedule_reminder` | time, text, repeat? | WorkManager + notification |
| `cancel_reminder` | id | `WorkManager.cancelUniqueWork` |
| `show_message` | text | Snackbar |
| `next_card` | deck | query_records + set_value (Anki-сценарий) |

Хранилище — одна универсальная таблица, без кода под каждый мини-апп:

```sql
records(id, collection TEXT, json TEXT, created_at INTEGER)
```

## 6. Границы генерации

- **Потолок задаёт формат, не переговоры в диалоге:** словарь блоков ограничивает вид, словарь экшенов — поведение. «Сделай CRM» физически не может стать CRM — модель соберёт ближайшую аппроксимацию (список + форма + счётчики).
- **Правило честного упрощения (в скилле):** если запрос превышает возможности — собрать простейшую полезную версию и явно сказать пользователю, что упрощено и как.
- **Эволюция по логам:** новые типы блоков добавляются, только когда лог фейлов/упрощений показывает реальный спрос (30 запросов на график → блок `chart`; 2 запроса на календарь → игнор). Ничего «на всякий случай».

## 7. Безопасность

| Угроза | Защита |
|---|---|
| LLM/injection управляет UI напрямую | Невозможно: рендерится только DivKit, сгенерированный нашим маппером из провалидированного компакт-JSON |
| Эксфильтрация через `image.url` | Whitelist доменов на сервере |
| Выдуманные экшены | Словарь: невалидный action не проходит семантическую валидацию; на клиенте `when` с веткой-заглушкой |
| Ключи LLM-провайдеров | Только на сервере |
| Скилл как IP | Только на сервере, итерируется без релиза APK |
| Клиент-серверный канал | HTTPS/TLS; подпись ответов — не нужна в v1 (свой сервер) |

## 8. Стейджи

### Stage 1 — Спайк DivKit · 1–2 дня
Подключить DivKit к клиенту. Руками написанный DivKit JSON (карточка: текст + кнопка) рендерится в `MessageBubble` через `AndroidView { Div2View }`. Тап по кнопке → `DivActionHandler` → локальное уведомление.
**Done when:** захардкоженная карточка видна в чате, тап даёт уведомление. Без LLM, без сервера.

### Stage 2 — Сервер: формат + маппер + луп · 1 неделя
Ktor-сервис с `POST /v1/generate`. JSON Schema компакт-формата, семантический валидатор (словарь, квоты), маппер компакт-JSON → DivKit JSON, repair loop (≤ 3), первый драфт скилла с 4 few-shot примерами (лекарства, финансы, Anki, калории). Логирование фейлов.
**Done when:** `curl /v1/generate '{"intent":"счётчик калорий"}'` стабильно возвращает валидный DivKit JSON; невалидный вывод модели чинится лупом; 3 фейла подряд → fallback_text.

### Stage 3 — Клиент: тул + экшены + хранилище · 1 неделя
Тул `create_mini_app(intent)` в существующем ToolRegistry → вызов сервера → рендер ответа. `DivActionHandler` со словарём 8 экшенов. Таблица `records`. `schedule_reminder` через WorkManager. Персистенция карточек в Room (DivKit JSON в колонке сообщения) — карточки переживают перезапуск.
**Done when:** «напомни принимать витамины в 9:00» end-to-end: интент → сервер → карточка → кнопка «Принял» пишет запись → в 9:00 приходит уведомление → карточка на месте после рестарта приложения.

### Stage 4 — Скилл · 3–5 дней (итеративно)
Вылизывание препромпта на пуле из ~30 тестовых интентов: точность формата, правило честного упрощения, качество layout'а. Замер: доля успеха с первого прохода, после repair, доля fallback. Кэш intent → JSON.
**Done when:** ≥ 90% тестовых интентов дают полезную карточку не более чем за 2 цикла; «сделай CRM» возвращает честную аппроксимацию с пояснением.

### Stage 5 — Полировка · 1 неделя
Edge cases: битый JSON с сервера, длинные списки (>100 записей), пустые состояния, офлайн (сервер недоступен → честное сообщение). Markdown-fallback при ошибке рендера. Unit-тесты: маппер, валидатор, ActionHandler. Интеграционный тест лупа с MockWebServer.
**Done when:** все 4 сценария работают на физическом устройстве; ни один сбой не оставляет пустой бабл.

**Итого: ~3.5–4.5 недели.**

## 9. Открытые вопросы

1. Хостинг сервера — VPS / serverless? (влияет только на деплой, не на код — Ktor везде)
2. LLM-провайдер на сервере и конкретная модель (Qwen/DeepSeek/Llama-класс через NIM или OpenRouter) — выбрать на Stage 2 по факту качества лупа.
3. Аутентификация клиент↔сервер — в v1 достаточно статического токена в хедере?
4. Обновление уже отрендеренных карточек (пользователь просит «добавь в счётчик воду») — v1: генерируется новая карточка; редактирование существующей — v1.1.

## 10. Что осознанно НЕ делаем (v1)

- Мульти-экранность, навигация, связи между карточками — мини-апп, не суперапп.
- Сырой DivKit от LLM — только компакт-формат.
- Reflection-роутер, contract.json, подпись бандлов, KMP-модуль — наследие v0.3, удалено.
- Кастомные типы блоков «на всякий случай» — только по логам спроса.
- Шаблоны мини-аппов — возможная оптимизация v1.1 (кэш покрывает большинство выгод).
