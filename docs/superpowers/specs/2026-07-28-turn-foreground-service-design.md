# Foreground-сервис на время хода агента

Дата: 2026-07-28. Статус: дизайн согласован, готов к декомпозиции.

## 1. Цель

Дать ходу агента честную гарантию доведения до конца, когда приложение свёрнуто.

Сегодня граница живучести — процесс: `TurnManager` держит ход в appScope-скоупе
(`CoroutineScope(SupervisorJob() + Dispatchers.Default)`, `TurnModule`), поэтому ход
переживает уход с экрана, но не переживает вытеснение процесса из памяти. После
сворачивания приложение — обычный кэшированный процесс: Android вправе убить его в любой
момент, а на агрессивных прошивках делает это быстро. Пользователь при этом видит свою
реплику в истории и молчание в ответ.

## 2. Почему пересматриваем решение 2026-07-04

`docs/superpowers/specs/2026-07-04-background-turns-design.md` рассматривал foreground-сервис
и отклонил его: «обязательное уведомление во время работы, тип `dataSync` с таймаутами на
Android 15, много ЖЦ-кода. Оверкилл для хода в 10–60 сек».

Что изменилось:

1. Решение пользователя 2026-07-28: цена в виде уведомления приемлема.
2. Тип `shortService` (API 34+) подходит лучше `dataSync`: он ровно про «доделать короткую
   задачу», не требует обоснования категории при публикации и не тратит суточную квоту
   `dataSync` (6 ч на API 35+).
3. С API 31 система по умолчанию **откладывает показ FGS-уведомления примерно на 10 секунд**.
   Типичный ответ в чате укладывается раньше — в большинстве случаев уведомление не появится
   вообще. Это снимает главное возражение исходной спеки.

## 3. Ограничения Android, формирующие дизайн

Эти три факта не обсуждаются, они диктуют форму решения:

- **Стартовать FGS из фона нельзя.** С API 31 старт foreground-сервиса, когда приложение не
  на экране, бросает `ForegroundServiceStartNotAllowedException`. Значит захват возможен
  ровно один — в момент отправки, пока экран перед пользователем. Схема «поднимать сервис на
  каждый запрос к LLM и отпускать между витками» нереализуема: второй виток случается уже в
  фоне и упадёт именно тогда, когда защита нужна.
- **`shortService` ограничен примерно тремя минутами.** По истечении система вызывает
  `Service.onTimeout()` и требует остановиться.
- **`startForegroundService` обязан вызвать `startForeground` в течение ~5 секунд**, иначе
  система прибьёт приложение. Сервис показывает уведомление сразу в `onStartCommand`.

Следствие для продукта: защищается **весь ход целиком**, а не отдельный запрос к бэкенду.
Это совпадает с интуицией «покрыть отправку истории и запрос»: обычный чат-ход без
инструментов — это буквально «отдать историю → дождаться стрима → записать ответ». Разница
проявляется только на многовитковом GOAL. Отдельно защищать сетевой обмен бессмысленно ещё и
потому, что ответ ассистента пишется в БД один раз, в конце всего хода
(`TurnPersistence.addAssistantMessage`): смерть процесса между витками теряет результат
независимо от того, был ли защищён сам HTTP-запрос.

## 4. Архитектура

### 4.1 Новый порт

Рядом с существующими узкими портами в `agent/loop/TurnPorts.kt` (`ForegroundState`,
`TurnNotifier`), чтобы `TurnManager` остался тестируемым без Android:

```kotlin
interface TurnLifeSupport {
  /**
   * Просит защиту для хода [conversationId].
   * false — система отказала (типично: старт из фона). Ход всё равно исполняется, просто
   * без гарантии, ровно как до этой фичи.
   */
  suspend fun acquire(conversationId: String): Boolean

  /** Идемпотентно снимает защиту; последний release гасит сервис. */
  fun release(conversationId: String)

  /**
   * Регистрирует реакцию на «система отобрала защиту» (onTimeout). Аргумент — набор
   * conversationId, которые на этот момент были защищены.
   */
  fun onProtectionLost(handler: (Set<String>) -> Unit)
}
```

### 4.2 Компоненты

- **`TurnForegroundService`** — `foregroundServiceType="shortService"`, `exported=false`.
  В `onStartCommand` немедленно вызывает `startForeground`. Переопределяет `onTimeout`
  (сигнатуры разошлись: API 34 — `onTimeout(startId)`, API 35+ — `onTimeout(startId, fgsType)`;
  реализуются обе под `@RequiresApi`).
- **`AndroidTurnLifeSupport`** (`@SingleIn(AppScope)`, реализация порта) — держит счётчик
  защищённых `conversationId`. Первый `acquire` поднимает сервис, последний `release` глушит.
  Ловит `ForegroundServiceStartNotAllowedException`/`SecurityException` и возвращает false.
- **`TurnManager`** — `acquire` перед стартом job хода, `release` в `finally` (успех, ошибка,
  отмена — все ветки). Он же единственный, кто вызывает `onProtectionLost` — один раз, при
  создании (в `TurnModule`), потому что только он владеет job-ами ходов и может их отменить.

### 4.3 Поток

```text
launchTurn → acquire(convId)            ← пока экран видим, старт разрешён
           → job: startTurn → ReAct-цикл → запись ответа
           → finally: release(convId)    ← последний release гасит сервис
```

## 5. Поведение на потолке

Дедлайн принадлежит сервису и отсчитывается от его старта, а не от начала каждого хода: при
двух параллельных ходах в разных диалогах второй получает остаток общего окна. Это осознанное
упрощение — параллельные ходы редки, а отдельный сервис на диалог был бы и дороже, и
неприятнее (несколько уведомлений).

При `onTimeout()`:

1. Если приложение **в фоне** (`ForegroundState.isInForeground() == false`) — защищённые ходы
   отменяются и получают `TurnStatus.Failed(canRetry = true)` с внятным текстом про
   исчерпанную фоновую защиту. «Повторить» уже существует и перегоняет ход с нуля.
2. Если приложение **на экране** — ход не трогаем, просто отпускаем сервис. Защищать нечего:
   foreground-процесс система не вытесняет. Без этого гейта длинный GOAL-прогон падал бы на
   глазах у пользователя без всякой внешней причины, хотя сегодня доезжает.

Своего таймера на API < 34 не заводим: там системного потолка для FGS нет, и убивать ход
незачем. Поведение по версиям ОС различается сознательно, деградация — в сторону большей
дееспособности на старых устройствах.

## 6. Отказ в захвате

`acquire` возвращает false там, где старт FGS запрещён: ретрай, инициированный из
уведомления при свёрнутом приложении, и любой иной старт хода не с экрана. В этом случае ход
исполняется по сегодняшней схеме — в appScope, без гарантии.

**Отсутствие защиты никогда не является причиной провалить ход.** Иначе фича сделала бы хуже,
чем было.

## 7. Уведомление

Отдельный канал, `IMPORTANCE_LOW` (без звука и вибрации), отдельный от существующего
`ai_agent_channel`, чтобы пользователь мог отключить его независимо от напоминалок. Текст —
«Агент отвечает…», тап открывает соответствующий чат.

`setForegroundServiceBehavior` намеренно **не** переводится в `FOREGROUND_SERVICE_IMMEDIATE`:
поведение по умолчанию позволяет системе отложить показ, и типичный ход завершится раньше,
чем уведомление появится.

Манифест: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SHORT_SERVICE`, объявление `<service>`.

## 8. Границы

- **Heartbeat не трогаем.** `HeartbeatRunner` не проходит через `TurnManager.launchTurn`; у
  фоновых пробуждений своя гарантия через WorkManager.
- **PREVIEW-ходы конструктора** идут через `launchTurn` и защиту получают заодно — они всегда
  стартуют с экрана, отдельной логики не нужно.
- **Планы** (`structured-plan-engine-907066`) исполняются внутри хода GOAL и попадают под ту
  же защиту; `PlanRecovery` остаётся как есть — он чинит durable-состояние после смерти
  процесса, и эта фича его не отменяет, а делает более редко нужным.

## 9. Ошибки и edge cases

- Захват отклонён системой → ход идёт без защиты (раздел 6).
- Ход завершился/отменён/упал → `release` в `finally`; уведомление не должно пережить ход.
- Два хода в разных диалогах → рефкаунт, одно уведомление, общее окно (раздел 5).
- `onTimeout` при приложении на экране → сервис гасится, ход продолжается (раздел 5).
- Force-stop приложения пользователем → сервис не спасает; это ожидаемо и вне гарантии.
- Пользователь отключил канал уведомлений → на API 34+ FGS всё равно работает, но система
  может показать уведомление принудительно; отдельной обработки не требуется.

## 10. Тестовая стратегия

- **Юнит `TurnManager`** с фейковым `TurnLifeSupport`: захват до старта хода; освобождение в
  `finally` по всем веткам (успех, ошибка, отмена); отказ захвата не ломает ход; срабатывание
  `onProtectionLost` при фоне даёт `Failed(canRetry = true)`; при foreground — ход не тронут.
- **Юнит `AndroidTurnLifeSupport`**: рефкаунт (первый acquire поднимает, последний release
  гасит, повторный release идемпотентен), проглатывание исключения старта из фона.
- **Robolectric на сервис** — только старт/стоп и создание канала. Настоящее поведение FGS
  (выживание процесса, системный `onTimeout`, отложенный показ уведомления) Robolectric не
  воспроизводит.
- **Ручной прогон на устройстве обязателен** и является частью Definition of Done: отправить
  сообщение, свернуть приложение, дождаться ответа; то же со смахиванием из recents.

## 11. Out of scope

- `dataSync` и защита длинных прогонов дольше трёх минут.
- Эскалация типа сервиса на лету.
- Переживание смерти процесса (force-stop, перезагрузка) — это Room-first стриминг или
  бэкенд, обе альтернативы отклонены в спеке 2026-07-04 и не пересматриваются здесь.
- Дозапуск оборвавшегося хода при следующем старте приложения — отдельная фича.
- Защита heartbeat-ходов.

## 12. Definition of Done

- Ход, начатый с экрана, доезжает до записи ответа при свёрнутом приложении.
- Уведомление появляется только если ход затянулся, и исчезает вместе с ходом.
- Ход, не уложившийся в окно при свёрнутом приложении, честно падает с возможностью
  «Повторить», а не пропадает молча.
- Ход при приложении на экране не прерывается по потолку никогда.
- Отказ в захвате защиты не меняет наблюдаемое поведение по сравнению с сегодняшним.
- Юнит-тесты, debug-сборка и `traxer check` проходят; ручной прогон на устройстве выполнен.
