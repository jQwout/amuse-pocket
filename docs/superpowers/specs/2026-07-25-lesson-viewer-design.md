# Десктопная читалка уроков (lesson-viewer)

Дата: 2026-07-25. Статус: дизайн согласован в чате, ожидает review.
Ветка: `tools/lesson-viewer`.

## 1. Цель

Смотреть контент уроков (`app/src/main/assets/lessons/*.json`) на десктопе, не собирая
и не устанавливая Android-приложение.

Боль, которую лечим: чтобы проверить один шаг урока, сейчас надо собрать APK, поставить
его на телефон или эмулятор, зайти в академию, открыть урок и прокликать до нужного шага.
Правка одной строки в JSON стоит минут. Плюс на экране телефона видно один шаг за раз,
а при вычитке урока нужен весь его текст сразу.

Не-цель: показать, КАК урок выглядит в приложении. Это читалка контента, а не превью
внешнего вида. Про верность рендера — раздел 9.

## 2. Зафиксированные решения

1. **Ничего общего с `:app` не создаём.** Ни общего модуля, ни `srcDir` на его исходники,
   ни правок в самом `:app`. Причина: код агента ещё в движении, и вырезать из него общий
   модуль сейчас — значит переделывать вырезку потом. Пересмотреть, когда код агента
   зафиксируется.
2. **Отдельная Gradle-сборка**, которой нет в `settings.gradle.kts`. Основной проект её не
   видит: ни новых модулей, ни правок каталога версий, ни индексации в Android Studio.
   Это же снимает риск дублей классов, который уже ломал сборку на `.claude/worktrees/*`.
3. **Уроки читаются с диска по пути**, а не из ресурсов сборки. Правка JSON видна по кнопке
   «Перечитать», без пересборки вьюера.
4. **Свои модели данных** (раздел 4), скопированные по смыслу, а не подтянутые из `:app`.
5. **Весь урок одной прокруткой**, а не по шагу с кнопкой «Далее».
6. **Только чтение.** Ничего не кликается, состояние прохождения не ведётся.
7. Compose Desktop, а не генерация HTML: HTML пришлось бы выкинуть, если позже захочется
   настоящих карточек, а Compose Desktop до них доживёт.
8. **Вне traxer.** Ни записи в `traceability.yaml`, ни маркеров `@trace`, ни трейлера
   `Trace:` в коммитах вьюера. Причина: traceability описывает продукт, а это инструмент
   разработчика, живущий вне сборки приложения. Если вьюер когда-нибудь станет частью
   продукта — завести id тогда.

## 3. Размещение и сборка

```
tools/lesson-viewer/
  settings.gradle.kts        # самостоятельная сборка, rootProject.name = "lesson-viewer"
  build.gradle.kts           # kotlin("jvm") + org.jetbrains.compose
  src/main/kotlin/…
  src/test/kotlin/…
```

Каталог не входит в `settings.gradle.kts` корневого проекта, поэтому для Gradle основного
проекта его не существует. Запуск — `./gradlew run` из `tools/lesson-viewer/`.

Зависимости: `org.jetbrains.compose` (версия, совместимая с Kotlin 2.3 — уточняется при
реализации), `kotlinx-serialization-json`. Больше ничего.

Удаление вьюера = удаление каталога `tools/lesson-viewer/`.

## 4. Модель данных

`LessonStep` в `:app` — плоский `@Serializable`-класс, у которого все поля кроме `type`
имеют дефолты. Поэтому модель вьюера — прямая калька без полиморфизма, разбираемая
`Json { ignoreUnknownKeys = true }`.

```kotlin
@Serializable
data class Lesson(
  val id: String = "",
  val title: String = "",
  val description: String = "",
  val steps: List<LessonStep> = emptyList(),
)

@Serializable
data class LessonStep(
  val type: String = "",
  // text
  val text: String = "", val note: String = "",
  // quiz
  val questions: List<QuizQuestion> = emptyList(),
  // image
  val asset: String = "", val url: String = "", val caption: String = "",
  val imageKey: String = "", val alt: String = "",
  // reveal / fill
  val question: String = "", val answer: String = "", val template: String = "",
  // concept
  val term: String = "", val definition: String = "", val example: String = "",
  // example
  val label: String = "", val parts: List<ExamplePart> = emptyList(),
  // sort / match
  val instruction: String = "", val items: List<String> = emptyList(),
  val pairs: List<MatchPair> = emptyList(),
  // scenario
  val situation: String = "", val q: String = "", val options: List<String> = emptyList(),
  val correct: JsonElement? = null, val explain: String = "",
  // input / challenge (в уроках пока не встречаются)
  val prompt: String = "", val hint: String = "", val task: String = "",
)
```

`correct` полиморфен ровно как в `:app`: у `sort` это массив индексов, у `scenario` —
одно число. Разбирается через `JsonElement`, при отсутствии/мусоре даёт `null`/`-1`,
а НЕ `0` — иначе вьюер молча пометил бы первый вариант правильным (тот же класс бага,
что чинил `f646e64` в приложении).

Модель сознательно продублирована. Расхождение с `:app` ограничено тем, что новое поле
урока не отобразится, пока его не добавят сюда — это ловится тестом из раздела 8.

## 5. Чтение уроков

Каталог уроков ищется относительно рабочего каталога процесса. При запуске `./gradlew run`
из `tools/lesson-viewer/` рабочий каталог — сам `tools/lesson-viewer/`, поэтому путь по
умолчанию `../../app/src/main/assets/lessons` разрешается в корень репозитория.

Путь переопределяется системным свойством `-Dlessons.dir=…`. Если каталог по умолчанию не
найден, вьюер не падает, а показывает сообщение по пункту 7.4 — иначе запуск из другого
места выглядел бы как «уроков нет».

Список уроков — `*.json` в каталоге, отсортированные по имени файла. Порядок
педагогической последовательности (`ROADMAP_LEVELS` в `:app`) намеренно не воспроизводим:
он живёт в коде приложения, и его копия здесь была бы ещё одним источником расхождения.

Кнопка «Перечитать» перечитывает каталог целиком и заново разбирает открытый урок.

## 6. UI

Одно окно, две панели.

**Слева** — список уроков: имя файла и заголовок из `title`. Выбор — обычное состояние
(`var selected by remember`), без навигационной библиотеки.

**Справа** — весь урок одной вертикальной прокруткой. Каждый шаг — карточка с плашкой
типа (`text`, `quiz`, `reveal`…) и порядковым номером, чтобы номер шага можно было назвать
вслух, сверяясь с приложением.

Рендер по типам (12 типов реально встречаются в уроках; счётчики — на 2026-07-25):

| Тип | Встреч | Как рисуем |
|---|---|---|
| `text` | 214 | абзац текста |
| `quiz` | 25 | вопрос, варианты списком, правильный подсвечен, под ним `explain` |
| `scenario` | 18 | ситуация, вопрос, варианты, правильный подсвечен, `explain` |
| `reveal` | 15 | вопрос и ответ друг под другом (ничего не скрыто) |
| `image` | 13 | картинка из `asset`/`imageKey`, под ней `caption` |
| `concept` | 13 | термин, определение, пример |
| `match` | 10 | инструкция и пары «термин — определение» |
| `sort` | 7 | инструкция, элементы и массив `correct` (см. ниже) |
| `fill` | 4 | `template` с подставленным в пропуск `answer` |
| `example` | 2 | `label` и части с их ролями |
| `profile`, `persona`, `language` | по 1 | служебные шаги онбординга — заголовок и `text` |

Интерактивные по смыслу типы (`quiz`, `sort`, `match`, `scenario`, `fill`) показываются
сразу с ответом: вьюер нужен для вычитки, а не для прохождения.

Про `sort`: семантика массива `correct` (индекс элемента для позиции, или целевая позиция
для элемента) в этой спеке НЕ фиксируется — её надо прочитать в `SortCardView`
(`DrivenUiCardViews.kt`) при реализации и сослаться на источник комментарием. Пока она не
подтверждена, шаг рисуется как элементы в авторском порядке плюс сырой `correct` рядом:
показать «правильный порядок», угадав семантику неверно, хуже, чем не показывать вовсе.

Картинки: `imageKey` разворачивается в `lessons/images/{imageKey}.svg`, иначе берётся
`asset`. SVG рисуется штатным `loadSvgPainter` Compose Desktop. Поле `url` (сетевой
фолбэк) не поддерживается — вместо картинки показывается плашка с самим URL.

## 7. Обработка ошибок

Вьюер должен показывать то, что в приложении молча превращается в пустоту:

1. **Урок не разбирается** — в списке помечен, справа текст ошибки сериализации и имя
   файла. Остальные уроки продолжают открываться.
2. **Неизвестный тип шага** — красная плашка «неизвестный тип: `<type>`» и сырой JSON шага.
3. **Картинка не найдена или не рисуется** — красная плашка с путём, который искали.
4. **Каталог уроков не найден** — вместо списка сообщение с ожидаемым путём и подсказкой
   про `-Dlessons.dir`.
5. **`correct` битый или отсутствует** — правильный вариант не подсвечивается ни один,
   и рисуется пометка, что ключ битый. Молчаливого «правильный первый» быть не должно.

## 8. Тестирование

Один тест, он же смысл всей затеи как инструмента:

`AllLessonsParseTest` — проходит по всем `*.json` в каталоге уроков и проверяет, что
каждый разбирается в `Lesson`, и что `type` каждого шага входит в список известных вьюеру.
Падение = либо битый урок, либо модель вьюера отстала от `:app`.

UI не тестируем: это одноразовый инструмент, а не продукт.

## 9. Что осознанно НЕ входит

- **Верность внешнего вида.** Ни glass, ни Haze, ни шрифта Lora, ни настоящих
  `DrivenUiCardViews`. Вьюер отвечает на вопрос «правильный ли текст урока», а не «как
  этот шаг выглядит на телефоне». Второе потребует общего модуля — отдельный разговор
  после фиксации кода агента.
- LLM, «переспросить», свободные вопросы по ходу урока.
- Room, прогресс прохождения, состояние между запусками.
- Интерактив: ничего не кликается и не проверяется.
- `RoadmapScreen` и педагогический порядок уроков.
- Правка уроков из вьюера — только чтение.

## 10. Риски

1. **Версия Compose Desktop против Kotlin 2.3.** Проверяется первым делом: пустое окно
   должно собраться и открыться до того, как будет написано что-то ещё.
2. **`loadSvgPainter` против конкретных SVG уроков.** 12 файлов в `lessons/images/`,
   часть могла быть нарисована в расчёте на Coil. Если какой-то не рисуется — красная
   плашка по пункту 7.3, а не падение окна.
3. **Расхождение модели.** Ограничено и ловится тестом из раздела 8.
4. **Разрастание.** Соблазн «дорисовать до настоящих карточек» превратит одноразовый
   инструмент в второй UI без общего кода. Граница зафиксирована в разделе 9; выход за
   неё — повод вернуться к разговору про общий модуль, а не расширять вьюер.
