# Урок 02: подключение внешних возможностей через MCP

> **Цель урока.** Понять, что такое MCP (Model Context Protocol), чем он
> отличается от локальных навыков из [урока 01](./01-sozdanie-navykov.md), и как
> по нему подключить к ассистенту возможности, которые живут *вне* приложения.
>
> **Предпосылка.** В уроке 01 навык был «зашит» в приложение: описание в system
> prompt + код в `DrivenUiEngine.kt`. Это удобно, но у такого подхода есть
> потолок: каждый новый навык требует пересборки приложения, и навык не может
> сходить во внешний мир (в вашу БД, в чужой API, в файловую систему). MCP
> снимает оба ограничения.

---

## 1. Что такое MCP и зачем он нужен

**MCP (Model Context Protocol)** — открытый протокол (создан Anthropic), который
стандартизирует, как приложение-хост подключает к языковой модели внешние
**инструменты**, **данные** и **промпты**. Грубо говоря, это «USB-C для
LLM-возможностей»: один разъём — много устройств.

Сравним два мира на примере нашего приложения:

| | Локальный навык (урок 01) | MCP-инструмент (этот урок) |
|---|---|---|
| Где живёт логика | внутри APK, в `DrivenUiEngine.kt` | в отдельном **MCP-сервере** (свой процесс/сервис) |
| Когда появляется | на этапе сборки | **в рантайме**, обнаруживается по сети |
| Что может делать | рисовать UI из готовых данных | ходить в БД, в чужие API, в файлы, в интернет |
| Кто ещё может им пользоваться | только это приложение | любой MCP-хост: Claude Desktop, Claude Code, ваш бот |

**Главная мысль:** MCP-инструмент — это «навык, который вынесли наружу и сделали
переносимым между хостами». Анатомия из урока 01 («объявление → контракт →
парсер → обработчик») сохраняется, но обработчик теперь — на другом конце
соединения.

---

## 2. Универсальная анатомия MCP

MCP — это архитектура «клиент-сервер» поверх **JSON-RPC 2.0**.

```
  ХОСТ (наше приложение, Claude Desktop, Claude Code)
   │
   ├── MCP-КЛИЕНТ ───────(JSON-RPC: stdio | HTTP)──────► MCP-СЕРВЕР #1  (погода)
   │                                                  └─► MCP-СЕРВЕР #2  (ваша БД)
   └── LLM (модель)
```

**Три роли:**
- **Host** — приложение, в котором живёт модель и UI (у нас — Android-приложение).
- **Client** — коннектор внутри хоста; ровно один клиент на одно соединение с сервером.
- **Server** — отдельная программа, которая публикует возможности.

**Сервер публикует три вида примитивов:**
1. **Tools (инструменты)** — функции, которые модель может вызвать
   (`tools/list`, `tools/call`). Это прямой аналог наших навыков.
2. **Resources (ресурсы)** — данные/контекст, которые хост может прочитать и
   подложить модели (файлы, записи БД) — `resources/list`, `resources/read`.
3. **Prompts (промпты)** — переиспользуемые шаблоны запросов, которые сервер
   предлагает хосту.

**Транспорт** (как байты ходят между клиентом и сервером):
- **stdio** — сервер запускается как локальный процесс, общение через
  stdin/stdout. Идеально для локальных инструментов на той же машине.
- **Streamable HTTP** — сервер живёт по сети (URL), общение по HTTP. Для
  удалённых/общих серверов.

**Рукопожатие.** Соединение начинается с `initialize`: стороны обмениваются
версиями протокола и **возможностями** (capability negotiation). После этого
хост обычно сразу зовёт `tools/list`, чтобы узнать каталог инструментов.

> Сопоставьте с уроком 01: `tools/list` = «объявление навыка», `input_schema`
> инструмента = «контракт», `tools/call` = «вызов», ответ сервера = результат
> «обработчика». Те же 4 части — просто по сети и по стандарту.

## 3. Как это связано с нашим приложением

Сейчас путь возможности такой (см. `ChatViewModel.kt` и `NvidiaClient.kt`):

```
system prompt (каталог навыков, зашит в код)
        │
        ▼
   NvidiaClient.generateResponse()  ──HTTP──►  NVIDIA NIM (LLM)
        │
        ▼
   модель отвечает JSON {template, params}
        │
        ▼
   DrivenUiEngine.parseJsonString()  →  локальный рендер
```

Каталог навыков статичен: он целиком лежит в строке `systemPrompt`. Чтобы
добавить MCP, мы вставляем между моделью и «обработчиком» новый слой —
**MCP-клиент**, который:

1. на старте подключается к серверам и зовёт `tools/list`;
2. **переиспользует механизм из урока 01** — кладёт описания полученных
   инструментов в тот же system prompt (динамически, а не хардкодом);
3. когда модель просит вызвать инструмент, **маршрутизирует** вызов не в
   `DrivenUiEngine`, а в `McpClient.callTool(...)`, и возвращает результат в
   диалог.

```
   tools/list (рантайм)  ─────────────┐
                                       ▼
system prompt = [локальные навыки] + [MCP-инструменты]
        │
        ▼
   модель решает: render_card  ИЛИ  вызов инструмента
        │                              │
        ▼                              ▼
   DrivenUiEngine            McpClient.callTool() ──► MCP-сервер
   (локально, урок 01)            (наружу, этот урок)
```

Так локальные навыки и внешние инструменты сосуществуют, а модель выбирает
нужное. Полноценный MCP-клиент на Kotlin — заметный объём кода, поэтому ниже
практика разбита на «сервер целиком» (его можно запустить сегодня) и «эскиз
клиента» (как встроить в приложение).

## 4. Практика, часть А: пишем минимальный MCP-сервер

Сервер проще всего написать на Python с официальным SDK. Он публикует один
инструмент `get_forecast`.

```python
# weather_server.py  (pip install "mcp[cli]")
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool()
def get_forecast(city: str) -> str:
    """Вернуть короткий прогноз погоды для города."""
    # здесь мог бы быть реальный вызов погодного API
    return f"{city}: +18°C, ясно, ветер 3 м/с"

if __name__ == "__main__":
    mcp.run()  # транспорт stdio по умолчанию
```

Что здесь есть из анатомии раздела 2:
- **объявление** — имя `get_forecast` и docstring (его получит хост через `tools/list`);
- **контракт** — сигнатура `city: str` автоматически становится `input_schema`;
- **обработчик** — тело функции.

Проверить сервер без всякого приложения можно инспектором:

```bash
mcp dev weather_server.py     # откроет MCP Inspector в браузере
```

## 5. Практика, часть Б: эскиз MCP-клиента в приложении

В приложении появляется слой `McpClient` рядом с `NvidiaClient`. Псевдокод
ключевых шагов (Kotlin-стиль, без деталей транспорта):

```kotlin
class McpClient(/* транспорт: процесс или URL */) {
    // 1. Рукопожатие + получить каталог инструментов
    suspend fun listTools(): List<McpTool>          // -> tools/list

    // 2. Вызвать инструмент по имени с аргументами
    suspend fun callTool(name: String, args: JSONObject): String  // -> tools/call
}
```

Интеграция в `ChatViewModel`:

```kotlin
// (1) на старте: динамически дополняем каталог в system prompt
val mcpTools = mcpClient.listTools()
val toolsCatalog = mcpTools.joinToString("\n") { t ->
    """- ${t.name}: ${t.description}. Аргументы: ${t.inputSchema}"""
}
// добавляем toolsCatalog в systemPrompt РЯДОМ с описанием render_card-навыков

// (2) при ответе модели: если это вызов инструмента — маршрутизируем в MCP
if (parsed.template == "mcp_call") {
    val result = mcpClient.callTool(parsed.params.getString("tool"),
                                    parsed.params.getJSONObject("args"))
    // (3) кладём result обратно в историю и просим модель ответить пользователю
    repository.insertMessage(ChatMessage(sender = "system", content = result))
}
```

Обратите внимание: пункт (1) — это буквально механизм «объявления» из урока 01,
только каталог теперь приходит по сети, а не лежит константой.

> В реальном проекте вместо самодельного `{"template":"mcp_call"}` лучше
> использовать **function calling** провайдера (если поддерживается), а MCP-схему
> инструмента отдавать туда напрямую — тогда парсинг берёт на себя SDK.

## 6. Перенос: тот же сервер в других хостах

Сервер из раздела 4 не привязан к нашему приложению. Тот же `weather_server.py`
подключается:
- к **Claude Desktop** — добавлением записи в конфиг MCP-серверов;
- к **Claude Code** — командой `claude mcp add` (stdio или HTTP-сервер);
- к **любому другому MCP-хосту** — потому что протокол один.

Это и есть выгода стандарта: один раз написанный сервер работает во всех хостах,
а одному хосту доступны все серверы. Сравните с локальным навыком из урока 01,
который жил только внутри одного APK.

## 8. Частые ошибки

- **Путают ресурс и инструмент.** Инструмент модель *вызывает* (действие);
  ресурс хост *читает* и подкладывает как контекст (данные). Не делайте «чтение
  файла» инструментом, если это просто контекст.
- **Слишком общий инструмент.** `do_everything(query)` модель применяет невпопад.
  Дробите на узкие инструменты с понятными `description` — как и навыки в уроке 01.
- **Описания на сервере «для людей».** `description` инструмента читает модель —
  пишите его как инструкцию для модели, а не как комментарий разработчику.
- **stdio там, где нужен HTTP.** stdio — для локального процесса на той же машине;
  для удалённого/общего сервера берите Streamable HTTP.
- **Доверие к выводу инструмента.** Результат MCP-сервера — внешние данные.
  Не подставляйте их слепо в привилегированные действия; относитесь как к
  непроверенному вводу.
