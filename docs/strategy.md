# Стратегия: visibility → exit

> **Дата:** 2026-06-24 · **Статус:** активный план, придерживаемся
> **Связано:** [business-eval.md](./business-eval.md) — полная аналитика; этот файл — короткий «север», к которому возвращаемся при каждом решении.

## 0. Стратегическая цель (north star)

**Стать заметными в глобальном AI-dev сообществе за 9–12 месяцев и продаться стратегу.**

Не ARR. Не unit-economics. Не enterprise.
Это меняет почти всё: что мы строим, что меряем, что **не** делаем.

**Целевой диапазон сделки: $1–10M на команду (acqui-hire).** Это **достаточно**, не «компромисс». Из этого следуют ключевые тактические выводы, которые задают всё дальнейшее:

- **Time-to-exit > size-of-exit.** Шесть месяцев до сделки на $2M лучше, чем восемнадцать до сделки на $8M.
- **Не растим команду** ради «видимости масштаба». Acqui-hire на 2–3 человек — нормальный исход.
- **VC-раунд не нужен.** Любое внешнее финансирование размывает долю и удлиняет сроки до сделки (инвесторы хотят больший exit). Bootstrap или микро-grant (Y Combinator? AI-grant-программа Anthropic/OpenAI?) — потолок.
- **Терпим худшую unit-economics** в продукте ради скорости — оптимизируем сигнал, не себестоимость.
- **Не ждём «правильной цены».** Первый разумный оффер от стратега — берём, если он в диапазоне.

## 1. Что это означает в практических решениях

**Архитектурное основание:** продукт построен по схеме **клиент + сервер**. Уроки, методика, evaluation, прогресс, дополнительные персоны и динамический контент живут **на сервере**. Клиент — это renderer + tool runner + чат-UI. Это позволяет применить классическую модель **«OSS client, closed server»** (Cursor, Tailscale, Vercel/Next.js, Mattermost, Supabase, Element/Matrix). Эта модель — наш главный стратегический рычаг и применяется с альфы, а не позже.

| Решение | Acquisition-стратегия | Что **не** делаем |
|---|---|---|
| Цена | **Free навсегда + опц. Pro $9.99 как сигнал ARR**, не воронка | Не строим B2B sales, не гоняемся за корпоративными контрактами |
| Метрика недели | DAU, GitHub stars (client repo), X-импрешны, demo-видео-views | НЕ MRR, НЕ retention day-30, НЕ CAC/LTV |
| Канал | Контент (X, HN, PH, YouTube), demo-видео, OSS-client community, closed beta waitlist, dev-инфлюенсеры | НЕ performance-маркетинг, НЕ SEO long tail |
| Roadmap | Демо-достойные фичи (агент трогает реальный телефон → видео виральное); сервер-стороннее всегда первично, клиент-сторонее — второе | НЕ внутренние tooling-фичи, которых не видно снаружи |
| Open source | **Клиент OSS (Apache-2.0 или MIT). Сервер закрыт.** Уроки, методика, evaluation, прогресс, расширенный контент — серверная IP, никогда не публикуется | Не открываем сервер ни на каком этапе; не открываем proprietary-промпты уроков и evaluation-логику |
| Платформы | iOS как можно раньше — половина AI-X-audience на iPhone | НЕ Windows / Web-десктоп до экзита |

**Эвристика принятия решений:** *«Если бы Anthropic/Cursor/Duolingo увидели это завтра — это сделало бы их хотеть купить нас сильнее или слабее?»* Если ответ «слабее» или «нейтрально» — не делаем.

**Дополнительный фильтр для клиент/сервер:** *«Если эту вещь увидит конкурент, скопировав клиент-репо — теряем ли мы что-то ценное?»* Если да — это серверная компонента, не клиентская.

## 1.5 Граница клиент/сервер (что открываем, что прячем)

Граница — критическая. Если в OSS-клиенте окажется хоть один файл уроков или evaluation-prompt — IP уходит с первым же `git clone`. Граница не «по компонентам Android», а **по «можно ли скопировать смыслово»**.

### Клиент (OSS, Apache-2.0)
**Цель:** renderer + tool runner + чат-shell + SDK для общения с любым сервером, который реализует протокол.

- Chat UI (Jetpack Compose / iOS-ный аналог через KMP)
- `DrivenUiEngine` — рендеринг карточек по JSON-контракту
- Tool runner — `CalendarTool`, `AlarmTool`, `EmailTool`, `file_tool`, `work_manager`, `memory_tool` (логика выполнения, не данные)
- Скилл-формат (JSON Schema + парсер) — это **публичный стандарт**, его как раз и продвигаем как «AI Open Pocket Skill Schema»
- Multi-provider LLM-клиент (NIM / Groq / GitHub Models — без ключей, ключи приходят с сервера или вводятся юзером)
- Базовые персоны (1–2 «дефолтные», простые) — символическая демонстрация формата
- Локальная БД и offline-режим
- Tool trace UI
- Сетевой клиент к нашему серверу (открытый API-протокол)

### Сервер (closed, проприетарно навсегда)
**Цель:** уроки, методика, evaluation, прогресс, динамика контента, премиум-аудитория.

- **Все уроки роадмапа** — сейчас лежат в `app/src/main/assets/prompts/roadmap/*.md`, **необходимо перенести на сервер до OSS-релиза клиента**. Это главный actionable пункт.
- Evaluation-логика (квизы, проверка прогресса, сертификаты)
- **Расширенные персоны** — не дефолтные, а «авторские» (платные / эксклюзивные); базовые могут остаться в клиенте
- Skill marketplace (каталог + распространение)
- LLM-прокси с нашими ключами (для бесплатного и Pro-уровней)
- A/B-тесты контента, dynamic difficulty, аналитика
- Пользовательские профили, прогресс, синхронизация (если будет)
- Биллинг (Stripe, App Store, Google Play)
- Серверная часть чат-проектов (project-prompts, memory-namespace, инжект контекста)

### Серая зона — переехать на сервер ДО OSS-релиза клиента
Эти сущности сейчас в клиенте, но открыть их = подарить ключевой IP. К моменту публичного OSS-релиза они должны загружаться с сервера:

| Сущность | Сейчас | Целевое место |
|---|---|---|
| Уроки роадмапа | `assets/prompts/roadmap/*.md` | сервер, fetch по запросу |
| Tutorial-промпт | `assets/prompts/tutorial.md` | сервер |
| `system_base.md` | `assets/prompts/system_base.md` | сервер (или базовая публичная версия + серверный «production» override) |
| Премиум-персоны | сейчас все 7 в `assets/personas/` | оставить 2 в клиенте как демо, 5 на сервер |
| Каталог моделей | `assets/config/models.json` | сервер (динамическая ротация без релиза клиента) |
| Каталог апов (`assets/apps/*.json`, v0.5) | в клиенте | сервер |

**Правило:** клиент должен **корректно работать без сервера** (offline-режим, базовая функциональность), но **«интересное» — уроки, прогресс, advanced — только через сервер.** Это даёт OSS-репутацию без подарка IP.

## 3. Сигналы, которые покупают

Что **на самом деле** смотрят M&A-команды в AI-secone 2026 (по публичным сделкам Adept→Amazon, Inflection→Microsoft, Multi→OpenAI, Character→Google):

1. **DAU и кривая роста** — линейные продукты не покупают, exponential покупают.
2. **Brand awareness** в нише — упоминания на X / в подкастах / в блогах.
3. **GitHub stars и community** — proxy для культурного влияния.
4. **Distinctive IP** — что-то, что нельзя сделать «у себя за квартал». Наша скилл-архитектура (`docs/lessons/01-sozdanie-navykov.md` §§ 2, 5) — именно это.
5. **Team caliber** — кого фактически покупают.
6. **Strategic adjacency** — закрываем дыру в их roadmap.

Что **не** покупают (или покупают с дисконтом):
- ARR $50–500K — слишком мало для revenue-multiple, слишком много для acqui-hire (мешает «купить только команду»).
- Enterprise pipelines без deals — pipe гадается, deals — нет.
- Большая команда — дороже acqui-hire.

**Sweet spot:** маленькая команда (2–5 чел.) + сильный продукт + видимая аудитория + чистая IP + zero-to-low revenue.

## 4. Перепрошитый 90-дневный план (под visibility, не ARR)

### Альфа: 0–6 недель — заложить вирусную механику и закрыть pre-launch
Цель: **выйти на запуск с готовым «гнездом» внимания, а не с холодного старта.**

1. **100 RU/Android альфа-тестеров** — как раньше, источник продуктовых инсайтов. Без выручки.
2. **Чистка артефактов** для возможности красивого open-source-старта:
   - `com.example` → реальный package
   - `debug.keystore.base64` из git вычистить, history переписать (`git filter-repo`)
   - Минимальный CI с unit-тестами
3. **«Сезон 2» уроков 8–10:** function calling, MCP, мульти-агент. Это контент для viral-demo-роликов.
4. **Demo-видео #1:** «Я научил телефон ставить мне встречи через AI-агента за 60 секунд» — 60-90 сек., iOS Reminders / Google Calendar tools в действии. Эта запись поедет на X, HN, PH.
5. **Twitter/X-аккаунт в режиме build-in-public:** 3–5 постов в неделю про разработку, видео тулов, скриншоты уроков. Накопить 500–1000 подписчиков **до** запуска. На запуск это превращается в первичный bump.
6. **Lurk targets:** подписаться, читать, комментировать у swyx, simonw, alexalbert__, deepseek_ai, anthropicai, cursor_ai, dr_cintas. Стать узнаваемой репликой в треды.

### Pre-beta: 6–12 недель — снять платформенные ограничения и подготовить client/server split
7. **EN-локализация.** Без неё HN/PH не работают.
8. **iOS-релиз через Compose Multiplatform.** Хотя бы read-only beta. Без iOS — половина X-аудитории нас не увидит.
9. **Закончить переезд уроков и premium-промптов на сервер** (см. §1.5, «серая зона»). **Блокер для OSS-релиза клиента** — пока эти ассеты в клиентском репо, открывать его нельзя.
10. **Подготовить OSS-репо клиента** к публикации: чистая git history (`git filter-repo` для `debug.keystore.base64`), реальный namespace, Apache-2.0 LICENSE, CONTRIBUTING.md, CLA, README с «AI Open Pocket Skill Schema» как центральным офером.
11. **Закрытый бета-waitlist** на сервер-side доступ (Pro-фичи, уроки) с потолком 1 000 invites. Управляемый дефицит = виральный хук. Один-на-один inviting dev-инфлюенсерам (swyx, simonw, alexalbert__) — премиум-доступ + бесплатный Pro навсегда — основа PR-канала.
12. **Paid tier $9.99/мес. с trial 14 дней** — не как воронка, как **сигнал, что есть платящие** (важно для M&A-pitch). Конверсия 2–5% — норм, не оптимизируем.
13. **Лендинг в качестве «product company»**: команда, манифест, blog с инженерными постами + ссылки на OSS-клиент и MIT-документацию скилл-формата.

### Beta launch: 12–16 недель — главный шум (OSS-клиент публикуется здесь)
14. **Скоординированный launch-week** (один pitch с двумя гранями: продукт + OSS-клиент = двойной hook):
    - Понедельник: Show HN с постом «I built a pocket AI agent trainer — every lesson is a prompt, every tool is real. Client is open source.»
    - Вторник: Product Hunt
    - Среда: thread на X с demo-роликом + анонс OSS-клиента
    - Четверг: пост в r/LocalLLaMA + r/ClaudeAI + r/Replit (для последних — упор на OSS-аспект, эта аудитория особенно реагирует)
    - Пятница: ретроспектива «what we learned, here's the data» — превращает launch в постоянный контент.
15. **Outreach по подкастам:** Latent Space (swyx), MLST, Practical AI, Changelog (специально под OSS-angle). Pitch: «we built the Duolingo for AI agents, the client is OSS and follows our open Skill Schema».
16. **Demo-видео #2 и #3** — приурочить к launch. Одно специально показывает, как написать кастомный скилл по нашей открытой спеке (это HN-bait).
17. **Цель к концу 16-й недели:** 5K GitHub stars на клиент-репо, 50K+ X-импрешн, 10K+ install, 1 публикация в TechCrunch/Verge/Engadget, упоминание Skill Schema в ≥3 dev-newsletters.

### После launch: 4–9 месяцев — войти в радар покупателей
16. **Ежемесячный demo-day** — публичный stream / X Space «what's new this month». Это форсирует ритм публичной видимости.
17. **Партнёрство с одним из MCP-серверов** (Postgres, Brave Search, Slack) — co-marketing.
18. **Серия инженерных постов:** «как мы рисуем UI через LLM», «как мы делаем скиллы переносимыми», «почему мы выбрали Compose Multiplatform». Это контент, который приводит acquirer-инженеров.
19. **Появиться на конференции:** AI Engineer Summit, droidcon, GDG-events. Презентация = ещё одна точка узнаваемости.
20. **Тёплые контакты с DevRel / corp-dev** Anthropic, Duolingo, Replit, Cursor через X. Не pitch — но «look at what we built» периодически.

### Месяцы 9–12 — момент истины
21. **Если виральность пошла:** проактивный pitch corp-dev top-3. Подготовить deck «strategic fit slide» для каждого из них отдельно.
22. **Если виральность не пошла:** триггер для одного из двух пивотов — **Plan B** (B2B-corp-обучение, см. business-eval.md §§ 6, 8) или **Plan C** (детская аудитория, см. §9 ниже). По умолчанию — Plan C, как более стратегически защитимый и с другим acquirer-set'ом.

## 5. Что мы НЕ делаем (явно)

- Не строим enterprise-sales-команду
- Не гонимся за SOC 2 / EU AI Act до сделки (это покрывает покупатель)
- Не делаем мультиплатформенный десктоп до экзита
- Не пилим много локалей (EN + RU достаточно для виральности)
- Не оптимизируем retention day-30 (ROI ниже, чем у поступающего внимания)
- Не пилим визуальные конструкторы скиллов в UI пользователя — слишком дорого на нашу команду; пользователь либо собирает скилл через промпт-чат с агентом, либо ждёт каталог от нас
- **Не открываем сервер ни на каком этапе** — даже как «community edition». Это была бы потеря единственного ценного IP-asset'а
- **Не публикуем proprietary-промпты уроков** в OSS-клиент — даже в качестве «дефолтных примеров»
- Не интегрируемся с CRM / Slack / Outlook (это для B2B, не для виральности)

## 6. Метрики, по которым меряемся каждую неделю

С client/server-моделью GitHub stars возвращаются как осмысленная метрика — клиент-репо публичен. Вес делится между OSS-сигналом (stars, contributors, форки), brand-сигналом (X, видео) и продуктовым (installs, WAU).

| Метрика | Источник | Цель к концу 90 дней |
|---|---|---|
| GitHub stars (client repo) | github.com | **5 000** |
| Внешние контрибьюторы (PRs merged) | git | **≥15** |
| Сторонние скиллы по нашей Skill Schema | manual / search | **≥5 видимых** (gist, blog, fork) |
| X followers | X analytics | 5 000 |
| X impressions на главные посты | X analytics | суммарно >500K |
| Demo-video views (cumulative) | YouTube + X | >250K |
| Waitlist signups | лендинг | 5 000 |
| Active installs (после launch) | Play Console + App Store Connect | 10 000 |
| WAU / MAU | Amplitude / PostHog | WAU 3K+, MAU 8K+ |
| Press mentions (Tier-1) | manual track | 1+ Tier-1 (TC/Verge/Eng.), 3+ Tier-2 (newsletters) |
| Influencer-tweets (dev-tier) | manual track | ≥10 органических постов от 5K+ follower dev-аккаунтов |
| Paid users (как сигнал) | Stripe | 50–200 (не оптимизируем — следим) |

MRR / retention D30 / CAC / LTV — только раз в квартал, для M&A-deck.

**Не меряем еженедельно:** MRR, retention D30, CAC, LTV. Их меряем раз в квартал, для M&A-deck.

## 6.5 Защита от «скопируют, не купят»

Главный риск всей стратегии. Полная защита невозможна — большой игрок с deep pockets копирует продукт за 3–12 мес. Реалистичная цель: **сделать копирование дороже и медленнее, чем покупку**, и сделать так, чтобы решение «build vs buy» в их совете вообще обсуждалось.

### Что **не** защищает (хотя соблазн использовать велик)
- Патенты в этой области — прайор-арт везде, бесполезно.
- «Мы сделали первыми» — fast followers в AI выигрывают чаще, чем first movers.
- Trade secrets / закрытый код — реверс-инжиниринг работающего приложения занимает недели.
- «У нас лучше UX» — копируется за месяц.
- Open source кода — могут просто форкнуть.

### Что реально защищает (по приоритету)

**1. Скорость к exit.** Главная защита. Чем быстрее мы достигаем «купить дешевле, чем построить», тем меньше у них времени принять решение «build». Сравнительная стоимость:
- 6 месяцев работы 4–6 senior-инженеров в Anthropic ≈ $1.5–3M в полностью загруженных costs.
- Acqui-hire нас на тех же $1.5–3M = они получают готовый продукт + команду + community, экономят 6 месяцев календарного времени.
- **Чем дольше мы существуем — тем больше у них стимула строить самим.** На 3-м месяце build-vs-buy 50/50, на 18-м месяце они уже строят (потому что их собственный launch уже близко).

**2. Client OSS + closed server = два moat'a за цену одного.** Клиент-серверная архитектура (см. §1.5) позволяет одновременно:
   - Открыть клиент → **community-as-standard moat** включён с альфы: скилл-формат становится «AI Open Pocket Skill Schema», GitHub stars работают как метрика, dev-инфлюенсеры форкают и пишут о нас, трансперанси-нарратив легитимизирует продукт в AI-dev-комьюнити.
   - Держать сервер закрытым → **IP-moat защищён**: уроки, методика, evaluation, прогресс, биллинг не утекают с `git clone`. Любой, кто форкает клиент, получает только пустую оболочку — нужно ещё переписать все уроки.
   - Прецедент: Cursor (OSS-форк VS Code → закрытый AI-сервер), Tailscale (OSS клиенты → закрытый control plane), Vercel (Next.js OSS → закрытая платформа), Supabase (libs OSS → managed backend). Все они защищены от копирования именно тем, что **ценность сидит в сервере, а адопшен — в OSS-клиенте**.
   - Эта модель — наш ответ на «скопируют, не купят»: чтобы скопировать продукт, нужно скопировать **сервер с уроками** (закрыт + сложен) ИЛИ воссоздать всю educational curriculum с нуля (долго). Скопировать клиент бессмысленно — это просто общедоступный SDK.

**3. Multi-provider, не Claude-only.** Если мы 100%-Claude-приложение, Anthropic не нужно нас покупать — они владеют моделью. Текущая архитектура NIM → Groq → GitHub Models уже правильная: мы — **стратегический ассет**, а не captive user. То же про Duolingo: если их интересует «not married to one LLM», multi-provider — плюс.

**4. Прямые отношения до оффера.** M&A почти всегда начинается со «знакомый знакомому». Тактически:
   - Tom Brown / Mike Krieger / Daniela Amodei (Anthropic) — добиться, чтобы один из них хотя бы лайкал наши X-посты.
   - Amjad Masad (Replit), Michael Truell (Cursor), Luis von Ahn (Duolingo) — аналогично.
   - Это не «pitch» — это «look at what we built» периодически, через X, через интервью на их подкастах (Latent Space часто гостит таких).
   - Хорошие лиды появляются у людей, кого M&A-команды покупателя видят в Twitter feed своего CEO.

**5. Distribution > technology.** На момент оффера у нас должно быть **то, что они не могут быстро купить иначе**: 10K+ активных пользователей именно в AI-dev сегменте. Anthropic может построить технологию за квартал, но «10K AI-engineers, обученных на нашей платформе» — нельзя. Прецеденты:
   - WhatsApp: 50 сотрудников, 450M пользователей → Facebook купил за $19B
   - Instagram: 13 сотрудников, 30M пользователей → Facebook купил за $1B
   - В обоих случаях дистрибуция была moat, не технология.

**6. Конкурирующие интересы покупателей.** Один интересант → они либо демпингуют, либо строят сами. Три интересанта → они конкурируют, и решение «build» проигрывает по срокам. Тактика — параллельно держать тёплый контакт с Anthropic + Duolingo + Cursor/Replit + Yandex/Sber. Не блефовать — реально культивировать все четыре линии.

**7. Defensive M&A leverage.** Если Anthropic не уверены, нужен ли им продукт, но **точно не хотят, чтобы нас купил Duolingo или Replit** — они купят защитно. Прецедент: Instagram → Facebook в 2012 (Facebook боялись Twitter / Google). Это работает, только если другие интересанты видимы.

**8. Acquireability hygiene с первого дня.** Чистый код, чистая IP, чистый cap table, чистые лицензии, без долгов перед сотрудниками. Любая friction в due diligence удлиняет сделку на месяцы — а время работает против нас (см. п. 1). Конкретно сейчас:
   - `com.example` → реальный namespace **до** первой публичной видимости.
   - `debug.keystore.base64` из git вычистить с переписыванием history.
   - Контракты с любыми контрибьюторами (если будут) — CLA или MIT-license с самого начала.
   - Никаких GPL-зависимостей (заразны для проприетарного продукта покупателя).

**9. Optionality narrative.** В разговоре с покупателем всегда должна быть **видимая опция Б**: «если не вы — мы возьмём $2M seed от a16z и продолжим расти». Не блеф — это должно быть реалистично. Опция-Б создаёт **срочность** у покупателя.

**10. Не быть слишком привязанными к одному vertical.** Если мы строго «учим Claude-разработчиков» — Anthropic смотрит на нас как на «свой сегмент, построим». Если мы «учим работать с агентами вообще» (включая MCP, LangChain, function-calling у любого провайдера) — мы инфраструктура, и каждый игрок боится, что нас купит конкурент.

### Эвристика на каждое решение
*«Делает ли это нас более защищаемой целью M&A — увеличивает ли community, скорость, многосторонний интерес, чистоту IP?»* Если нет — не делаем.

### Тактический минимум первых 90 дней
- **Перевести уроки + premium-промпты на сервер** (см. §1.5, серая зона) — **это блокирующий пункт** перед любым OSS-релизом клиента.
- **Опубликовать OSS-клиент** одновременно с beta-launch — отдельный репо `pocket-agent` (или нейтральное название), лицензия Apache-2.0, чистая history (без `debug.keystore`, без `com.example`).
- **Скилл-формат продвигаем как «AI Open Pocket Skill Schema»** — отдельная страница в репо, JSON Schema, 10+ примеров, документация. Цель — стать упоминаемым стандартом, как «Anthropic MCP» в своей нише.
- Multi-provider явно подсвечиваем в любом контенте — сигнал «инфраструктура, не вертикаль».
- Параллельно поддерживать минимум **2 направления M&A-разговоров** до конца beta launch.
- Чистка артефактов (`com.example`, keystore, GPL-зависимости, CLA для контрибьюторов) — **до** первого commit'а в публичный репо, потому что git history сделать чистой потом нельзя.

## 6.6 Чем выигрываем от client/server split (и что всё-таки теряем)

Модель «OSS-клиент + закрытый сервер» — это локально-оптимальная стратегия для visibility→exit. Она почти бесплатна в IP-терминах и даёт нам сразу несколько активов.

### Что выигрываем
- **GitHub stars обратно в метриках** — самый дешёвый канал в AI-dev community снова доступен.
- **Community-as-standard moat** включён со старта, без всякого «триггера».
- **Доверие через прозрачность** — пользователи могут лично убедиться, что отправляется на сервер. В эпоху AI privacy paranoia это значимый дифференциатор.
- **Виральные форки клиента** — «я форкнул и добавил тул для X» = бесплатный контент-маркетинг.
- **Контрибьюторская воронка** — лучшие контрибьюторы становятся кандидатами в команду (а после acqui-hire — частью deal'а).
- **Снижение due diligence-рисков** — открытый клиент = у покупателя на половину меньше неизвестного кода для аудита.
- **Запасной revenue stream** — кто-то может попросить self-hosted enterprise-вариант сервера. Сейчас не приоритет, но опция есть.

### Что теряем (и принимаем)
- **Открытый клиент даёт acquirer'у вариант «возьмём только сервер»** — теоретически Anthropic может построить свой клиент на базе нашего OSS, заинвестировав в свою curriculum. Митигация: к моменту M&A у нас уже есть **дистрибуция и бренд**, которые нельзя форкнуть.
- **«Зачем покупать, если SDK open?»** — митигация: покупают не SDK, а **сервер + бренд + curriculum + команду**. Это формулируется в M&A-deck'е.
- **Поддержка community-вопросов** — issues, PRs, доки. Стоит ~5–10 часов в неделю. Принимаем как операционный налог.
- **Меньше свободы ломать API клиент-сервер** — open SDK создаёт обязательства по версионированию. Митигация: явная политика «alpha API, может меняться» в первые 6 месяцев.

## 7. Риски этой стратегии (честно)

1. **Viral attempt не выстрелит.** Большинство launch-week не выстреливают. Митигация: подготовленная аудитория до запуска (X в build-in-public + альфа-тестеры).
2. **Acquirer waits too long.** Большие игроки могут долго смотреть → деньги кончатся. Митигация: paid tier даёт минимальный runway-сигнал; Plan B (B2B-corp-обучение, business-eval.md) и Plan C (детская аудитория, §9) — задокументированные пивот-опции с явными триггерами.
3. **Acquirers скопируют, не купят.** Anthropic может просто построить такое же. Митигация: distinctive IP (скилл-архитектура + педагогика) + скорость + community.
4. **EU AI Act compliance может всплыть у покупателя** на due-diligence. Митигация: держать архитектурную чистоту (local-first, no PII в облако без согласия) изначально.
5. **Соблазн «дождаться оффера получше».** Когда первый оффер $1–3M прилетает, легко начать тянуть в надежде на $10M+ через полгода. Митигация: записать «первый разумный оффер в диапазоне — берём» в §0 и держаться, потому что через полгода продукт может выдохнуться или большой игрок построит сам.

## 9. Plan C: пивот в детскую аудиторию

Реальная стратегическая опция, не запасной выход. Если Plan A (visibility→exit на adult AI-dev сегменте) не выходит на нужный темп к месяцу 6 — пивот в **детский продукт «учим работать с AI через игру»** с упрощёнными агентами и сильной визуальной составляющей.

Это не «маленькая корректировка», это **другая компания** в маркетинге, дистрибуции, регуляторике и acquirer-наборе. Поэтому фиксируем как отдельный план с явным триггером, чтобы не размывать энергию параллельной разработкой.

### 9.1 Почему это сильная опция

- **Underserved рынок.** Khanmigo, Synthesis School, Buddy.ai, Curio AI — рынок только формируется. Конкуренция в 10× меньше, чем у adult-AI-tools.
- **Сильный UI — реальный moat в детских продуктах.** Взрослые терпят уродливые продукты ради функции; дети и их родители — нет. Это игра, где наше «сильное юай» из задачи становится защитой.
- **«Sandbox/safety» story превращается из минуса в плюс.** Для adult-AI «мы не даём агенту делать опасное» — ограничение. Для детей — главная фича, за которую платит родитель.
- **Родитель платит, ребёнок пользуется.** Чёткая монетизация — в отличие от adult-AI, где все ждут бесплатного.
- **App Store «featured»-слоты в категории Kids/Education** реально достижимы — Apple и Google активно продвигают family-friendly edu-приложения. Это бесплатный distribution boost.
- **Меньше LLM-затрат.** Упрощённые агенты = меньшая модель = ниже unit-cost.
- **Acquirer-набор частично сильнее**, чем у Plan A (см. §9.3).

### 9.2 Жёсткие минусы и риски

- **COPPA + GDPR-K + UK Age Appropriate Design Code + ФЗ-152.** Регулятор вокруг детских данных — самый жёсткий блок в индустрии. Verified parental consent, ограничения на сбор данных, более строгий App Store review. Стартовый бюджет: $10–30K на legal + audit, 1–2 месяца чистого календарного времени.
- **LLM safety для детей — отдельная инженерная задача.** Один галлюциногенный ответ — и продукт мёртв. Нужны: content moderation layer, pre-tested response patterns, fine-tuned safer модель или rule-based fallback. Это съедает значительную часть пита «настоящего агента» — дети видят сильно guardrailed-thing.
- **Параллельная продуктовая поверхность для родителей** — настройка, мониторинг, контроль времени, прогресс ребёнка. Минимум +30% к скоупу UI.
- **Другие каналы дистрибуции.** Adult AI-dev живёт на X / HN / GitHub. Дети-родители — на TikTok, Instagram, mom-blog'ах, родительских чатах, school PTA, App Store features. Контент-фабрика нужна **другая**, и она у нас на нуле.
- **Skill Schema moat почти не работает.** Restaurant-у с 8-летним пользователем неважно, что у нас открытый стандарт. Часть community-as-standard защиты теряется.
- **Сильнее размывается оригинальный pitch.** «Учись агентам, используя те же тулы, что у взрослого агента» — это уникальный pitch Plan A. С детьми мы скатываемся в «kid-friendly AI-chatbot», где уже есть Khanmigo, Curio, Synthesis.
- **Команда без опыта kid-edu.** Дизайн под детей, gamification, character design, parental UX — отдельные skill'ы. Нужно либо нанимать, либо учиться на ходу.

### 9.3 Acquirer-landscape (по убыванию вероятности)

| Покупатель | Зачем им мы | Шанс |
|---|---|---|
| **Khan Academy / Khanmigo** | Уже партнёр с OpenAI; добавить мобильное приложение + agents formats — стратегически очевидно (но KA — нонпрофит, M&A через дочки) | ⭐⭐⭐⭐ |
| **Duolingo** | Активно растят kids/ABC/Math направление; «Duolingo for AI literacy» им и так в roadmap'е | ⭐⭐⭐⭐⭐ |
| **Apple Education / Google for Education** | Им нужны premium-kids-edu приложения для платформенных features; periodic acqui-hires в этой нише | ⭐⭐⭐⭐ |
| **Scholastic / McGraw-Hill / Pearson / HMH** | Legacy-edu в панике ищут AI-плеи. Большие чеки, но медленнее | ⭐⭐⭐ |
| **Roblox / Minecraft Education** | Educational gaming + AI tutor = стратегический fit | ⭐⭐⭐ |
| **Curio AI / Buddy.ai / Synthesis School** | Прямые конкуренты, могут купить за consolidation | ⭐⭐⭐ |
| **LEGO Group / Mattel** | Legacy-toys ищут digital extensions; LEGO активно в AI-edu | ⭐⭐ |
| **ByteDance (Lark Education)** | Kids-edu activelyно растёт; высокий чек | ⭐⭐⭐ |
| **Disney / Sesame Workshop** | Огромный контент-бренд, медленный pipeline | ⭐⭐ |
| **VK Образование / Яндекс Учебник / Skysmart Junior** | RU-локальный exit, если traction RU-фокусированный | ⭐⭐⭐ |
| **Anthropic / OpenAI** | Если у них появится «kids initiative» — strategic fit; пока спекулятивно | ⭐⭐ |

**Топ-3 для Plan C:** **Duolingo, Apple/Google Edu, Khan Academy.** Хорошая новость — Duolingo пересекается с топ-3 Plan A. Значит, отношения с ними имеет смысл культивировать **прямо сейчас**, независимо от того, какой план победит.

### 9.4 Что переиспользуется, что строится с нуля

**Переиспользуем (большая часть текущей работы выживает):**
- ✅ `DrivenUiEngine` — для детей **более** ценен (визуальные карточки > текст)
- ✅ Tool runner и архитектура — упрощается, но не выбрасывается
- ✅ Multi-provider LLM — критично для cost control
- ✅ Client/server split — структурно тот же
- ✅ Серверная инфра, биллинг, аналитика
- ✅ iOS через KMP — это и так в roadmap'е

**Строится заново:**
- ❌ Весь curriculum (детская методика — другая)
- ❌ Personas → kid-friendly characters (имя, иллюстрация, голос)
- ❌ Content moderation + safety layer
- ❌ Verified parental consent flow
- ❌ Parental dashboard
- ❌ Gamification (бэйджи, стрики, награды)
- ❌ Age-appropriate UI (большие кнопки, анимации, звук)
- ❌ Marketing-фабрика для TikTok/Instagram/родительских каналов

**Оценка перестройки:** 2–3 месяца focused-работы на kids-MVP, при условии что инфра-фундамент остаётся. Плюс $10–30K и 1–2 месяца на регуляторику.

### 9.5 Триггер перехода

Решение принимаем по чек-пойнтам, а не «когда захочется» — иначе утопаем в обоих планах.

| Чек-пойнт | Метрика | Действие |
|---|---|---|
| **Месяц 3** | X followers < 1K, demo-video views < 50K, GitHub stars < 500 | Жёлтый флаг. Усиливаем Plan A, готовим Plan C-skeleton в shadow-режиме (~10% времени) |
| **Месяц 6** | X followers < 2.5K, нет ни одного тёплого M&A-разговора | Триггер: пивот в Plan C официально. Adult-продукт переводится в maintenance-mode, focused-разработка переключается на kids-версию |
| **Месяц 9** | По Plan A: < 5K MAU без traction | Окончательный пивот, adult-продукт закрывается |

После переключения возврат к Plan A не предусмотрен — параллельно вести не получится.

### 9.6 Что **не делаем сейчас**, чтобы не отрезать Plan C

Эти решения нужно принимать с оглядкой на возможный пивот:

- **Не вкладываем в curriculum, который не переиспользуется в детской версии.** Уроки роадмапа должны быть атомарными и серверными — менять контент на детский можно за неделю, если они правильно структурированы.
- **Архитектурно tool runner и `DrivenUiEngine` не специализируем** под adult-tooling. Calendar/SMS/Email-тулы — adult-only; держим их как plug-in, не как core. Для детской версии те же hooks должны принимать другие тулы (творческие, игровые, обучающие).
- **Сервер пишем мульти-tenant с самого начала** — не «production curriculum», а «namespace + curriculum в namespace». Тогда детский продукт = новый namespace, не новый сервер.
- **Не нанимаем под adult-only специализацию** — пока не пробит чек-пойнт месяца 6.
- **Domain'ы / бренды.** Если регистрируем доменное имя — не привязываем жёстко к «AI agents for developers». Лучше нейтральное «agent-anything» или «pocket-X», под которое можно подсунуть любой curriculum.

### 9.7 Что **делаем уже сейчас** в shadow-режиме (≤ 5% времени)

- **Tail-tail observation детского AI-edu рынка** — что покупают Khanmigo / Buddy.ai / Curio, сколько привлекают, где их weakness.
- **Один разговор с человеком, который вёл детский edu-продукт.** Час времени — собрать «что бы вы хотели знать заранее».
- **Юр. preview по COPPA/GDPR-K** — сколько реально стоит, какие сроки. Не нанимать юриста, просто оценить порядок.
- **Сохранить domain'ы под детскую версию** заранее (дёшево, страховка).

### 9.8 Резюме плана C

Сильная стратегическая опция с другим **acquirer-set**'ом, частичной reuse-инфры и **жёсткой регуляторикой**. Решение: **держим архитектуру совместимой**, **не вкладываем активно сейчас**, **пивотируем по триггеру месяца 6**, если Plan A не выходит на нужный темп. Главный пересекающийся пункт между Plan A и Plan C — **Duolingo**, поэтому отношения с ними имеют смысл начинать в любом случае.

## 10. Один абзац, к которому возвращаемся при каждом решении

> Мы строим **самый узнаваемый «карманный учитель по AI-агентам»** на глобальном рынке за 9–12 месяцев. Каждая фича, каждый пост, каждое видео — это либо узнаваемость, либо отличающая IP, либо ничто. Если решение не помогает первым двум — его нет в roadmap. Покупатель смотрит на: график роста DAU, distinctive tech, узнаваемое имя в нише, маленькую команду. Мы оптимизируем эти четыре переменные, всё остальное — подчинено им.
