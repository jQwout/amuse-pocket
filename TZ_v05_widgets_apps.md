# ТЗ v0.5: Driven UI v1 — предзаполненные виджеты + апы-композиции

> **Версия:** 0.5 · **Дата:** 2026-06-15 · **Статус:** согласовано, pre-implementation
> Пивот после парковки DivKit. Заменяет направление [TZ_v04_DivKit.md](TZ_v04_DivKit.md) (⏸️ отложено до v2).

---

## 1. TL;DR

Никакого DivKit и никакого сервера в v1. Driven UI собирается **целиком на клиенте** из того, что уже есть:

- **Виджеты** — существующие шаблоны `render_card` → `DrivenUiEngine` (todo, weather, timer, table, chart_bar, form, choice, lesson_complete). Без изменений.
- **Апы** — **предзаполненные композиции этих виджетов**: несколько виджетов как одна карточка-экран в чате. Апы авторятся руками (JSON в assets), LLM их только **выбирает**, а не сочиняет.

Граница возможностей задаётся форматом: виджеты ограничивают вид, фиксированный каталог апов — набор. «Сделай CRM» не появится — модель выберет ближайший готовый ап или соберёт ответ из виджетов.

| Решение | Почему |
|---|---|
| Только клиент, без сервера | v1-скоуп: быстрый выход, нет инфраструктуры, нет ключей вне устройства |
| Переиспользуем `DrivenUiEngine` | Виджеты уже написаны и рендерятся; добавляем только контейнер |
| Ап = контейнер из виджетов (`AppCard`) | Один ап = один `cardSpec` → текущее хранение в Room работает без изменений |
| Апы — предзаполненный каталог, не свободная LLM-композиция | Безопасность и предсказуемость: LLM выбирает `app_id` из enum, недоверенного layout-JSON в рендере нет |
| DivKit/сервер/свободная композиция | Отложено в v2 ([TZ_v04_DivKit.md](TZ_v04_DivKit.md)) |

## 2. Архитектура

```
┌─────────── КЛИЕНТ (Android, существующий код) ───────────┐
│ ChatScreen → агентский ReAct-цикл (как сейчас)            │
│   ↓ tool_call: render_card(template, params)  ← виджеты   │
│   ↓ tool_call: open_app(app_id)               ← апы (new) │
│ ToolResult.Success(json)  →  MessageEntity.cardSpec       │
│ MessageBubble → RenderDrivenUiCard(spec)                  │
│   DrivenUiEngine.parseJsonString → DrivenUiCard           │
│     • виджет  → существующая *CardView                    │
│     • "app"   → AppCard → Column из дочерних *CardView     │
│ Ошибка парсинга → toMarkdown() fallback                   │
└───────────────────────────────────────────────────────────┘
```

Новое в v1: тип `AppCard` в `DrivenUiEngine`, тул `open_app`, папка `assets/apps/`. Всё остальное — существующее.

## 3. Формат апа (композиция)

Ап — обычная `render_card`-спека с новым `template: "app"`, где `params.blocks` — массив **существующих** виджетов в формате `{template, params}`.

```json
{
  "template": "app",
  "params": {
    "title": "Мой день",
    "blocks": [
      { "template": "todo_list",  "params": { "title": "Задачи", "items": [...] } },
      { "template": "chart_bar",  "params": { "title": "Часы за неделю", "labels": [...], "values": [...] } },
      { "template": "choice",     "params": { "question": "Как прошёл день?", "options": ["Огонь","Норм","Так себе"] } }
    ]
  }
}
```

Правила:
- `blocks[]` содержит только **уже существующие** типы виджетов; новый виджет = сначала в `DrivenUiEngine`, потом в апы.
- Вложенность ровно 1 уровень: `app` не может содержать `app`.
- `blocks` ≤ 8 (квота против простыни).
- Рендер: `Column` с вертикальным спейсингом, дочерние виджеты — те же `*CardView`, что в чате.

## 4. Каталог предзаполненных апов

- Каждый ап — файл `app/src/main/assets/apps/<app_id>.json`, содержащий объект `params` (`title` + `blocks`).
- Апы пишутся **руками** (вручную авторишь композицию из виджетов). LLM их не генерирует.
- Полный каталог апов и их архетипы — в §12. Базовый v1-набор (чистые композиции): `reminders` (напоминалки), `notes` (заметки), `todo` (туду-листы), `recipes` (рецепты = спец-заметки).
- Эволюция: новый ап добавляется одним JSON-файлом + строкой в enum тула. Без релиза логики.

## 5. Тул `open_app`

```jsonc
{
  "name": "open_app",
  "description": "Открывает готовый мини-ап (композицию виджетов). Доступные: reminders, notes, todo, recipes.",
  "parameters": {
    "type": "object",
    "properties": {
      "app_id": { "type": "string", "enum": ["reminders", "notes", "todo", "recipes"] }
    },
    "required": ["app_id"]
  }
}
```

- Реализация (как `RenderCardTool`): `@Inject @SingleIn(AppScope::class) class OpenAppTool : Tool`, регистрация в том же DI-модуле (Metro multibinding в `ToolRegistry`).
- `execute`: грузит `assets/apps/<app_id>.json`, оборачивает в `{"template":"app","params": <file>}`, возвращает `ToolResult.Success(json)`.
- Невалидный `app_id` отсекается enum'ом на стороне LLM; на клиенте — `ToolResult.Error` с веткой-заглушкой.
- Результат попадает в `cardSpec` тем же путём, что `render_card` (`ChatViewModel` фильтрует tool-trace).

> **Открытый вопрос (см. §9):** разрешить ли LLM *собирать* `app` из виджетов на лету (свободная композиция) в дополнение к каталогу. Движок это умеет бесплатно (тот же код); в v1 по умолчанию **только каталог** — это и есть «предзаполненность».

## 7. Интерактив и round-trip

Сейчас замыкается только `onChoiceSelected → sendUserMessage`; `onFormSubmitted` в [ChatScreen.kt](app/src/main/java/com/example/ui/chat/ChatScreen.kt) — no-op, интерактив включён только в уроках (`isTutorial`).

Для v1-апов:
- Локальное состояние (чекбоксы, таймер, выбор) — как сейчас, в `remember`, без round-trip.
- **Дотянуть `onFormSubmitted`** → отправлять результат формы агенту (`sendUserMessage` с JSON полей). Обязательно, если апы содержат `form`.
- **Решить gating:** включать ли интерактивные виджеты в апах вне уроков (снять привязку к `isTutorial` для апов). По умолчанию — да, иначе апы вне уроков мертвы.
- Персистентные действия (запись «принял таблетку» в БД, напоминания) — **не в v1**. Это словарь экшенов из v2/DivKit. В v1 апы — отображение + лёгкий локальный интерактив + round-trip через чат.

## 8. Квоты и безопасность

- `app_id` — только из фиксированного enum; свободного layout от LLM в рендере нет.
- `blocks` ≤ 8, вложенность = 1, только существующие типы виджетов.
- Любая ошибка парсинга/неизвестный тип → `toMarkdown()` fallback, никогда пустой бабл.
- Никаких сетевых вызовов и недоверенного JSON — всё из локальных assets и валидированного формата.

## 9. Стейджи

### Stage A — Контейнер · 0.5–1 день
`AppCard` в `DrivenUiEngine` (parse + render Column) + `AppCard.toMarkdown()` + unit-тест (`DrivenUiEngineTest`). Захардкоженная app-спека рендерится в чате.
**Done when:** руками поданная `{"template":"app",...}` показывает несколько виджетов в одном бабле; битый блок → markdown-fallback.

### Stage B — Тул + каталог · ~1 день
`OpenAppTool` + регистрация в DI, папка `assets/apps/` с 2 апами, enum `app_id`, описание в `system_base.md`.
**Done when:** «открой план дня» → `open_app(day_plan)` → ап из assets рендерится в чате.

### Stage C — Интеграция · 0.5 дня
`open_app` в извлечении cardSpec (`ChatViewModel`), проверка персистентности (ап переживает рестарт через `MessageEntity.cardSpec`).
**Done when:** ап на месте после перезапуска приложения.

### Stage D — Интерактив · 0.5 дня
Подключить `onFormSubmitted` → агент; снять `isTutorial`-gating для апов (или осознанно оставить).
**Done when:** сабмит формы в апе доходит до агента и тот реагирует.

### Stage E — Полировка · 0.5 дня
Edge cases: пустой ап, длинные списки, спецсимволы; тесты на парсер и тул.

**Итого: ~3–3.5 дня.**

## 10. Что осознанно НЕ делаем (v1)

- DivKit, свой сервер, серверная генерация UI — это v2 ([TZ_v04_DivKit.md](TZ_v04_DivKit.md)).
- Свободная композиция апа от LLM — по умолчанию off (только каталог); движок готов, флип — в v1.1.
- Персистентные действия / словарь экшенов / таблица `records` — v2.
- Мультиэкранность, навигация между апами, подстановка данных в плейсхолдеры (`{$var}`) — v1.1+.
- Новые типы виджетов «на всякий случай» — только по реальному спросу.

## 12. Каталог мини-апов (видение, 2026-06-15)

Полный список от пользователя. Ключевое: это **три разных архетипа**, и только Архетип 1 — это «композиция виджетов» из данного ТЗ. Остальные требуют отдельных механизмов и идут позже / отдельным треком.

### Архетип 1 — Композиции виджетов (механизм этого ТЗ, v1-ready)

| Ап | Из чего | Зависимости |
|---|---|---|
| Напоминалки | form(текст,время) + choice(повтор) → `schedule_task` | работает сейчас |
| Заметки | form(текст) + list/table; хранение в files/memory | files/memory tool |
| Туду-листы | todo_list + form(добавить); хранение | memory/db |
| Рецепты | = структурированные заметки (table ингредиенты + todo шаги) | как заметки |

Иерархия: базовые — **напоминалки, заметки, туду**. Рецепты — специализация заметок. Лекарства — специализация напоминалок, но с трекингом → уходит в Архетип 2.

### Архетип 2 — Stateful: нужен стор данных или сенсор (v1.5–v2)

| Ап | Что нужно сверх композиции |
|---|---|
| Бюджет | накопительный стор расходов + категории (возможно виджет-метрика); есть skill budget |
| Карточки запоминания | колода + spaced repetition + виджет «переворот карточки» (нет) |
| Прием лекарств | периодические напоминания + лог приёма (принял/пропустил) |
| Шагомер | сенсор шагов (SensorManager / Health Connect) + ACTIVITY_RECOGNITION — нативная механика, не карточки. Самый большой прыжок. |

### Архетип 3 — Чат-проекты: scoped разговор + план + память (как Project в Claude; НЕ карточки)

| Ап | Что это |
|---|---|
| Тренер иностранного (EN/DE) | выделенный чат + tutor-персона + план обучения в памяти |
| АИ тренер | туду + заметки + чат-коучинг |

Механизм уже есть в зачатке: conversations + personas + memory + `PrePromptAssembler` (инжект контекста) + паттерн уроков роадмапа (чат с впрыснутым сценарием). Чат-проект = разговор, посеянный персоной + персистентным планом/памятью, scoped к теме. Дёшево и сильно дифференцирует — но это **другая фича**, чем апы-карточки.

### Рекомендованный срез и порядок

- **v1 (композиции):** напоминалки + заметки + туду (+ рецепты почти бесплатно).
- **v1 пилот Архетипа 3:** языковой тренер — проверяет паттерн чат-проекта на существующей инфре, без системы композиций.
- **Отложить:** бюджет, флешкарты, лекарства (нужен стор/лог), **шагомер** (сенсор — дальше всех), аи-тренер (после языкового).
