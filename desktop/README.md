# Десктопный клиент генерации медиа (OpenRouter)

Генерация картинок через OpenRouter — одним ключом, из одного окна.

**Что умеет ядро и чего нет в интерфейсе.** `:core-genai` работает со всеми тремя модальностями —
картинки, видео, озвучка, — и они покрыты тестами. Но экран генерации сейчас **только про
картинки**: переключатель модальности из него убран по решению пользователя (см. KDoc `MODALITY`
в `GenerateScreen`). **Ни видео, ни озвучку из интерфейса запустить нельзя вообще** — последний вход
в видео, кнопка «сделать видео» на карточке результата, убран вместе с остальными иконками ряда.
Ядро обе модальности умеет и покрыто по ним тестами; это осознанный срез интерфейса, а не потеря
возможностей ядра, но нажать сейчас негде.
Фаза 0–1 плана из [`desktop_genai_plan.md`](../desktop_genai_plan.md).

## Запуск

    ./gradlew -p desktop :app-desktop:run

Чтобы запускать без Gradle — самостоятельный образ с вшитой JVM, тот самый `.exe` под ярлык:

    ./gradlew -p desktop :app-desktop:createDistributable

Готовый образ: `app-desktop/dist/main/app/AiOpenPocket/AiOpenPocket.exe`.
Ярлык запускает **собранный образ, а не текущий код** — после правок в исходниках образ надо
пересобрать той же командой, иначе откроется прошлая версия.

Образ лежит в `dist/`, а не в `build/`, по двум причинам, обе выяснились на практике: `clean`
сносил цель ярлыка, а запущенное приложение держало каталог образа своим рабочим, и следующая
сборка падала на «Unable to delete directory» — блокировка переживала даже закрытие окна. По той же
причине у ярлыка рабочий каталог домашний, а не папка образа. Перед пересборкой приложение всё
равно лучше закрыть: Windows не даёт перезаписать jar-ы работающего процесса.

Образ, а не MSI-установщик (`packageMsi`), сознательно: тот требует WiX, которого на машине может
не быть вовсе, и ставит приложение в систему — а нужен запуск, не дистрибуция.

Ключ OpenRouter вводится в приложении (экран «Настройки»), а не через переменные окружения.
Там же кнопка **«Проверить связь»** — дёргает `GET /api/v1/key` и показывает, принят ли ключ,
сколько потрачено и какой лимит. Стоит нажать до первой генерации: иначе про сломанный ключ
или закрытую сеть узнаёшь из непонятного отказа на платном запросе.

Тесты ядра (без сети, транспорт подменён MockEngine):

    ./gradlew -p desktop :core-genai:test

## Модули

| Модуль | Что внутри |
|--------|-----------|
| `:core-genai` | Всё, что не про UI: клиент OpenRouter на три модальности, очередь заданий, каталог моделей, хранение ключа/истории/файлов. Ktor + kotlinx.serialization, никакого Compose. |
| `:app-desktop` | Compose Desktop: три экрана (Генерация / История / Настройки), ручная сборка графа в `AppContainer`. |

`:core-genai` намеренно не знает про Compose, а `:app-desktop` — про Ktor: движок собирается
в `GenaiRuntime` внутри ядра. Это та граница, по которой модуль поедет в общий KMP-код в фазе 4.

**Ядро держится в рамках Android API 24.** Никакого `java.nio.file`, `java.util.Base64`,
`java.time` — только `java.io.File` и `kotlin.io.encoding.Base64`. Причина не в удобстве:
`java.nio.file` на Android 7.x даёт `NoClassDefFoundError`, а это `Error`, а не `Exception` —
он проходит мимо любых `catch (e: Exception)` и роняет процесс. В `:app` на этом уже обожглись
(`OpenRouterCatalogCache`), так что общее ядро писалось сразу без этих API.
Стережёт `AndroidApiLevelTest`: он читает исходники и падает, если запрещённое вернётся.

## Почему это отдельная Gradle-сборка

Так же, как `tools/lesson-viewer`: корневая сборка — Android и требует SDK, десктопу он не нужен.
Модули переедут в корневой `settings.gradle.kts` в фазе 4, когда общий код начнёт делиться с `:app`.
Побочный эффект: Android Studio эту сборку не индексирует, открывать её надо отдельным проектом.

## Как устроена генерация

Одна очередь на все три модальности — `GenerationQueue`. Разница только в протоколе провайдера:

| Модальность | Эндпоинт | Как приходит результат |
|-------------|----------|------------------------|
| Картинка | `POST /api/v1/images` | синхронно, base64 в `data[].b64_json` |
| Видео | `POST /videos` → `polling_url` | асинхронно: опрос до `status:"completed"`, затем ссылки в `unsigned_urls` |
| Аудио | `POST /audio/speech` | синхронно, сырой mp3 в теле ответа |

Параллельность ограничена (по умолчанию два задания разом), но пропуск держится только пока
работаем мы. Как только провайдер взял задание себе и остаётся лишь опрашивать его — слот
отпускается: иначе два видео на пятнадцать минут заперли бы очередь, и ни одна картинка не
сгенерировалась бы. У ожидающих заданий свой предел (8): без него полсотни видео дают десяток
запросов в секунду и упираются в rate-limit ключа.

Входная картинка едет по системе **путём**, а в base64 разворачивается только перед самим
запросом, на IO-диспетчере. Иначе картинка на 6 МБ превратилась бы в 8 МБ base64 внутри задания —
и переписывалась бы вместе со всей историей на каждом переходе статуса.

История подрезается до 500 записей: файл читается и переписывается целиком, расти без предела он
не может. Выбрасываются только самые старые завершённые задания — незавершённые никогда, среди
них может быть видео, которое ещё предстоит догнать. Файлы результатов при этом остаются на
диске: удалять чужие картинки за спиной приложение не вправе.

Статус задания пишется на диск (`~/.local/share/aiopenpocket/jobs.json`) на **каждом** переходе —
по тому же принципу, что фоновый ход агента в `:app`. Поэтому закрытое окно не уносит с собой
уже оплаченное видео-задание: при следующем запуске `resumeUnfinished()` продолжает опрос по
сохранённому `polling_url`. Прерванные синхронные задания помечаются упавшими и **не**
перезапускаются сами — повторный запрос стоит денег второй раз, это решение пользователя.

По той же причине **исчерпанный опрос — не отказ**. Когда 180 попыток (≈15 минут) заканчиваются,
задание остаётся в `POLLING`, а не падает: видео уже оплачено, ссылка на него сохранена, и опрос
по ней бесплатен. Терминальный статус здесь означал бы ровно обратное тому, что нужно, —
`resumeUnfinished()` пропускает терминальные задания, так что подхватить результат стало бы нечем,
а единственной кнопкой осталась бы «Повторить», то есть заплатить второй раз за то же самое.
Надоело ждать — есть «Отменить», и это выбор пользователя.

## Файлы на диске

| Что | Где |
|-----|-----|
| Результаты | `~/AiOpenPocket/generations/<id>/` |
| Ключ | `~/.config/aiopenpocket/openrouter.key` (права 600 — **только на POSIX**, см. ниже) |
| История заданий | `~/.local/share/aiopenpocket/jobs.json` |
| Свой список моделей | `~/.config/aiopenpocket/genai-models.json` (**перекрывает** встроенный) |
| Кеш живого каталога | `~/.local/share/aiopenpocket/genai-models-cache.json` |
| Примеры картинок у моделей | `~/.local/share/aiopenpocket/model-previews/` (кеш **навсегда**, удалять безопасно) |
| Свои заготовки промптов | `~/.config/aiopenpocket/genai-prompts.json` (**дополняет** встроенные) |
| Избранные модели | `~/.config/aiopenpocket/genai-favorites.json` |
| Избранные заготовки | `~/.config/aiopenpocket/genai-prompt-favorites.json` |
| Сколько раз вставляли заготовку | `~/.local/share/aiopenpocket/genai-prompt-usage.json` |
| Настройки (журнал запросов) | `~/.config/aiopenpocket/genai-settings.json` |

XDG-переменные учитываются, если заданы. На Windows каталоги те же самые (`%USERPROFILE%\.config\…`),
по-виндовому в `%APPDATA%` ключ не переезжает — так путь совпадает с тем, что печатает экран настроек.

**Про «права 600» на Windows.** Их там нет. У NTFS нет POSIX-прав вовсе
(`supportedFileAttributeViews` = owner/dos/acl/basic/user), и `File.setReadable(false, false)`
возвращает `false`, ничего не изменив, — то есть шаг «снять чтение у всех» молча не срабатывает.
Ключ на Windows защищён ровно настолько, насколько защищён профиль пользователя: от других учёток —
да, от администратора и SYSTEM — нет. `ApiKeyStore.write` возвращает признак того, удалось ли сузить
права, чтобы вызывающий мог об этом сказать вслух, а не делать вид, что «600» есть везде.

Разница между двумя последними намеренная: список моделей пользователь ведёт целиком под себя,
а встроенные заготовки промптов — примеры формулировок, и терять их при сохранении первого
своего промпта незачем. Совпадение по `id` в обоих случаях выигрывает у пользователя.

## Каталог моделей: живой список, а не вшитый файл

Раньше здесь был статический JSON, и этот README сам признавал, что слаги устаревают быстрее, чем
правится файл. Теперь список берётся с `GET /api/v1/models` и кешируется на сутки — тот же приём,
что у `OpenRouterCatalogService` в `:app`, включая различение «список провайдера» и «встроенные
подсказки»: по неавторитетному списку нельзя заключить, что модель снята с обслуживания.

Отличие от `:app` предметное: там модели отбираются по `tools`, здесь — по **выходной** модальности,
потому что генератору важно, что модель отдаёт. Чат-модели в каталог генерации не попадают вовсе.

**Картинки генерируются своей ручкой `POST /api/v1/images`, а не через чат.** Через
`chat/completions` картинку получить можно, но в тот запрос некуда положить разрешение, соотношение
сторон и формат файла — таких полей у чата нет. А модели их заявляют, и пользователь их просит.
Вдобавок каталог картиночных моделей — это `/api/v1/images/models`, и через чат из сорока моделей
отвечает меньшинство: выбранная в списке `qwen/qwen-image-3-pro` уходила бы в ручку, которая её не
знает. Побочная выгода — вложения теперь уходят настоящим полем `input_references`.

**Ручек три, и это не педантизм.** Картинки берутся из `/api/v1/images/models`, видео — из
`/api/v1/videos/models`, и только аудио из общего `/api/v1/models`. Причина в полноте: в общем
списке картиночных моделей одиннадцать, а в их собственном каталоге — **сорок** (проверено
2026-08-05). Qwen Image, Krea, MAI-Image, GPT Image в общий список не попадают вовсе, и пока каталог
собирался только из него, пользователь видел четверть доступного, не имея повода это заподозрить.

Порядок сборки списка — сверху вниз:

1. **Свой `genai-models.json`** — прямое указание пользователя. Живой список его не отменяет:
   OpenRouter перечисляет в `/models` не всё, что готов обслужить.
2. **Живой список** (сеть → кеш).
3. **Встроенные подсказки** — только для модальностей, которых не закрыл никто выше.

Пункт 3 — не перестраховка. Живой `/api/v1/models` проверен 2026-08-04: он отдаёт 11 картиночных
моделей, 4 аудио и **ни одной видео** — видео у OpenRouter живёт за отдельным `POST /videos`. Без
отката на встроенный список «обновили каталог» означало бы «потеряли выбор видео-моделей целиком».

Оттуда же второй урок: `openrouter/auto` и `openrouter/auto-beta` — маршрутизаторы, а не генераторы,
и по дате появления они всплывают в самый верх, то есть становятся моделью по умолчанию. Какая
модель и по какой цене отработает, при этом заранее неизвестно, поэтому вендор `openrouter/`
из живого списка отсеивается. Если пользователь вписал такую модель себе в файл сам — остаётся:
это осознанный выбор.

## Пачки: варианты одного промпта

**Вариантов ×N** — N заданий с одним промптом. Модели генеративны, разброс между прогонами — часть
работы: проще отобрать из четырёх, чем жать «Повторить» и терять предыдущие.

Режим «Сравнить модели» (один промпт в несколько моделей сразу) из интерфейса убран. В очереди он
жив и под тестами — `GenerationQueue.submitAcrossModels`, — но кнопки для него больше нет, и старые
пачки такого вида по-прежнему корректно показываются в истории.

Заготовка с плейсхолдером `{основной промпт}` — это приписка: она оборачивает набранный текст,
а не затирает его. Без плейсхолдера заготовка самостоятельная и промпт заменяет.

И то и другое проставляет заданиям общий `batchId`, и в истории пачка показывается одной
карточкой с результатами рядом. Пачка из одного задания batchId не получает — иначе история
группировала бы одиночные генерации.

## Витрина: примеры картинок у моделей

В списке выбора модели рядом с каждой строкой — пример того, что она рисует. Это единственное место
в приложении, которое ходит **не в API, а в вёрстку сайта**: в `/api/v1/models` картинок нет вовсе,
`links` содержит только служебный `/endpoints`, а адрес примера из полей ответа не собрать — в пути
стоит uuid, которого в API нет ни в каком виде. Он есть только в HTML страницы модели.

Раз это разбор чужой разметки, он написан так, чтобы ломаться тихо и предсказуемо:

- поиск идёт по хосту хранилища (`model-assets.openrouter.ai`), а не по классам и структуре —
  имена классов генерируются сборщиком сайта и меняются каждый релиз;
- в пути ассета обязан быть слаг самой модели, иначе пример не берётся: на странице однажды
  появится блок «похожие модели», и без этой проверки в кеш лёг бы чужой пример **навсегда**;
- кеш вечный, но одноразовый: не открылось — показывается полосатая заглушка, приложение не падает
  и адрес не угадывает;
- к сайту относимся вежливо: не больше трёх параллельных запросов, повторные обращения за одной
  моделью схлопываются в один, `User-Agent` называет приложение по имени.

Сломается вёрстка — упадёт тест `ModelPreviewsTest`, а не пользователь, увидевший пустые карточки.

## Про деньги

Сводка расходов считается только по успешным заданиям и показывает, **по скольким заданиям
стоимость неизвестна**. Не каждый ответ несёт `usage.cost` — у озвучки его нет вовсе, в теле
сырой mp3. Поэтому «потрачено» — нижняя оценка, и приложение говорит об этом прямо, а не выдаёт
неполную сумму за полную.

## Что проверено, а что нет

Ядро покрыто тестами: все три протокола, поллинг видео, отказы (401/402/429, пустой ответ,
пустой ключ), очередь, догон после перезапуска, пачки и сравнение моделей, слияние библиотеки
промптов, подсчёт расходов, проверка ключа, права на файл ключа, запись артефактов,
каталог моделей (встроенный и живой), входная картинка, фильтр входных файлов, оценка расхода перед
запуском, совместимость с API 24 — **148 тестов**, транспорт подменён MockEngine.

На Windows их 146 + 2 пропуска: обе проверки прав на файле ключа требуют POSIX-прав, которых у NTFS
нет. Пропуск объявлен явной причиной, а не замаскирован ослабленным утверждением, — на Linux/macOS
эти два теста работают в полную силу.

`GenerationQueueConcurrencyTest` — единственный, который гоняет очередь на настоящих потоках
(300 заданий, 16 параллельно). Остальные однопоточные и гонку в состоянии очереди увидеть не
могут в принципе.

Про силу этих тестов честно, потому что «есть тест» и «тест что-то ловит» — разные вещи:

| Тест | Что доказано |
|------|--------------|
| потеря обновлений статуса | ловит: до исправления падал 3 прогона из 3 |
| поздний результат поверх отменённого задания | ловит: до исправления падал 3 прогона из 3 |
| тип картинки по ссылке (`image/jpeg`, не `png`) | ловит: до исправления падал |
| ожидание провайдера не запирает очередь | ловит: до исправления падал |
| `..` в id задания не уводит запись из папки результатов | ловит: до исправления падал |
| в историю не утекает base64 входной картинки | ловит: до исправления падал |
| битый свой файл моделей не роняет каталог до трёх моделей | ловит: до исправления падал |
| история подрезается, но незавершённые задания не выбрасываются | ловит: до исправления падал |
| в ядро вернулся API 26 (`java.nio.file`, `java.util.Base64`) | ловит: проверено на обоих семействах |
| исчерпанный опрос не хоронит оплаченное видео | ловит: до исправления падал |
| ключ не уходит на чужой хост за результатом | ловит: до исправления падал |
| два параллельных обновления каталога не сносят кеш | ловит: до исправления падал 3 прогона из 3 |
| откат из терминального статуса через `cancel()` | **не ловит** ту гонку — между чтением и записью были два соседних оператора, попасть в окно извне нечем. Стоит как страж инварианта |
| права на файле ключа | проверяет итоговое состояние, а не окно между созданием и `chmod` — окно не тестируется в принципе |

**Что проверено на живом API, а что нет.**

Проверено по-настоящему: **каталоги моделей** (2026-08-05) — они публичные, ключа не требуют и денег
не стоят. Оттуда взялись правки, которых по документации было не увидеть: в общем `/api/v1/models`
нет ни одной видео-модели и всего 11 картиночных, зато `openrouter/auto*` всплывают в самый верх по
дате; у картинок и видео есть свои каталоги на 40 и 21 модель, и `supported_parameters` в них —
