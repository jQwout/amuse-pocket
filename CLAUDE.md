## Traceability (traxer)

Репо использует traxer: `traceability.yaml` + маркеры `@trace <id>` в коде (см. скилл `trace`).

Перед коммитом — даже если работаешь по процессу superpowers (verification-before-completion, finishing-a-development-branch):

1. Прогони `traxer check` и разгреби, что он покажет (broken link / фича без кода / stale).
2. Новая фича → `traxer id`, запись в `traceability.yaml` (id, title, rationale = ПОЧЕМУ), маркер `@trace <id>` в коде.
3. В коммит — трейлер `Trace: <id>`.
4. Stale-warnings blessить (`traxer bless <id>`) только после подтверждения, что rationale ещё верен.

## Графовая память репозитория (codebase-memory-mcp)

Код ищи через граф, а не перебором файлов: MCP-сервер `codebase-memory-mcp` держит символы, вызовы и импорты репозитория. `search_graph` — символы по шаблону, `trace_path` — кто зовёт функцию и кого зовёт она, `get_code_snippet` — исходник по узлу, `get_architecture` — модули; Grep и `search_code` — для литералов и там, где граф не покрывает. Спроси граф первым, файлы читай уже по его ответу.

Две вещи ломают ожидания. Вотчер и автоиндекс выключены нарочно, поэтому граф отвечает по прошлому индексу: своих свежих правок и новых символов ветки в нём нет, пересобирать руками. И любой ручной вызов требует `CBM_WORKERS=1` — иначе индексация падает на Windows (в `.mcp.json` переменная уже стоит). Что как настроено и команда переиндексации — `docs/codebase-memory-mcp-plan.md`.

## Оркестратор

Агент-руководитель ведёт проект к критериям владельца: делит работу на задачи по 1–3 часа, раздаёт их субагентам в отдельных worktree, проверяет результат, сливает в `mvp`, ведёт журнал и приносит владельцу вехи и вопросы с рекомендацией. Перенесён из `xrchief` 27 окт 2026 по его `orchestrator/PORTING.md`.

- **Цикл** — навык `.claude/skills/orchestrate/SKILL.md`. Один цикл: `/orchestrate`. Непрерывно: `/loop Выполни один цикл навыка orchestrate` (слэш-команду внутрь `/loop` приложение не пускает, поэтому обычным текстом).
- **Субагенты** — `.claude/agents/`: `implementer` (одна задача в своём worktree), `verifier` (придирчивая проверка ветки), `researcher` (факты об API с источниками), `device-tester` (эмулятор; телефон владельца — только по его «да»).
- **Вход владельца** — `orchestrator/CRITERIA.md` (что значит «готово») и `orchestrator/AUTONOMY.md` (что можно без спроса). Менять их может только владелец. Ход работы — `orchestrator/ROADMAP.md` и `orchestrator/JOURNAL.md`; сценарии живой проверки — `orchestrator/DEVICE_CHECKLIST.md`.
- **Дисциплина правки** — навык `.claude/skills/craft/SKILL.md` (`/craft`): три фазы (сначала заработало, потом правильно, потом практика) и гейты, которые в этом репозитории правда запускаются. Переложен с правил `ub-mode` Роберта Мартина: его `crapper`/`dryer`/`mutator` Kotlin не читают, их место заняли мутация руками и поиск дублей по графу.
- **Одна команда проверки** — `python tools/check.py` (`--fast` — с компиляцией, `--full` — со сборкой, тестами и сканом APK). Её зовут все: исполнитель перед коммитом, проверяющий, оркестратор после слияния. ID в выводе совпадают с ID в `CRITERIA.md`, код выхода не 0 при FAIL. Новую проверку обязательно проверь, временно сломав то, что она стережёт: проверка, которая не может упасть, хуже отсутствующей. Исходник скрипта — только ASCII (кириллица через `\uXXXX`): консоль на машине владельца в cp1251.
- Доказательства (скриншоты, логи) складываются в `orchestrator/evidence/` и **не** попадают в git — репозиторий станет публичным, и мегабайты картинок в истории ему не нужны; в отчёт вехи они идут файлами артефакта.
