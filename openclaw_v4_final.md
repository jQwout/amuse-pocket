# OpenClaw: Практическое руководство — от первой заметки до автоматизации дня

---

## Введение: твой AI-агент, который живёт в телефоне

OpenClaw — это не чат-бот в облаке. Это не очередной голосовой помощник, который шлёт данные на чужие серверы и требует ежемесячную подписку. Это локальный AI-агент, который работает прямо на твоём Android-телефоне. Все данные — заметки, таблицы, финансы, тренировки, семантические embeddings — хранятся исключительно в памяти устройства. Никаких подписок, никакой слежки, никаких утечек. Только ты и твой агент. Всё работает offline там, где это возможно: файлы, база данных, напоминания, семантический поиск по сохранённым фактам.

Приложение подключается к провайдерам языковых моделей через API-ключи. У тебя три варианта: **NVIDIA NIM** (основной, рекомендуется для лучшего качества), **Groq** (запасной, молниеносная скорость ответа), **GitHub Models** (резервный, бесплатный тир с лимитами). Настройка занимает минуту — открываешь настройки приложения, вставляешь API-ключ в соответствующее поле, выбираешь модель из списка, готово. Если один провайдер временно недоступен или лимит исчерпан, агент автоматически переключается на следующий по цепочке. Ты это даже не заметишь — в tool trace будет короткая запись `[fallback] NIM → Groq`, и диалог продолжится без прерывания.

**Что умеет OpenClaw?** Пишет и читает файлы — ты получаешь полноценную файловую систему внутри приложения. Шлёт уведомления через системный трей Android. Ставит напоминания по расписанию с точностью до минуты (с поправкой на doze mode). Работает с базой данных SQLite — создаёт таблицы, вставляет данные, выполняет сложные SELECT-запросы с группировкой, JOIN, агрегатными функциями. Ищет в интернете и загружает страницы. Сохраняет факты в долговременную семантическую память с векторным поиском. Находит нужное по смыслу, а не только по точным словам. Показывает интерактивные карточки — списки дел с чекбоксами, погоду, таблицы данных, формы ввода, столбчатые графики. И делает всё это под твоим полным контролем: ты видишь каждый вызов инструмента в чате — это называется **tool trace**, и это фича, а не баг.

**Семь персон.** Агент умеет разговаривать в семи разных стилях, и каждый стиль — это не просто "привет" vs "здравствуй", а полностью разная манера общения: длина ответов, использование эмодзи, степень инициативы, тон — всё меняется. По умолчанию он — **Резкий напарник** (`sharp_partner`): деловой, краткий, без воды, без вступлений вроде "как я могу помочь". Но можешь переключить на кого угодно:

| Персона | ID | Стиль | Когда использовать |
|---------|-----|-------|-------------------|
| Тихий дворецкий | `silent_butler` | Сухой, минимальный. Только факты, никаких обращений. | Когда нужна точность и краткость. Быстрые факты без обёртки. |
| Внимательный секретарь | `attentive_secretary` | Вежливый, всегда уточняет детали. | Для сложных задач, где одна неточность дорого стоит. Переспросит, чтобы не ошибиться. |
| Резкий напарник | `sharp_partner` | Default. Деловой, краткий, по делу. | Быстрые задачи, когда не нужна обёртка. Сразу действие. |
| Партнёр-эгалитарист | `egalitarian_partner` | Ровный, советует, не командует. | Совместное планирование, обсуждение вариантов. "Давай подумаем" вместо "Сделай так". |
| Дружелюбный компаньон | `friendly_companion` | Тёплый, с эмодзи, поддерживает. | Когда нужна поддержка, мягкость. Празднует победы вместе с тобой. |
| Ироничный ассистент | `ironic_assistant` | Саркастичный, умный, подтрунивает. | Для лёгких задач и поднятия настроения. Превращает рутину в игру. |
| Строгий коуч | `strict_coach` | Прямой, мотивирует, требует результата. | Спорт, цели, дисциплина. Нет отговорок. Нет "попробуй". Только действие. |

**Как общаться.** Пиши как человеку. Не нужно заучивать команды и синтаксис. "Напомни мне завтра позвонить маме", "Сколько я потратил на еду этот месяц", "Найди рецепт карбонары" — агент сам поймёт, какой инструмент вызвать. Но если хочешь точности и скорости, можешь напрямую попросить конкретный тул: `write_file(notes/idea.txt, Текст заметки)` или `query_db(SELECT * FROM meals WHERE date = '2024-01-15')`. Агент поймёт и оба варианта.

**Принцип: от задачи к инструменту.** Ты думаешь о задаче — агент подбирает инструмент. Хочешь записать мысль? Агент вызовет `write_file`. Нужно найти старую заметку? `search_files` или `search_memory`. Требуется посчитать сумму трат за месяц? `query_db` с SQL. Ты видишь каждый вызов в чате — tool trace показывает имя инструмента, параметры и результат. Чем больше ты используешь агента, тем лучше он тебя понимает — через семантическую память (remember_fact → embeddings → search_memory) и эпизодические хроники (recall_episodes).

Готов? Поехали. Двенадцать кейсов. От простого к сложному. От "запиши мысль" до "автоматизируй мой день".

## Кейс 1: Быстрые заметки — мысль не ускользнёт

**Уровень:** 1 · **Время освоения:** 5 минут · **Нужно знать:** ничего

---

### Проблема

Пришла в голову гениальная идея — записал на краю салфетки. Номер телефона диктовали по телефону — набрал в заметках. Ссылку на статью скинули в мессенджер — скопировал в буфер обмена. А потом всё это безвозвратно теряется. Салфетка в мусорке через час. Заметка среди сотни других неприметных. Буфер перезаписан следующим копированием. Нужно единое место, куда можно быстро сбросить любую мысль — и гарантированно найти потом, даже если не помнишь точное название файла.

OpenClaw решает эту проблему радикально: у тебя есть полноценная файловая система внутри приложения. Пишешь текстом — агент создаёт файл. Хочешь найти — агент ищет по именам и содержимому. Всё хранится локально, никуда не утекает, доступно даже без интернета.

---

### Что умеет OpenClaw

Три инструмента покрывают 95% потребностей в заметках:

- `write_file(path, content)` — создаёт файл по указанному пути, записывает текст. Если папки в пути не существуют — создаёт их автоматически.
- `read_file(path)` — читает содержимое файла и показывает в чате.
- `search_files(query)` — ищет по именам файлов И по их содержимому. Возвращает список совпадений.
- `list_dir(path)` — показывает дерево файлов и папок.

Всё. Никаких облачных сервисов, никаких синхронизаций, никаких подписок. Файлы лежат в твоём телефоне, рядом с приложением.

---

### Пошагово: запись, поиск, чтение

**Шаг 1. Записываем контакт**

Ты пишешь:
> Запиши: номер Ивана +7-999-123-45-67

Агент анализирует запрос: нужно создать файл с контактной информацией. Определяет путь — `contacts/ivan.txt`. Вызывает инструмент:
```
write_file(contacts/ivan.txt, Иван — +7-999-123-45-67)
```

В чате, под ответом агента, ты видишь tool trace:
```
[write_file] contacts/ivan.txt — OK (created)
```

Агент отвечает: "Записал. Файл contacts/ivan.txt создан."

Обрати внимание: агент сам выбрал папку `contacts/` и имя файла `ivan.txt`. Ты мог бы уточнить путь: "Запиши в телефоны/иван.txt" — и агент бы использовал твой вариант.

**Шаг 2. Создаём заметку с идеями для проекта**

Ты пишешь:
> Создай заметку "Идеи для проекта": 1) Автоматизация отчётов 2) Интеграция с Telegram 3) Мобильная версия дашборда

Агент вызывает:
```
write_file(projects/ideas.txt, Идеи для проекта

1. Автоматизация отчётов
2. Интеграция с Telegram
3. Мобильная версия дашборда)
```

Получаешь подтверждение. Файл создан, содержимое записано. Теперь эта заметка не потеряется — она лежит в папке `projects/`.

**Шаг 3. Смотрим все файлы**

Ты пишешь:
> Покажи все мои файлы

Агент вызывает `list_dir(".")` и показывает дерево:
```
contacts/
  ivan.txt
projects/
  ideas.txt
```

Ты видишь структуру: две папки, в каждой по файлу. Это твоя личная файловая система. По мере использования она будет расти: добавятся заметки, рецепты, отчёты, шаблоны.

**Шаг 4. Ищем конкретную заметку**

Ты пишешь:
> Найди заметку про Ивана

Агент вызывает `search_files("Иван")`. Система просматривает все файлы, находит:
```
contacts/ivan.txt (совпадение в имени файла)
```

Агент показывает: "Нашёл один файл: contacts/ivan.txt"

А теперь представь: у тебя 50 файлов. `search_files` найдёт все, где встречается "Иван" — в имени или в содержимом.

**Шаг 5. Читаем файл**

Ты пишешь:
> Прочитай файл projects/ideas.txt

Агент вызывает `read_file("projects/ideas.txt")`, получает содержимое и выводит тебе в чат:
```
Идеи для проекта

1. Автоматизация отчётов
2. Интеграция с Telegram
3. Мобильная версия дашборда
```

---

### Продвинутые фишки: организация, шаблоны, память

**1. Организация папок — не клади всё в корень**

Когда файлов мало — бардак терпим. Когда становится 30+ — найти невозможно. Создавай структуру с самого начала:

> Создай папки: notes/, contacts/, projects/, finance/, health/, recipes/

Агент создаст все директории. Теперь когда создаёшь файл, указывай нужную папку:
> Запиши в notes/movie_list.txt: фильмы к просмотру — Интерстеллар, Дюна, Бегущий по лезвию

> Запиши в finance/budget_feb.txt: Бюджет февраля — аренда 30000, еда 15000, транспорт 5000

**2. Шаблоны заметок — копируй и заполняй**

Попроси агента создать шаблон, который будешь копировать каждый раз:

> Создай шаблон заметки "Встреча": Дата: ___. Участники: ___. Повестка: ___. Решения: ___. Действия: ___.

Агент сохранит файл `templates/meeting.txt`:
```
Дата: ___
Участники: ___
Повестка: ___
Решения: ___
Действия: ___
```

Когда нужно — копируешь шаблон:
> Скопируй шаблон "Встреча" в meetings/2024_01_15_alpha.txt и заполни: Дата: 15 января, Участники: Иван, Петр

Агент: `read_file("templates/meeting.txt")` → заменяет placeholder'ы → `write_file("meetings/2024_01_15_alpha.txt", [заполненный шаблон])`.

**3. Связь с семантической памятью — контекст к контактам**

Контакту можно добавить контекст, который агент вспомнит позже:

> Запомни: Иван — фронтенд-разработчик, работал над проектом Альфа, предпочитает React

Агент вызовет:
```
remember_fact("Иван", "фронтенд-разработчик, работал над проектом Альфа, предпочитает React", "contacts")
```

Теперь через месяц:
> Кто такой Иван?

Агент вызовет `search_memory("Иван")` → найдёт факт → ответит с контекстом. Это работает независимо от файлов — память хранит векторные представления смысла.

**4. Теги в именах файлов — система именования**

Используй префиксы для быстрого поиска по маске:
- `meeting_2024_01_15_alpha.txt` — все встречи начинаются с `meeting_`
- `recipe_carbonara_v2.txt` — все рецепты начинаются с `recipe_`
- `expense_taxi_450_2024_01_15.txt` — все траты начинаются с `expense_`
- `idea_push_notifications.txt` — все идеи начинаются с `idea_`

Потом ищешь:
> Найди все файлы с meeting в названии

Агент: `search_files("meeting")` → список всех встреч.

**5. Поиск по содержимому — находит даже если не помнишь имя**

`search_files` ищет не только по именам, но и по содержимому файлов. Записал "бюджет" внутри заметки о встрече — `search_files("бюджет")` найдёт эту заметку, даже если в названии слова "бюджет" нет.

---

### Куда расти

- **Кейс 9** — глубокая организация файлов: структура папок, массовые операции, архивация
- **Кейс 11** — семантический поиск: ищешь по смыслу, а не по точным словам. "Где я записал про встречу?" — и агент найдёт, даже если файл называется `meeting_2024_01_15.txt` а ты спрашиваешь "конференция в январе"

## Кейс 2: Напоминания — ничего не забудешь

**Уровень:** 1 · **Время освоения:** 5 минут · **Нужно знать:** ничего

---

### Проблема

Надо позвонить маме — помнишь утром, забываешь к вечеру. Записаться к стоматологу — откладываешь три недели. Выключить плиту через два часа — это вообще на грани чуда, если вспомнишь. Купить молоко по дороге домой — проезжаешь мимо магазина, в голове только задачи с работы. Мозг не должен держать рутину — он нужен для решения сложных проблем. Нужен надёжный внешний напоминальщик, который сработает даже если телефон в кармане, экран выключен, и ты забыл про запрос.

OpenClaw использует Android WorkManager — системный механизм, который гарантирует выполнение задач даже при закрытом приложении и перезагрузке телефона. Это не хак — это официальный Google API для фоновой работы.

---

### Что умеет OpenClaw

- `schedule_task(name, trigger_at, payload)` — одноразовое напоминание на точное время (timestamp в миллисекундах). Задача сохраняется в системе, WorkManager отслеживает её выполнение.
- `schedule_task(name, cron, payload)` — периодическое напоминание по расписанию cron. "Каждый день в 9:00", "Каждый понедельник в 10:00".
- `cancel_task(name)` — отменить ранее созданную задачу по её ID/имени.
- `send_notification(title, body, actions[])` — мгновенное уведомление прямо сейчас, без отложенного времени.

---

### Пошагово: от одноразового до периодического

**Шаг 1. Напоминание на конкретное время**

Ты пишешь:
> Напомни мне завтра в 10:00 позвонить маме

Агент анализирует: "завтра в 10:00" → вычисляет timestamp (например, 1705674000000). Вызывает:
```
schedule_task(
  name = "call_mom",
  trigger_at = 1705674000000,
  payload = "Позвонить маме"
)
```

В чате видишь tool trace:
```
[schedule_task] call_mom — trigger_at: 2024-01-20 10:00 — OK
```

Агент подтверждает: "Напоминание call_mom установлено на завтра в 10:00."

Ровно в 10:00, независимо от того открыто ли приложение, телефон покажет уведомление: "Позвонить маме". Тап по уведомлению откроет ChatScreen с контекстом — можешь сразу ответить агенту "Позвонил, всё ок" или "Перенеси на час".

**Шаг 2. Периодическое напоминание**

Ты пишешь:
> Каждый день в 9:00 напоминай проверить почту

Агент вызывает:
```
schedule_task(
  name = "check_email_daily",
  cron = "0 9 * * *",
  payload = "Проверить почту"
)
```

Теперь каждое утро в 9:00 — уведомление. Это твой будильник для рутины. Каждый день, включая выходные. Если нужно только по будням — скажи "по будням", агент сделает cron `0 9 * * 1-5`.

**Шаг 3. Напоминание через промежуток времени**

Ты пишешь:
> Напомни через 2 часа выключить плиту

Агент считает: сейчас 14:30, значит trigger_at = 16:30. Вызывает `schedule_task` с вычисленным временем:
```
[schedule_task] stove_off — trigger_at: 2024-01-19 16:30 — OK
```

Это спасает ситуации: поставил кастрюлю, записал голосом "через 2 часа", забыл — агент напомнит.

**Шаг 4. Показать все напоминания**

Ты пишешь:
> Покажи мои напоминания

Агент использует `recall_episodes` для поиска в истории вызовов `schedule_task`, или `query_db` если задачи хранятся во внутренней БД приложения. Показывает список:
```
Активные напоминания:
- call_mom: 2024-01-20 10:00 (одноразовое)
- check_email_daily: каждый день 9:00 (периодическое)
- stove_off: 2024-01-19 16:30 (одноразовое)
```

**Шаг 5. Отменить напоминание**

Ты пишешь:
> Отмени напоминание про почту

Агент определяет ID задачи — "check_email_daily". Вызывает:
```
cancel_task("check_email_daily")
```

Получаешь подтверждение: "Напоминание check_email_daily отменено."

### ВАЖНО: ограничения Android — знай свою платформу

**Минимальный период — 15 минут.** Нельзя поставить напоминание каждые 5 минут. Это жёсткое ограничение WorkManager для экономии батареи. Если попросишь "каждые 10 минут" — агент предупредит: "Минимальный период 15 минут. Устанавлию каждые 15 минут."

**Точность ±10–15 минут в doze mode.** Когда телефон долго лежит без движения (в кармане, на столе ночью), Android переходит в режим экономии батареи — doze mode. Напоминания откладываются до "окна обслуживания" и могут сдвинуться на 10–15 минут. Если нужна хирургическая точность (например, медицинские напоминания) — foreground service, но он заметно жрёт батарею.

**Задачи сохраняются при перезагрузке.** Перезагрузил телефон — все напоминания на месте. WorkManager восстанавливает их автоматически. Это не таймер внутри приложения — это системный сервис Android.

**Constraints — умные условия.** Можно добавить условия выполнения:
- "Напомни про резервное копирование только при WiFi" — schedule_task с network=unmetered constraint
- "Напомни про зарядку только когда телефон не на зарядке" — requiresCharging=false
- "Напомни выйти из дома за 30 минут до встречи" — schedule_task с вычисленным временем

**Deep link.** Тап на уведомление открывает ChatScreen с контекстом задачи. Можешь сразу ответить агенту, не ища приложение в лаунчере.

## Кейс 3: Чеклисты и списки дел — отмечай прогресс

### Проблема

Список покупок в голове — приходишь из магазина и вспоминаешь, что забыл купить масло. Задачи на день — выполнил половину, но не помнишь какую именно, и сидишь вечером в тревоге, что что-то упустил. Нужен интерактивный чеклист, который показывает прогресс, позволяет отмечать выполленное тапом, сохраняет состояние между сессиями, и работает без интернета.

OpenClaw решает это через шаблон `todo_list` — одну из шести доступных карточек. Чекбоксы интерактивные: тапнул — галочка появилась, тапнул ещё раз — исчезла.

### Что умеет OpenClaw

- `render_card(template="todo_list", params)` — показывает карточку с чекбоксами. Принимает заголовок и массив пунктов с флагами checked/unchecked.
- `write_file(path, content)` — сохраняет состояние списка в файл для долговременного хранения.
- `read_file(path)` — загружает ранее сохранённый список и восстанавливает чекбоксы.

## Кейс 4: Ролевые консультации — Эксперт на вызов

**Уровень:** 1-2 · **Время:** 15 мин · **Нужно знать:** Кейсы 1-3

---

## Проблема

Ты уже умеешь делать заметки, списки и напоминания. OpenClaw слушается как приличный помощник. Но иногда нужно не просто "записать", а **разобраться**. Составить план питания — но с учётом того, что ты вегетарианец и не переносишь орехи. Получить программу тренировок — но не из интернета, а под твой уровень и оборудование. Разобрать задачу по физике — шаг за шагом, как это сделал бы репетитор. Выучить испанские глаголы — с таблицами и примерами.

Можно искать в Google. Но там статьи на 5000 слов, реклама добавок, и никто не спросит: "А у тебя аллергия?" Можно нанять эксперта. Но это дорого, долго, и не в 11 вечера перед экзаменом.

OpenClaw умеет **вставать в роль**. Одна фраза — и он становится диетологом, тренером, репетитором или лингвистом. Не шуточный "притворись кошкой", а полноценная консультация с планами, таблицами, структурой. И главное — он помнит твои предпочтения, уровень, ограничения. Следующая консультация начинается с того места, где закончилась прошлая.

**Ключевая идея: Персона + Роль = Мощь.** Персона — это *как* говорит агент. Строгий коуч будет давать командирские установки: "Двадцать приседаний. Без остановки." Дружелюбный компаньон подбодрит: "Ты справишься, я верю в тебя!" Роль — это *о чём* говорит агент. Диетолог, тренер, репетитор, лингвист. Комбинируй: "Действуй как тренер, но со стилем Строгого коуча" — и получишь мотивирующие тренировки с железной дисциплиной. Переключай персону под задачу — и один и тот же ответ будет звучать по-разному.

## Что умеет OpenClaw

- **Rich markdown через mikepenz multiplatform-markdown-renderer** — красивое форматирование прямо в чате: заголовки, таблицы, списки, цитаты, код. Выглядит как хорошая статья, а не стена текста.
- **remember_fact** — запоминает твои предпочтения, ограничения, уровень подготовки. Назвал раз что вегетарианец — запомнит навсегда.
- **search_memory** — находит ранее записанные факты. "Какой у меня уровень испанского?" — вспомнит.
- **write_file** — сохраняет план, программу или разбор в файл, чтобы не потерялось.
- **render_card(table)** — если нужно показать данные структурированной таблицей.

### Сценарий 3: Репетитор (помощь с ДЗ)

#### Шаг 1: Дать задачу
- **Ты пишешь:** "Действуй как репетитор по физике. Объясни решение: камень бросают вертикально вверх со скоростью 20 м/с. На какую высоту поднимется? g = 10 м/с²"
- **Агент делает:** Выбирает персону "Наставник" (объясняет по полочкам) + роль репетитора.
- **Видишь:**

  > **Решение задачи на движение вертикально вверх**
  >
  > **Дано:**
  > - Начальная скорость: `v₀ = 20 м/с`
  > - Ускорение свободного падения: `g = 10 м/с²`
  > - Скорость на максимальной высоте: `v = 0 м/с`
  >
  > **Найти:** максимальную высоту `h`
  >
  > **Решение:**
  >
  > Используем формулу:
  > ```
  > v² = v₀² - 2gh
  > ```
  >
  > На максимальной высоте `v = 0`, поэтому:
  > ```
  > 0 = v₀² - 2gh
  > 2gh = v₀²
  > h = v₀² / 2g
  > h = 400 / 20 = 20 м
  > ```
  >
  > **Ответ: 20 метров**
  >
  > > 💡 Проверь себя: если g = 9.8 м/с², высота будет ~20.4 м. Разница небольшая, но на ЕГЭ важна точность.

#### Шаг 2: Попросить похожую задачу
- **Ты пишешь:** "Дай похожую задачу для самостоятельного решения"
- **Агент делает:** Генерирует новую задачу через rich markdown.

  >
  > 1. На какую высоту поднимется мяч?
  > 2. Через сколько секунд он вернётся?
  >
  > *(g = 10 м/с²)*
  >
  > *Напиши ответ — проверю.*

# Кейс 5: Дневник питания — считай, что ешь

**Уровень:** 2 · **Время освоения:** 15 минут · **Нужно знать:** Кейсы 1–3

---

### Проблема

Ешь что попало — и не понимаешь почему вес растёт. Пробовал считать калории в голове — забыл к обеду сколько съел на завтрак. Скачивал приложения для подсчёта калорий — они требуют подписку, шлют данные в облако, и каждый приём пищи вносить 5 минут. Нужна система: записываешь быстро текстом, агент считает суммы, рисует графики, показывает тренды, напоминает про лимиты — и всё это локально, без подписок.

OpenClaw превращает твой телефон в центр управления питанием. SQLite-база хранит каждый приём пищи. SQL-запросы считают суммы и средние. Столбчатый график показывает динамику. Семантическая память запоминает предпочтения (вегетарианец, аллергии, любимые блюда). Всё работает offline.

---

### Что умеет OpenClaw

- `insert_db(table, values)` — создаёт таблицы (через CREATE TABLE внутри values._sql) и записывает данные (INSERT). **Только insert_db может создавать таблицы!**
- `query_db(sql, params[])` — **только чтение**: SELECT, PRAGMA, SHOW TABLES. Ни CREATE TABLE, ни INSERT, ни UPDATE, ни DELETE — только SELECT.
- `render_card(template="chart_bar", params)` — столбчатый график калорий по дням или категориям.
- `render_card(template="table", params)` — таблица приёмов пищи за день/неделю.
- `remember_fact(key, value, category)` — запомнить предпочтения: вегетарианец, не переношу лактозу, люблю острую еду.

**ВАЖНО — SQL-разделение:**
- `query_db` — **только SELECT**. Попытка создать таблицу через query_db вернёт ошибку. `query_db("CREATE TABLE ...")` — не сработает.
- `insert_db` — **CREATE TABLE, INSERT, UPDATE, DELETE**. Всё что меняет данные — только через insert_db.

Агент генерирует SQL автоматически, но ты можешь попросить показать запрос: "Покажи SQL-запрос который ты использовал".

**1. Установка лимита калорий**

WHERE date >= date('now', '-7 days')
GROUP BY meal_type
ORDER BY total DESC

**4. Связь с таблицей веса — корреляция данных**

SELECT m.date, SUM(m.calories) as kcal, w.weight
FROM meals m
LEFT JOIN weight w ON m.date = w.date
WHERE m.date >= date('now', '-30 days')
GROUP BY m.date
ORDER BY m.date
```

БД возвращает данные. Агент строит `chart_bar` с двумя осями — калории и вес. Ты видишь: в дни с 2500+ ккал вес растёт. Это не "агент интуитивно анализирует" — это агент генерирует SQL, SQLite считает, агент визуализирует результат.

## Кейс 5: Трекер тренировок — прогресс в цифрах

**Уровень:** 2 · **Время освоения:** 15 минут · **Нужно знать:** Кейсы 1–3

---

### Проблема

Ходишь в зал месяцами, но не помнишь сколько жмёшь. На глазок кажется, что растёшь — а на деле веса те же. Подходы, веса, повторения — всё смешалось в голове. Хочется видеть объективный прогресс: растут ли рабочие веса, сколько объёма за тренировку, какие личные рекорды по каждому упражнению, сравнение периодов.

OpenClaw превращает твой телефон в тренерский журнал. Каждая тренировка — запись в SQLite. Каждый подход — строка в таблице. SQL считает максимумы, суммы, средние. chart_bar рисует прогресс. table показывает рекорды. write_file сохраняет программу тренировок. Строгий коуч мотивирует, когда лень.

---

### Что умеет OpenClaw

Те же инструменты, что и в Кейсе 4:

- `insert_db(table, values)` — CREATE TABLE + INSERT. **Только через insert_db создание таблиц!**
- `query_db(sql, params[])` — **только SELECT**. MAX, SUM, COUNT, GROUP BY, ORDER BY.
- `render_card(chart_bar)` — график прогресса по весам за период.
- `render_card(table)` — таблица подходов, рекордов, программы.
- `write_file(path, content)` — сохранить программу тренировок в файл.

```sql
SELECT
  exercise,
  MAX(weight) as pr_weight,
  MAX(reps) as pr_reps,
  COUNT(DISTINCT date) as total_sessions
FROM workouts
GROUP BY exercise
ORDER BY pr_weight DESC
```

→ `render_card(table)` с колонками: Упражнение, Рекорд вес, Рекорд повторов, Всего тренировок.

**4. Связь с таблицей сна — корреляция**

Если ты ведёшь таблицу сна (аналогично meals — insert_db CREATE TABLE + INSERT), агент может JOIN:

```sql
SELECT
  w.date,
  w.exercise,
  MAX(w.weight) as max_w,
  s.hours as sleep_hours
FROM workouts w
LEFT JOIN sleep s ON w.date = s.date
WHERE w.date >= date('now', '-30 days')
GROUP BY w.date, w.exercise
ORDER BY w.date
```

Проверяешь гипотезу: после 8+ часов сна жмёшь больше? Данные скажут. Корреляция находится SQL-запросом, результатом считает БД, агент только форматирует вывод.

**5. Периодизация — mesocycle tracking**

> Покажи средний вес по приседаниям по неделям

```sql
SELECT
  strftime('%Y-%W', date) as week,
  AVG(weight) as avg_weight,
  MAX(weight) as max_weight
FROM workouts
WHERE exercise = 'Приседания'
GROUP BY week
ORDER BY week
```

Видно: неделя 1 — средний 62.5, неделя 4 — средний 77.5. Прогресс +15 кг за мезоцикл.

## Кейс 6: Учёт финансов — куда утекают деньги

**Уровень:** 2 · **Время освоения:** 15 минут · **Нужно знать:** Кейсы 1–3

---

### Проблема

Зарплата пришла — через неделю уже дует в кошельке. Куда ушло? Кофе по 450 рублей, такси по 300, доставка еды каждый вечер по 800. Мелочь, а набегает. Хочется видеть реальную картину: сколько суммарно, на что именно, в какие дни больше всего трат, какие категории съедают бюджет. Не интуитивно "кажется много" — а конкретные цифры: 23% на еду, 18% на транспорт, 12% на подписки.

OpenClaw строит полноценную систему учёта финансов на SQLite. Траты записываются за секунды текстом. SQL-запросы считают суммы, средние, проценты. chart_bar показывает структуру расходов. table выводит детализацию. remember_fact хранит бюджетные лимиты. Всё локально — твои финансовые данные никогда не покидают телефон.

---

### Что умеет OpenClaw

- `insert_db(table, values)` — CREATE TABLE + INSERT. **Только через insert_db!** query_db не умеет создавать таблицы.
- `query_db(sql, params[])` — **только SELECT**: SUM, AVG, COUNT, GROUP BY, HAVING, ORDER BY, JOIN.
- `render_card(chart_bar)` — столбчатый график: траты по категориям или по дням.
- `render_card(table)` — таблица транзакций с датами, суммами, категориями.
- `remember_fact(key, value, category)` — месячный бюджет, финансовые цели, инсайты.
- `write_file(path, content)` — экспорт отчётов в текстовый файл.

### Пошагово: от первой траты до бюджетного контроля

**Шаг 1. Создаём таблицу expenses**

Ты пишешь:
> Создай таблицу трат: дата, сумма, категория, описание

Агент через insert_db (не query_db!):
```
insert_db(
  table = "expenses",
  values = {
    "_sql": "CREATE TABLE expenses (id INTEGER PRIMARY KEY AUTOINCREMENT, date TEXT, amount REAL, category TEXT, description TEXT)"
  }
)
```

Колонки:
- `id` — автономер
- `date` — дата траты, "2024-01-15"
- `amount` — сумма в рублях (REAL — копейки через точку: 450.50)
- `category` — категория: еда, транспорт, развлечения, жильё, подписки, прочее
- `description` — что именно купил

**Шаг 2. Записываем трату**

Ты пишешь:
> Потратил 450 на кофе, категория еда

Агент:
```
insert_db(
  table = "expenses",
  values = {"date": "2024-01-15", "amount": 450, "category": "еда", "description": "Кофе"}
)
```

**Шаг 3. Ещё траты**

Ты пишешь:
> Потратил 1200 на такси домой, категория транспорт

> Потратил 850 на доставку еды, категория еда

Агент повторяет INSERT для каждой. Три траты записаны.

**Шаг 4. Сколько потратил сегодня?**

Ты пишешь:
> Сколько я потратил сегодня?

Агент:
```
query_db(
  sql = "SELECT SUM(amount) as total FROM expenses WHERE date = ?",
  params = ["2024-01-15"]
)
```

БД: `total = 2500`. Агент: "Сегодня 2500 ₽: кофе 450 + такси 1200 + доставка 850."

**Шаг 5. График по категориям — структура расходов**

Ты пишешь:
> Покажи траты по категориям за месяц графиком

Агент:
```sql
SELECT category, SUM(amount) as total
FROM expenses

**Шаг 6. Таблица транзакций — детализация**

Ты пишешь:
> Покажи все траты за неделю таблицей

**Шаг 7. Запоминаем инсайт**

> Запомни: я трачу слишком много на доставку еды

Агент:
```
remember_fact("финансы", "трачу слишком много на доставку еды", "insights")
```

При следующем анализе агент подтянет этот факт: "Как и ты сам отмечал, доставка еды — твоя главная статья перерасхода."

### Продвинутые фишки: бюджет, динамика, экспорт

**1. Установка месячного бюджета — контроль остатка**

> Установи бюджет 50000 на месяц

Агент: `remember_fact("бюджет", "50000", "finance")`.

Потом:
> Сколько осталось от бюджета?

Агент: `query_db(SELECT SUM(amount) FROM expenses WHERE date >= '2024-01-01')` → 32400 потрачено. Ответ: "Осталось 17600 ₽ из 50000 (65% потрачено, 11 дней до конца месяца)."

**2. Динамика по дням — в какие дни срываешься**

> Траты по дням за две недели

```sql
SELECT date, SUM(amount) as daily_total
FROM expenses
WHERE date >= date('now', '-14 days')
GROUP BY date
ORDER BY date
```

→ `chart_bar` — 14 столбцов. Видно: пятницы и субботы всплески (3000–4000), будни стабильно (1000–1500).

**3. Средний чек по категории — норма или перебор**

> Средний чек на еду

```sql
SELECT AVG(amount), COUNT(*), SUM(amount)
FROM expenses
WHERE category = 'еда'
```

"Средний чек на еду: 485 ₽, 47 покупок, итого 22795 ₽ за всё время."

**4. Поиск по описанию — находишь конкретную трату**

> Сколько я потратил на такси за месяц?

```sql
SELECT SUM(amount), COUNT(*)
FROM expenses
WHERE category = 'транспорт' AND description LIKE '%такси%'
```

"На такси: 8400 ₽, 14 поездок."

**5. Топ трат — куда уходят большие суммы**

> Покажи 10 самых больших трат за месяц

```sql
SELECT date, description, amount
FROM expenses
WHERE date >= date('now', '-30 days')
ORDER BY amount DESC
LIMIT 10
```

→ `render_card(table)`. Осознаёшь: три самых крупных — аренда (30000), новые наушники (8000), подарок (5000).

**6. Экспорт отчёта в файл**

> Сохрани траты за январь в файл reports/expenses_jan.txt

Агент: `query_db(SELECT * FROM expenses WHERE date LIKE '2024-01%')` → форматирует в текст → `write_file`. Получаешь текстовый отчёт, который можно отправить бухгалтеру, архивировать, или импортировать в другую систему.

**7. Корреляция: траты + тренировки + сон**

Все данные в одной SQLite — значит можно JOIN'ить:

```sql
SELECT
  e.date,
  SUM(e.amount) as spent,
  COUNT(DISTINCT w.date) as trained,
  s.hours as sleep
FROM expenses e
LEFT JOIN workouts w ON e.date = w.date
LEFT JOIN sleep s ON e.date = s.date
WHERE e.date >= date('now', '-30 days')
GROUP BY e.date
ORDER BY e.date
```

Проверяешь: в дни после тренировок тратишь больше на еду? Если да — это нормально (организм требует). Но если тратишь больше на развлечения — лень после зала, не хочется готовить.

## Кейс 7: Найти и сохранить — интернет на твоей стороне

**Уровень:** 3 · **Время освоения:** 10 минут · **Нужно знать:** Кейсы 1–3

### Проблема

Нашёл крутой рецепт в поисковике — но сайт грузится 15 секунд, половина экрана реклама, попапы лезут с предложением подписаться. Новость нужная — но через неделю ссылка протухнет, страница удалена, доступ по подписке. Хочется быстро найти информацию, вытащить суть, очистить от рекламы, сохранить локально — и иметь под рукой всегда, даже без интернета, даже если оригинальный сайт закрылся.

OpenClaw делает именно это: ищет через `web_search`, загружает чистый текст через `web_fetch`, сохраняет через `write_file` в твою локальную файловую систему. Никакой рекламы, никаких трекеров, никаких облачных зависимостей. Найденное — твоё навсегда.

---

### Что умеет OpenClaw

- `web_search(query)` — поиск в интернете, возвращает сниппеты (заголовок + описание + URL).
- `web_fetch(url)` — загружает текстовое содержимое конкретной страницы, очищенное от HTML-тегов и скриптов.
- `write_file(path, content)` — сохраняет найденное в файл.
- `remember_fact(key, value, category)` — запоминает ключевые факты для будущего семантического поиска.
- `render_card(template="weather_card", params)` — если искал погоду, покажет красивую карточку.

## Кейс 8: Организация файлов — порядок в голове начинается с порядка в файлах

**Уровень:** 3 · **Время освоения:** 10 минут · **Нужно знать:** Кейсы 1–3

---

### Проблема

Заметки валяются где попало. 47 файлов в корневой папке, половина называется "новый_документ_копия_финал_2.txt". Найти нужное — миссия невыполнима. Прошлый месяц не можешь отличить от позапрошлого. Хочется структуру: работа отдельно, личное отдельно, проекты по папкам, даты в именах файлов, понятная система именования.

OpenClaw даёт полноценную файловую систему. `list_dir` показывает дерево. `search_files` ищет по именам и содержимому. `read_file` + `write_file` комбинируются для любых операций: перемещение, копирование, объединение, архивация.

---

## Кейс 9: Периодические отчёты — цифры говорят громче слов

**Уровень:** 3 · **Время освоения:** 15 минут · **Нужно знать:** Кейсы 4–6 (трекинг)

---

### Проблема

Ведёшь трекинг: еду в `meals`, тренировки в `workouts`, траты в `expenses`. Данные копятся, но лежат мёртвым грузом. Ты знаешь что они есть, но не видишь картины. Хочется сводку: сколько потратил за неделю, как часто тренировался, сколько калорий в среднем, растут ли веса. И хочется получать это автоматически — без необходимости каждое воскресенье вручную писать SQL.

OpenClaw объединяет `query_db` (SQL-запросы к нескольким таблицам), `render_card` (графики и таблицы), `schedule_task` (автоматическая отправка по расписанию) и `write_file` (сохранение отчётов). Комбо-отчёт строится за один запрос.

---

### Что умеет OpenClaw

- `query_db(sql, params[])` — SELECT с группировкой, суммами, фильтрами по дате, JOIN между таблицами.
- `render_card(chart_bar)` — столбчатый график. **Единственный доступный тип графика!** `chart_line` и `chart_pie` НЕ существуют.
- `render_card(table)` — табличное представление данных.
- `schedule_task(name, cron, payload)` — автоматическая генерация и отправка отчётов по расписанию.
- `write_file(path, content)` — сохранение отчёта в файл.

**1. Сравнение периодов — эта неделя vs прошлая**

```

**2. JOIN между таблицами — связь данных**

Если ведёшь несколько таблиц (траты, тренировки, сон), агент JOIN'ит:

SELECT
  e.date,
  SUM(e.amount) as spent,
  COUNT(DISTINCT w.date) as trained,
  s.hours as sleep
FROM expenses e
LEFT JOIN workouts w ON e.date = w.date
LEFT JOIN sleep s ON e.date = s.date
WHERE e.date >= date('now', '-14 days')
GROUP BY e.date
ORDER BY e.date
```

**3. Группировка по категориям — структура расходов**

> Разбей траты за неделю по категориям

```sql

FROM expenses
WHERE date >= date('now', '-7 days')
GROUP BY category
ORDER BY total DESC
```

→ `render_card(table)` + `render_card(chart_bar)` — видно где перерасход с процентами.

**4. Ручной SQL — полный контроль**

> Выполни SQL: SELECT date, AVG(daily) FROM (SELECT date, SUM(calories) as daily FROM meals GROUP BY date) WHERE date >= date('now', '-30 days')

## Кейс 10: Семантический поиск — "Я где-то это записал"

**Уровень:** 4 · **Время освоения:** 15 минут · **Нужно знать:** Кейсы 1–9

---

### Проблема

Помнишь, что записал что-то важное. Но где? В файле `meeting_2024_01_15.txt`? Сказал агенту "запомни"? В заметке в папке `work/`? Или может в таблице `expenses`? Какой была формулировка? Точное слово?

С обычным поиском нужно точное совпадение. Записал "пароль от WiFi в отеле Санкт-Петербург" — а ищешь "пароль wifi питер" — и ничего не находится. Полнотекстовый поиск (FTS) ищет по словам: если слова нет — не найдёт. Это фундаментальное ограничение текстового поиска.

**Семантический поиск понимает СМЫСЛ, не только точные слова.** Это киллер-фича OpenClaw. Вот почему он круче обычных заметок, блокнотов, файловых систем и даже облачных note-taking приложений.

Как работает: ты говоришь "Запомни: ..." — система создаёт **embedding** (векторное представление смысла) через модель `nv-embedqa-e5-v5` (NVIDIA NIM). Вектор сохраняется в `sqlite-vec`. Когда ищешь — запрос тоже превращается в вектор, и система находит ближайшие по **семантической близости**, даже если формулировка полностью другая.

---

### Что умеет OpenClaw

- `remember_fact(key, value, category)` — сохраняет факт в долговременную семантическую память. Создаёт embedding автоматически.
- `search_memory(query, mode)` — ищет факты. `mode="semantic"` (default) — векторный поиск. `mode="fts"` — полнотекстовый.
- `recall_episodes(range, type)` — ищет в эпизодической памяти: лог всех действий, диалогов, вызовов инструментов.
- `read_file(path)` — читает файлы как fallback, когда семантический поиск не даёт результата.
- `search_files(query)` — поиск по содержимому файлов.

**Под капотом:**
- Embeddings: NVIDIA `nv-embedqa-e5-v5` через NIM (primary) → fallback на локальную модель
- Векторное хранилище: `sqlite-vec` — расширение SQLite
- Полнотекстовый fallback: FTS4 (встроен в SQLite)
- Эпизодическая память: SQLite-таблица с логом всех tool calls и сообщений

**ВАЖНО:** Если NIM недоступен — автоматический fallback на FTS4 с предупреждением: "Семантический поиск недоступен, используется текстовый поиск." Когда NIM восстанавливается — embeddings создаются retroactively для всех фактов без векторов.

---

### Пошагово: сохраняем, ищем, находим

**Шаг 1. Запоминаем пароль от Wi-Fi**

Ты пишешь:
> Запомни: пароль от Wi-Fi в отеле Москва — Room2345, сеть HotelMoscow_Guest

Агент:
```

  key = "wifi отель москва",
  value = "пароль Room2345, сеть HotelMoscow_Guest",
  category = "travel"
)
```

Система отправляет текст "wifi отель москва пароль Room2345" в NIM, получает 768-мерный вектор, сохраняет в `sqlite-vec`. В tool trace:
```

```

**Шаг 2. Запоминаем ресторан**

Ты пишешь:
> Запомни: мой любимый ресторан — Тесто на Невском, паста карбонара там лучшая

Агент: `remember_fact("ресторан", "Тесто на Невском, карбонара лучшая", "food")` → embedding создан.

Ты пишешь:
> Запомни: я предпочитаю работать по утрам, пик продуктивности 9–12

Агент: `remember_fact("продуктивность", "пик 9–12 утра, предпочитаю утро", "productivity")` → embedding создан.

**Шаг 4. Ищем пароль — другими словами!**

Агент:
```
search_memory("пароль wifi отель")
```

Система превращает "пароль wifi отель" в вектор, ищет ближайшие векторы в `sqlite-vec` — находит факт "wifi отель москва" из шага 1. Векторное расстояние маленькое, потому что:
- "вайфай" и "Wi-Fi" — семантически идентичны
- "тот отель" и "Москва" — контекстually связаны (вектор помнит контекст)
- "пароль" — общее слово

Агент отвечает: "Пароль от Wi-Fi в отеле Москва — Room2345, сеть HotelMoscow_Guest."

**Шаг 5. Ищем ресторан — по блюду, не по названию**

Ты пишешь:
> Где я ел крутую карбонару?

Агент: `search_memory("карбонара ресторан")` → находит факт "Тесто на Невском, карбонара лучшая". "Крутую" и "лучшая" — семантически близкие векторы. "Где я ел" и "ресторан" — тоже. Ответ: "Ты отмечал, что лучшая карбонара — в ресторане 'Тесто на Невском'."

**Шаг 6. Ищем режим — расплывчатый запрос**

Ты пишешь:
> Когда я лучше всего работаю?

Агент: `search_memory("продуктивность время")` → находит "пик 9–12 утра, предпочитаю утро". "Когда" и "время" векторно близки. "Лучше всего работаю" и "продуктивность" — синонимичны в embedding-пространстве.

**Шаг 7. Эпизодическая память — что делали вчера**

Ты пишешь:
> Что мы обсуждали вчера про тренировки?

Агент:
```
recall_episodes(range = "yesterday", type = "workout")
```

`recall_episodes` ищет в логе всех взаимодействий — tool calls, диалоги, уведомления. Возвращает хронику:
```
Вчера, 18:30: Вы записали тренировку
  [insert_db] workouts — Приседания 4×80×8 — OK
Вчера, 18:45: Вы спросили рекорд по приседаниям
  [query_db] SELECT MAX(weight) FROM workouts WHERE exercise='Приседания' → 80
Вчера, 19:00: Вы сохранили программу тренировок
  [write_file] programs/split.txt — OK
```

Это не просто "помнишь что-то" — это полный аудитлог всех действий.

**Шаг 8. Кросс-поиск — всё вместе**

Ты пишешь:
> Найди всё что связано с деньгами

Агент запускает три поиска параллельно:
1. `search_memory("деньги")` — факты про финансы (бюджет, траты, курс доллара)
2. `recall_episodes("last_month")` — диалоги про бюджет и расходы
3. `search_files("бюджет")` — файлы с упоминанием

Собирает сводку:
```
По теме "деньги" найдено:

Факты (3):
- Бюджет: 50000 ₽ в месяц
- Курс доллара: 92.50
- Трачу слишком много на доставку еды

Эпизоды (5):
- 15.01: Создана таблица expenses
- 16.01: Записана трата 450 ₽ на кофе
- ...

Файлы (2):
- personal/finance/expenses.txt
- reports/weekly_03.txt
```

### Продвинутые фишки: автоконтекст, режимы, анализ хроник

**1. Автоматический контекст при каждом запросе — LLM знает тебя**

При каждом твоём сообщении система автоматически (без твоего участия) подтягивает:
- top-3 релевантных факта из `search_memory`
- top-3 эпизода из `recall_episodes`

Это происходит прозрачно. Если ты раньше сказал "я вегетарианец", а потом спрашиваешь "Что приготовить на ужин?" — агент уже знает контекст и предложит вегетарианские варианты. Без необходимости повторять.

В tool trace это видно:
```
[search_memory] "что приготовить" → retrieved: "вегетарианец" (score: 0.91)
[recall_episodes] "еда" → 3 эпизода
```

**2. Режимы поиска — semantic vs fts**

`search_memory` поддерживает два режима:
- `mode="semantic"` (default) — векторный поиск, понимает смысл, работает через NIM + sqlite-vec
- `mode="fts"` — полнотекстовый поиск, точное совпадение слов, работает через FTS4

Если семантический даёт много мусора — переключи:
> Найди по тексту: "бюджет января"

Агент: `search_memory("бюджет января", mode="fts")` — ищет точное вхождение слов.

**3. Анализ хроник — как ты используешь агента**

> Проанализируй мои хроники — какие инструменты я использую чаще всего?

Агент: `recall_episodes(range = "last_month")` → получает лог всех tool calls → считает частоту:
```
query_db:     45% (SELECT-запросы к БД)
write_file:   30% (создание заметок)
schedule_task: 15% (напоминания)
web_search:    10% (поиск в интернете)
```

Полезно понимать свои паттерны: может, ты недоиспользуешь `remember_fact`?

**4. Память работает offline**

Все embeddings хранятся локально в SQLite. После того как факт сохранён через `remember_fact` — `search_memory` работает без интернета. NIM нужен только для создания embeddings новых фактов. Поиск — полностью локальный через sqlite-vec.

**5. Fallback при недоступности NIM**

Если NIM упал или нет интернета:
- `remember_fact` сохраняет текст, но помечает "embedding pending"
- `search_memory` автоматически переключается на FTS4
- Агент предупреждает: "Семантический поиск недоступен, использую текстовый."
- Когда NIM восстанавливается — embeddings создаются retroactively для всех "pending" фактов

## Кейс 11: Комбо — полная автоматизация дня

**Уровень:** 4 · **Время освоения:** 20 минут · **Нужно знать:** все кейсы

---

### Проблема

Каждое утро открываешь пять приложений: погоду, список дел, банк, трекер, календарь. Пять тапов, пять загрузок, пять интерфейсов. Потом ещё нужно связать это воедём: если дождь — взять зонт; если вчера перетренировался — сегодня лёгкая тренировка; если бюджет на грани — не предлагать ресторан. Хочется **один запрос** — и агент собирает весь день: погода, задачи, тренировка, бюджет, напоминания, вдохновение. Всё связано, всё учтено, всё в одном месте.

OpenClaw решает это через combo-сценарии: агент последовательно вызывает набор инструментов, каждый следующий шаг может зависеть от результата предыдущего. Tool trace показывает всю цепочку — ты видишь логику.

---

### Что умеет OpenClaw

Все инструменты в одном сценарии:

- `web_search` + `render_card(weather_card)` — погода и прогноз
- `read_file` / `query_db` — задачи, трекинг, бюджет
- `schedule_task` — напоминания на день
- `write_file` — план дня в файл
- `remember_fact` — сохранить выводы и достижения
- `render_card(todo_list)` — чеклист дня с чекбоксами
- `render_card(table)` — сводная таблица показателей
- `send_notification` — мгновенное уведомление если что-то срочное

---

### Пошагово: утро, день, вечер — всё в одном запросе

**Шаг 1. Погода — что надеть и брать ли зонт**

Ты пишешь:
> Какая погода сегодня?

Агент:
```
web_search("погода Москва сегодня")
```

→ `render_card(weather_card)` — температура (-5°C), осадки (снег), ветер (3 м/с), влажность (72%). Агент добавляет комментарий: "Ниже нуля, снег — бери перчатки и внимательно на дорогах."

**Шаг 2. Задачи на день — что предстоит сделать**

Ты пишешь:
> Покажи мои задачи на сегодня

Агент: `read_file("tasks/today.txt")` — показывает список:
```
- Отправить отчёт боссу (до 12:00)
- Позвонить клиенту (15:00)
- Сходить в спортзал (18:00)
- Купить подарок жене
```

Или если задачи в БД: `query_db(SELECT * FROM tasks WHERE date = date('now'))`.

**Шаг 3. Тренировка — что сегодня в зале**

Ты пишешь:
> Какая тренировка сегодня?

Агент проверяет:
1. `query_db`: была ли уже тренировка сегодня? (нет)
2. `remember_fact`: какая программа по дням недели? (понедельник — грудь + трицепс)
3. `query_db`: что было в прошлый понедельник? (жим 60×10)
4. Отвечает: "Сегодня понедельник — грудь и трицепс. Жим лёжа: 4 подхода, пробуй 62.5 кг (было 60). Разводка: 3×12×14. Брусья: 3×10."

**Шаг 4. Напоминание — не забыть созвон**

Ты пишешь:
> Поставь напоминание на 10:45 про созвон с командой

Агент:
```
schedule_task(
  name = "team_call",
  trigger_at = 1705406700000,
  payload = "Созвон с командой — подготовить обновления"
)
```

**Шаг 5. Бюджет дня — сколько можно потратить**

Ты пишешь:
> Сколько я потратил вчера и сколько осталось от бюджета?

Агент:
```sql
-- Вчерашние траты
SELECT SUM(amount) FROM expenses WHERE date = date('now', '-1 day');
-- Всего за месяц
SELECT SUM(amount) FROM expenses WHERE date >= '2024-01-01';
```

"Вчера потрачено 2300 ₽. За месяц: 32400 из 50000. Остаток: 17600 ₽ на 11 дней — ~1600 ₽ в день."

**Шаг 6. План дня в файл — сохраняем всё в одном месте**

Ты пишешь:
> Создай файл plan/today.txt с полным планом дня

Агент собирает всё и записывает:
```
write_file("plan/today.txt", === ПЛАН НА 16 ЯНВАРЯ ===

ПОГОДА:
-5°C, снег, ветер 3 м/с
Берём: перчатки, шапка, внимательно на дорогах

ЗАДАЧИ:
☐ Отправить отчёт боссу (до 12:00)
☐ Позвонить клиенту (15:00)
☐ Сходить в спортзал (18:00)
☐ Купить подарок жене

ТРЕНИРОВКА (грудь + трицепс):
- Жим лёжа: 4×62.5 кг×8
- Разводка: 3×14 кг×12
- Брусья: 3×10

НАПОМИНАНИЯ:
- 10:45 — Созвон с командой

БЮДЖЕТ:
- Вчера: 2300 ₽
- Месяц: 32400 / 50000 ₽ (65%)
- Остаток: ~1600 ₽/день

СОВЕТ ДНЯ:
Ты вегетарианец — сегодня отличный день
попробовать новый рецепт из сохранённых.
)
```

**Шаг 7. Сохраняем впечатление о дне — для будущего анализа**

Ты пишешь:
> Запомни: сегодня хороший день, продуктивность высокая, выполнил все задачи

Агент: `remember_fact("продуктивность", "16 января — высокая, все задачи выполнены", "daily")` — embedding создан, факт доступен для семантического поиска.

### Продвинутые фишки: авто-план, условная логика, tool trace

**1. Авто-план по расписанию — set and forget**

> Каждое утро в 8:00: погода + задачи + цитата дня

Агент:
```
schedule_task(
  name = "morning_routine",
  cron = "0 8 * * *",
  payload = "combo: web_search(погода) + read_file(tasks/today.txt) + web_search(вдохновляющая цитата дня) + render_card(table)"
)
```

Каждое утро в 8:00 — уведомление со сводкой. Открываешь — и весь день перед глазами.

**2. Условная логика — если X, то Y**

> Если температура ниже -10°C — добавь в задачи "взять тёплые перчатки"

Агент выполняет:
1. `web_search(погода)` → получает температуру
2. Проверяет условие: если < -10°C
3. Если да: `read_file("tasks/today.txt")` → добавляет "взять тёплые перчатки" → `write_file`
4. `render_card(todo_list)` с обновлённым списком

Если температура выше -10°C — задача не добавляется. Условная логика работает через агента, не через отдельный if-then движок.

**3. Связь всего со всем — данные говорят друг с другом**

Combo-сценарий показывает максимум OpenClaw:
- **Погода** влияет на задачи (перчатки при морозе, зонт при дожде)
- **Тренировка** зависит от программы (`remember_fact`) и прошлых результатов (`query_db`)
- **Бюджет** зависит от записанных трат (`query_db`) и установленного лимита (`remember_fact`)
- **Напоминания** зависят от календаря (`schedule_task`)
- **Советы** зависят от предпочтений (`remember_fact` — вегетарианец)
- **Всё** сохраняется в файл (`write_file`) и память (`remember_fact`)

Это не просто набор инструментов — это экосистема, где данные связаны.

**4. Tool trace как контроль качества**

Весь сценарий виден в чате:
```
[web_search] "погода Москва" → 3 результата
[render_card] weather_card — OK (-5°C, снег)
[read_file] tasks/today.txt — OK (4 задачи)
[query_db] SELECT MAX(weight)... → 62.5
[schedule_task] team_call — trigger_at: 10:45 — OK
[query_db] SELECT SUM(amount)... → 2300 (вчера)
[query_db] SELECT SUM(amount)... → 32400 (месяц)
[write_file] plan/today.txt — OK
[remember_fact] productivity — OK (embedding created)
```

Видишь каждый шаг. Если что-то пошло не так — знаешь где. Это builds trust: ты не веришь агенту на слово, ты **проверяешь**.

**5. Multi-provider fallback в действии**

Если NIM упал во время выполнения combo-сценария:
```
[LLM] NIM timeout after 30s
[fallback] switching to Groq (llama-3.1-70b)...
[LLM] Groq connected — continuing from step 4/8
```

Агент продолжает с того же места. Не начинает сначала — а продолжает цепочку. Модель другая, качество то же, инструменты те же. Ты даже не заметишь переключения, если не смотришь в tool trace.

## Кейс 12: Персоны и доверие — как агент думает

**Уровень:** 4 · **Время освоения:** 15 минут · **Нужно знать:** все кейсы

---

### Проблема

Один и тот же запрос звучит по-разному в разных контекстах. Тренировку хочется от Строгого коуча — чтобы мотивировал, не принимал отговорки, требовал результата. Совет по финансам — от Партнёра-эгалитариста — чтобы обсудить варианты, а не получить приказ. Быстрый факт — от Тихого дворецкого — только суть, без обёртки. Поддержку — от Дружелюбного компаньона — с теплотой и эмодзи. Нужно уметь переключать стиль агента под задачу, понимать как он работает, и строить доверие через прозрачность.

OpenClaw даёт 7 встроенных персон — не просто "формальный/неформальный", а полностью разные личности с разной манерой общения, длиной ответов, степенью инициативы, эмоциональной окраской. Tool trace показывает каждый вызов — ты видишь, как агент думает. Multi-provider fallback гарантирует, что агент всегда ответит.

### Пошагово: переключение, применение, доверие

**Шаг 1. Переключение персоны — глобально**

Ты пишешь:
> Переключись на Тихого дворецкого

Агент меняет системный промпт. Все последующие ответы — сухие, минимальные, без обращений.

Ты:
> Сколько я потратил сегодня?

Агент: "1650 ₽." — Точка. Без "Привет!", без "Вот твоя статистика...", без эмодзи.

Ты:
> Переключись на Дружелюбного компаньона

Агент: "Привет! 💙 Сегодня 1650 ₽ — это совсем немного! Ты молодец, держишь бюджет под контролем 😊"

Один и тот же факт. Три разных реакции. Выбирай под настроение.

**Шаг 2. Одноразовая персона — для конкретного запроса**

Можно не переключать глобально, а попросить конкретную персону для одного ответа:

> Как Строгий коуч: составь план тренировок на неделю

Агент переключается на `strict_coach`:
"План на неделю. Без компромиссов.

Понедельник: грудь + трицепс. Жим 4×8, разводка 3×12, брусья 3×10.
Среда: спина + бицепс. Тяга 4×8, подтягивания 4×макс, молотки 3×12.
Пятница: ноги + плечи. Присед 5×5, жим ногами 4×10, махи 3×15.

Три дня. Не два. Не четыре. Три. Выполняй."

Потом возвращается к default персоне (Резкий напарник).

**Шаг 3. Партнёр-эгалитарист для совместного планирования**

> Как Партнёр-эгалитарист: как лучше распределить бюджет?

"Давай разберём вместе. У тебя 50000 ₽ на месяц. Вот что я вижу по тратам:

- Жильё: 15000 (30%) — фиксировано, не трогаем
- Еда: 10000 (20%) — здесь можно оптимизировать доставку
- Транспорт: 6500 (13%) — в пределах нормы
- Прочее: 8500 (17%) — подушка безопасности
- Накопления: 10000 (20%) — цель на месяц

Варианты:
1. Сократить доставку еды на 2000 — готовить дома чаще
2. Переложить 3000 из прочего в накопления
3. Оставить как есть, но отслеживать еженедельно

Какой вариант ближе тебе? Или хочешь комбинацию?"

Обрати внимание: не "Сделай вариант 1", а "Какой ближе?" — равноправное обсуждение.

**Шаг 4. Tool trace — доверие через прозрачность**

В чате под каждым ответом агента виден tool trace:
```
[query_db] SELECT SUM(amount) FROM expenses WHERE date = '2024-01-15' → 1650
[remember_fact] retrieved: "бюджет 50000" (relevance: 0.92)
[search_memory] "траты еда" → 3 факта retrieved
[render_card] none — текстовый ответ
```

Это не баг — это фича. Ты видишь:
- Какие SQL-запросы выполняются (можешь проверить логику)
- Какие факты из памяти подтянулись (можешь оценить релевантность)
- Какие инструменты вызвались (видишь механику ответа)

Если агент соврёт — увидишь в tool trace. Если запрос неправильный — поправишь. Если факт нерелевантный — скажешь "забудь это".

Доверие строится не на "он умный, верю" — а на "вижу каждый шаг, проверяю, подтверждаю".

**Шаг 5. Multi-provider fallback — агент всегда на связи**

Если NIM падает:
```
[LLM] NIM timeout after 30s
[fallback] switching to Groq...
[LLM] Groq connected — llama-3.1-70b
```

Агент продолжает работать. Модель другая, персона та же, инструменты те же, память та же. Ты можешь проверить: зайди в настройки → LLM → отключи NIM — агент переключится на Groq без потери контекста.

Если Groq тоже падает — GitHub Models (`gpt-4o`) как последний рубеж. Цепочка: NIM → Groq → GitHub Models. Три уровня надёжности.

**Шаг 6. Семантическая память + персона — контекстуальные ответы**

Когда агент отвечает, он автоматически:
1. `search_memory(query)` — ищет релевантные факты о тебе
2. `recall_episodes(range)` — ищет эпизоды для контекста
3. Применяет стиль текущей персоны
4. Генерирует ответ с учётом всего контекста

Пример в персоне Дружелюбный компаньон:

Ты:
> Напомни что я люблю

Агент:
1. `search_memory("люблю")` → "карбонару", "утреннюю работу", "бег по выходным"
2. `recall_episodes("last_week")` → тренировки, рецепты, планы
3. Формирует ответ:

"Ой, с удовольствием вспомню! 💙

Ты любишь:
- Пасту карбонару (я сохранил рецепт в recipes/carbonara.txt! 🍝)
- Работать по утрам, твой пик — 9–12
- Бегать по выходным

И ещё ты вегетарианец! 🌿 Так что карбонару, наверное, в веган-версии? Я могу найти рецепт! 😄"

Обрати внимание: агент связал факты между собой (карбонара + вегетарианец), предложил действие (найти веган-рецепт), использовал стиль friendly_companion (эмодзи, теплота, восклицательные знаки).

### Продвинутые фишки: разные персоны для разных задач, обучение, планы

**1. Разные персоны для разных типов задач — A/B режим**

Можно просить конкретную персону для конкретного запроса без глобального переключения:

> Как Строгий коуч: мой план тренировок на завтра
> Как Ироничный ассистент: сколько я потратил на кофе this month
> Как Тихий дворецкий: покажи файлы
> Как Внимательный секретарь: создай таблицу для учёта расходов со всеми нужными колонками

Агент переключается для одного ответа, потом возвращается к default. Это как иметь семь специалистов в одном приложении.

**2. Tool trace как обучение — от потребителя к мастеру**

Часто смотришь tool trace — начинаешь понимать внутреннюю кухню:
- "А, `query_db` делает SELECT — значит я сам могу писать SQL и точно знать что получу"
- "`search_memory` ищет в embeddings — значит формулировка не важна, можно писать как удобно"
- "`schedule_task` использует cron — значит могу настроить любое расписание"
- "`remember_fact` создаёт вектор — значит чем больше фактов, тем умнее агент"

Это путь от "агент делает за меня" к "я управляю агентом с хирургической точностью".

**3. Проверка fallback — контролируй надёжность**

> Переключись на Groq

Агент меняет LLM-провайдер. Можно сравнить:
- NIM: медленнее (1–3 сек), но качественнее (Llama 3.1 70B/405B)
- Groq: мгновенно (<0.5 сек), качественно (Llama 3.1 70B)
- GitHub Models: надёжно (GPT-4o), работает когда нет ключей NVIDIA/Groq

**4. Память переживает любые переключения**

Персона меняется, провайдер LLM меняется — но `remember_fact`, `search_memory`, все файлы, все таблицы БД остаются. Это одно устройство, одна SQLite, один набор данных. LLM — это "мозг" на данный момент, данные — это "память" навсегда. Мозг можно заменить, память остаётся.

**5. Планы по развитию (v1.1)**

- **Кастомные персоны:** markdown-редактор, где ты описываешь свою персону — тон, стиль, запреты, предпочтения
- **A/B режим автоматический:** агент сам выбирает персону по типу задачи (тренировка → коуч, финансы → эгалитарист)
- **Голосовой ввод:** говоришь — агент понимает (пока не доступно, в планах)

| `write_file(path, content)` | Создаёт или перезаписывает файл | `write_file(contacts/ivan.txt, +7-999...)` | Нет append — только полная перезапись |

| `remember_fact(k, v, cat)` | Сохраняет факт в семантическую память | `remember_fact("любимое", "карбонара", "food")` | Создаёт embedding через NIM |

| `web_fetch(url)` | Загружает текст страницы | `web_fetch("https://example.com")` | Очищенный от HTML текст |

## FAQ: самые частые вопросы

**Q: Почему агент иногда ошибается в SQL?**
A: LLM генерирует SQL, но SQLite проверяет синтаксис и семантику. Если ошибка (опечатка в имени таблицы, неправильный синтаксис) — SQLite возвращает сообщение об ошибке, агент видит его, исправляет запрос и пробует снова. Это называется "self-correction loop". Ты можешь помочь: "Используй date('now', '-7 days') вместо CURRENT_DATE" или "Таблица называется expenses, не costs".

**Q: Могу ли я писать SQL сам, без агента?**
A: Абсолютно! Просто напиши: "Выполни SQL: SELECT * FROM expenses WHERE amount > 1000 ORDER BY amount DESC". Агент передаст твой запрос в `query_db` без изменений. Полный контроль для продвинутых пользователей.

**Q: Что если я случайно удалю важный файл?**
A: Удаление в OpenClaw — это `write_file(path, "")`, то есть запись пустого содержимого. Агент обычно сначала читает файл и показывает содержимое перед "удалением". Если перед этим сохранил что-то важное — используй `write_file(backup/имя.txt, [содержимое])` для резервной копии. В v1.1 планируется корзина (soft delete).

**Q: Работает ли без интернета?**
A: Частично. Всё что локальное — файлы, БД SQLite, напоминания WorkManager, семантический поиск по сохранённым фактам — работает без интернета. LLM требует интернет (NIM/Groq/GitHub Models — все облачные). `web_search` и `web_fetch` тоже требуют сеть. Если нет интернета — агент продолжит работать с локальными инструментами, но ответы будут генерироваться fallback-моделью (если настроена локальная).

**Q: Какой провайдер LLM выбрать?**
A: Зависит от приоритетов:
- **NVIDIA NIM** — лучшее качество (Llama 3.1 70B / 405B), но требует API-ключ NVIDIA. Рекомендуется как primary.
- **Groq** — молниеносная скорость (менее 0.5 сек), качество отличное (Llama 3.1 70B). Требует ключ Groq. Лучший fallback.
- **GitHub Models** — бесплатный тир с лимитами, GPT-4o. Не требует платёжных данных. Идеально для начала.

**Q: Может ли агент отвечать голосом?**
A: Пока нет. Только текстовый ввод и вывод. Голосовой ввод запланирован на v1.1. Но уведомления (`send_notification`) приходят со звуком системы.

**Q: Где хранятся мои данные? Всё локально?**
A: Да. Всё хранится на устройстве:
- Файлы — в файловой системе приложения (sandbox)
- БД и таблицы — SQLite в `/databases/`
- Семантические embeddings — в том же SQLite через sqlite-vec
- Эпизодическая память — SQLite-таблица `episodes`
- Напоминания — Android WorkManager (системный сервис)
Никакие данные не отправляются без твоего ведома. API-ключи хранятся в Android Keystore — зашифрованные.

**Q: Что такое tool trace и зачем оно видно?**
A: Tool trace — это лог вызовов инструментов, который отображается в чате под каждым ответом агента. Ты видишь: какой инструмент вызван, с какими параметрами, какой результат получен. Это фича, не баг. Она строит доверие: ты проверяешь, что агент не выдумывает данные, а реально выполняет SQL-запросы, читает файлы, ищет в памяти. Это прозрачность. Это контроль.

**Q: Как перенести данные на новый телефон?**
A: В v1.0 — ручной экспорт через `write_file`: агент собирает все файлы и БД-дамп, записывает в архивный файл. В v1.1 планируется автоматический бэкап в зашифрованный ZIP с возможностью переноса.

**Q: Могу ли я использовать несколько таблиц и JOIN'ить их?**
A: Конечно! SQLite поддерживает JOIN, LEFT JOIN, INNER JOIN, CROSS JOIN. Главное — создать таблицы с правильными ключами. Агент генерирует JOIN-запросы автоматически когда видит связанные данные. Или пиши SQL сам: "Выполни SQL: SELECT * FROM meals m LEFT JOIN workouts w ON m.date = w.date".

**Q: Что будет если NIM, Groq и GitHub Models все упадут одновременно?**
A: Агент перестанет генерировать текстовые ответы, но локальные инструменты продолжат работать: файлы, БД, напоминания, поиск. Как только хотя бы один провайдер восстанавливается — агент автоматически переподключается. Три уровня fallback делают такой сценарий крайне маловероятным.

**Q: Как работает семантический поиск?**
A: Когда ты говоришь "Запомни: ...", система отправляет текст в NVIDIA NIM, который возвращает вектор (768 чисел) — embedding. Этот вектор сохраняется в sqlite-vec. Когда ты ищешь, запрос тоже превращается в вектор, и система находит ближайшие по расстоянию. Если NIM недоступен — fallback на обычный текстовый поиск FTS4.

**Q: Могу ли я отключить tool trace?**
A: Нет, tool trace всегда видно. Это фундаментальная фича OpenClaw — прозрачность. Но оно не мешает: отображается компактно, свёрнутым, можно тапнуть чтобы развернуть.

**Q: Сколько данных помещается в SQLite?**
A: SQLite теоретически поддерживает до 281 терабайт. На практике — ограничен только свободным местом на телефоне. Для личного трекинга (тысячи записей о еде, тренировках, тратах) — места хватит на десятилетия.

**Q: Можно ли импортировать данные из других приложений?**
A: В v1.0 — через файлы. Если у тебя CSV или текстовый экспорт из другого приложения — запиши его в файл через `write_file`, потом попроси агент распарсить и вставить в БД через `insert_db`. В v1.1 планируется прямой импорт CSV.

### ВАЖНО: ограничения и edge cases

**Doze mode.** Если телефон не трогали 30+ минут — Android входит в doze. Напоминания сдвигаются на "окно обслуживания" (обычно каждые 1-4 часа). Для критичных задач — foreground service, но он жрёт батарею 10-15% в час.

**Перезагрузка.** WorkManager восстанавливает задачи автоматически. Но если задача была на конкретное время в прошлом (телефон был выключен) — она выполнится сразу при включении с пометкой "просрочено".

**Конфликт ID.** Если создашь две задачи с одинаковым name — вторая перезапишет первую. Используй уникальные ID: `morning_water`, `friday_report`, `mom_birthday_2024`.

**День 1 (Понедельник):**

> Покажи средние калории по дням недели

Агент:
```sql
SELECT
  CASE strftime('%w', date)
    WHEN '0' THEN 'Воскресенье'
    WHEN '1' THEN 'Понедельник'
    WHEN '2' THEN 'Вторник'
    WHEN '3' THEN 'Среда'
    WHEN '4' THEN 'Четверг'
    WHEN '5' THEN 'Пятница'
    WHEN '6' THEN 'Суббота'
  END as day_of_week,
  AVG(daily_calories) as avg_calories
FROM (
  SELECT date, SUM(calories) as daily_calories
  FROM meals
  WHERE date >= date('now', '-30 days')
  GROUP BY date
)
GROUP BY strftime('%w', date)
ORDER BY strftime('%w', date)
```

## А.10 Расширенные примеры: Кейс 11 — Семантический поиск

### Пример: как векторный поиск находит по смыслу

Ты записал: `remember_fact("отпуск", "люблю отдыхать в горах, последний раз был в Сочи в феврале", "travel")`

Система создала embedding для этого факта — вектор из 768 чисел, который представляет "отпуск", "горы", "Сочи", "февраль".

Через три месяца ты спрашиваешь:

> Когда я последний раз был на природе?

Агент: `search_memory("природа отдых")` → система превращает "природа отдых" в вектор → ищет ближайшие → находит факт про "горы" и "Сочи".

Почему это работает? Потому что "природа" и "горы" семантически близки в embedding-пространстве. "Отдыхать" и "отдых" — практически идентичны.

### Таблица: semantic vs FTS

| Критерий | Semantic (default) | FTS (текстовый) |
|---|---|---|
| Ищет по | Векторной близости | Точному совпадению слов |
| Понимает синонимы | Да | Нет |
| Работает offline | Да (после создания embeddings) | Да |
| Требует NIM | Да (для создания) | Нет |
| Скорость | Быстро (sqlite-vec) | Очень быстро (FTS4) |
| Лучше для | Свободных запросов | Точных терминов |

### Пример: кросс-поиск по всем источникам

> Найди всё что связано с "здоровье"

1. `search_memory("здоровье")` → факты: "вегетарианец", "предпочитаю утро", "пик продуктивности 9-12"

| Недельная сводка | Траты + тренировки + калории + цели | `schedule_task(cron="0 20 * * 0")` |
| Перед поездкой | Погода + чеклист + курс валют + бюджет | Ручной запрос перед вылетом |

## А.12 Расширенные примеры: Кейс 13 — Персоны

### Таблица: какая персона для какой задачи

| Тип задачи | Лучшая персона | Почему |
|---|---|---|
| Быстрый факт | Тихий дворецкий | Минимум слов, максимум скорости |
| Сложная задача | Внимательный секретарь | Уточнит детали, не ошибётся |
| Рабочие задачи | Резкий напарник (default) | По делу, без воды |
| Планирование | Партнёр-эгалитарист | Советует, не навязывает |
| Поддержка | Дружелюбный компаньон | Тепло, эмодзи, мотивация |
| Лёгкие задачи | Ироничный ассистент | Поднимает настроение |
| Спорт/цели | Строгий коуч | Требует результата |

### Пример: A/B тестирование персон

> Как Тихий дворецкий: сколько я потратил сегодня?
> "1650 ₽."

> Как Ироничный ассистент: сколько я потратил сегодня?
> "1650 ₽. 450 на кофе — твой стандарт. Хотя бы на такси пошёл, разнообразие какое-то. 🚕"

> Как Строгий коуч: сколько я потратил сегодня?
> "1650. Из них 450 — кофе. Это 27% дневного лимита. Бюджет: 50000, осталось 17600. 11 дней. Пересмотри приоритеты."

Один факт — три реакции. Выбирай стиль под задачу.

### Пример: tool trace как обучение

Новый пользователь видит:
```
[query_db] SELECT SUM(amount) FROM expenses WHERE date = '2024-01-15' → 1650
```

И думает: "Ага, значит агент реально выполняет SQL, а не выдумывает цифры."

Опытный пользователь видит:
```
[query_db] SELECT SUM(amount) FROM expenses WHERE date = '2024-01-15' → 1650
```

И думает: "Ага, `date = '2024-01-15'` — значит можно писать свои фильтры. Попробую `date >= date('now', '-7 days')`"

Эксперт видит:
```
[query_db] SELECT SUM(amount) FROM expenses WHERE date = '2024-01-15' → 1650
```

И пишет: "Выполни SQL: SELECT strftime('%Y-%W', date) as week, SUM(amount) FROM expenses GROUP BY week ORDER BY week"

Tool trace — это путь от новичка до эксперта.

## Приложение Б: Полный список ограничений OpenClaw v1.0

### Файловая система
- Нет `edit_file` — только `read_file` + `write_file`
- Нет append — `write_file` всегда перезаписывает
- Нет удаления файлов — только запись пустого содержимого
- Пути относительные, начинаются от корня sandbox-приложения

### База данных
- `query_db` — **только SELECT/PRAGMA/SHOW TABLES**
- `insert_db` — CREATE TABLE, INSERT, UPDATE, DELETE
- CREATE TABLE **только** через `insert_db` с `_sql`
- SQLite, версия 3.39+
- Поддерживает JOIN, подзапросы, оконные функции, CTE (WITH)

### Карточки
- **Только 6 шаблонов**: todo_list, weather_card, timer, table, chart_bar, form
- Нет `chart_line`, нет `chart_pie`, нет кастомных шаблонов
- `chart_bar` — единственный тип графика

### Персоны
- Ровно 7 встроенных персон, ID фиксированы
- Свои персоны — в v1.1 (markdown-редактор)
- Переключение: глобальное или для одного запроса

### LLM и сеть
- NIM (primary) → Groq (fallback) → GitHub Models (fallback)
- Без интернета: локальные инструменты работают, LLM — нет
- Голосового ввода нет (в планах v1.1)
- Нет локальной LLM в v1.0

### Напоминания
- Минимальный период: 15 минут (WorkManager)
- Точность ±10-15 минут в doze mode
- Задачи сохраняются при перезагрузке
- Нет foreground service по умолчанию

### Приватность
- Все данные на устройстве
- Никакой отправки данных без ведома пользователя
- API-ключи в Android Keystore (зашифрованы)
- Нет облачной синхронизации
- Нет multi-user / sharing

# Приложение C: SQL-справочник и типовые паттерны

Это приложение — твой шпаргалка по SQL внутри OpenClaw. Здесь нет теории про нормальные формы и академических определений. Только рабочие запросы, которые решают конкретные задачи из кейсов выше. Копируй, адаптируй, используй.

## C.1 Золотое правило: query_db vs insert_db

Забудь — и потратьшь полчаса на ошибку. В OpenClaw база данных разделена на два инструмента строго по типу операции:

| Инструмент | Разрешённые команды | Запрещённые команды |
|-----------|---------------------|---------------------|
| `query_db` | `SELECT`, `PRAGMA`, `SHOW TABLES`, `EXPLAIN` | `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `DROP`, `ALTER` |
| `insert_db` | `CREATE TABLE`, `INSERT`, `UPDATE`, `DELETE`, `DROP TABLE`, `ALTER TABLE` | `SELECT` |

**Ключевой момент:** `CREATE TABLE` идёт только через `insert_db`. Да, это контринтуитивно — "я же ничего не вставляю, я создаю таблицу!" — но так устроена безопасность. `query_db` — только чтение. `insert_db` — любая запись, включая создание структуры.

Практический пример создания таблицы:

```
Ты: Создай таблицу для учёта тренировок: дата, тип, длительность в минутах, интенсивность (низкая/средняя/высокая), заметки

Агент вызывает insert_db:
  table: "workouts"
  values: {
    "_sql": "CREATE TABLE workouts (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      date TEXT NOT NULL,
      type TEXT NOT NULL,
      duration_minutes INTEGER NOT NULL,
      intensity TEXT CHECK(intensity IN ('низкая','средняя','высокая')),
      notes TEXT,
      created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    )"
  }

Ты видишь в tool trace: [insert_db] workouts — CREATE TABLE — ok
```

**Частая ошибка:** попытка создать таблицу через `query_db`. Агент получит ошибку прав доступа. Правильно — явно сказать "создай таблицу", тогда агент сам выберет `insert_db`.

## C.2 Параметризованные запросы — защита от SQL-инъекций

Никогда не склеивай строку запроса с данными вручную. Всегда используй параметры `?` и массив `params`:

**Неправильно (не делай так):**
```sql
-- Опасно! Если в name содержится кавычка — запрос сломается или хуже
query_db(sql = "SELECT * FROM meals WHERE name = '" + user_input + "'")
```

**Правильно:**
```sql
query_db(
  sql = "SELECT * FROM meals WHERE name = ?",
  params = [user_input]
)
```

Агент делает это автоматически, но если пишешь SQL вручную — контролируй этот момент.

CREATE TABLE meals (

**Калории за день:**
```sql
SELECT 
  meal_type,
  SUM(calories) as total_calories,
  SUM(protein) as total_protein,
  COUNT(*) as meals_count
FROM meals 
WHERE date = ?
GROUP BY meal_type
ORDER BY CASE meal_type 
  WHEN 'завтрак' THEN 1 
  WHEN 'обед' THEN 2 
  WHEN 'ужин' THEN 3 
  ELSE 4 
END
```

**Средние калории по дням недели (последние 30 дней):**
```sql
SELECT 
  CASE strftime('%w', date)
    WHEN '0' THEN 'Воскресенье'
    WHEN '1' THEN 'Понедельник'
    WHEN '2' THEN 'Вторник'
    WHEN '3' THEN 'Среда'
    WHEN '4' THEN 'Четверг'
    WHEN '5' THEN 'Пятница'
    WHEN '6' THEN 'Суббота'
  END as day_of_week,
  ROUND(AVG(daily_calories), 0) as avg_calories
FROM (
  SELECT date, SUM(calories) as daily_calories
  FROM meals
  WHERE date >= date('now', '-30 days')
  GROUP BY date
)
GROUP BY day_of_week
ORDER BY avg_calories DESC
```

**Поиск по названию блюда (частичное совпадение):**
```sql
SELECT date, meal_type, name, calories 
FROM meals 
WHERE name LIKE '%' || ? || '%'
ORDER BY date DESC
LIMIT 20
```

### Кейс 5: Журнал тренировок

**Создание таблицы:**
```sql
CREATE TABLE workouts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL,
  type TEXT NOT NULL,
  duration_minutes INTEGER NOT NULL,
  intensity TEXT CHECK(intensity IN ('низкая','средняя','высокая')),

  notes TEXT,

)
```

**Статистика по типам тренировок (месяц):**
```sql
SELECT 
  type,
  COUNT(*) as sessions,
  SUM(duration_minutes) as total_minutes,
  ROUND(AVG(duration_minutes), 0) as avg_duration,
  SUM(calories_burned) as total_burned

```

**Прогресс по весам в упражнении (нарастающий максимум):**

SELECT

WHERE type = ? AND weight_kg IS NOT NULL
  AND date >= date('now', '-90 days')

ORDER BY date
```

**Недельный объём (сумма минут по неделям):**

SELECT

  COUNT(*) as sessions_count

WHERE date >= date('now', '-90 days')
GROUP BY week
ORDER BY week DESC

### Кейс 6: Учёт финансов

**Создание таблицы расходов:**
```sql
CREATE TABLE expenses (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL,
  amount REAL NOT NULL,
  category TEXT NOT NULL,
  subcategory TEXT,
  description TEXT,
  payment_method TEXT CHECK(payment_method IN ('наличные','карта','перевод','другое')),
  is_recurring BOOLEAN DEFAULT 0,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
)
```

**Расходы по категориям (текущий месяц):**
```sql
SELECT 
  category,
  SUM(amount) as total,
  COUNT(*) as transactions,
  ROUND(SUM(amount) * 100.0 / (SELECT SUM(amount) FROM expenses 
    WHERE strftime('%Y-%m', date) = strftime('%Y-%m', 'now')), 1) as percentage
FROM expenses
WHERE strftime('%Y-%m', date) = strftime('%Y-%m', 'now')
GROUP BY category
ORDER BY total DESC
```

**Динамика по месяцам (6 месяцев):**
```sql
SELECT 
  strftime('%Y-%m', date) as month,
  SUM(amount) as total_spent,
  COUNT(*) as transaction_count,
  ROUND(AVG(amount), 2) as avg_transaction
FROM expenses
WHERE date >= date('now', '-6 months')
GROUP BY month
ORDER BY month
```

**Поиск подозрительных дублей (похожие суммы в один день):**
```sql
SELECT 
  date, amount, COUNT(*) as occurrences,
  GROUP_CONCAT(description, ' | ') as descriptions
FROM expenses
WHERE date >= date('now', '-30 days')
GROUP BY date, amount
HAVING COUNT(*) > 1
ORDER BY occurrences DESC
```

**Бюджет: остаток до лимита по категории:**
```sql
-- Предполагаем таблицу budgets(category, monthly_limit)
SELECT 
  b.category,
  b.monthly_limit,
  COALESCE(SUM(e.amount), 0) as spent,
  b.monthly_limit - COALESCE(SUM(e.amount), 0) as remaining
FROM budgets b
LEFT JOIN expenses e ON b.category = e.category 
  AND strftime('%Y-%m', e.date) = strftime('%Y-%m', 'now')
GROUP BY b.category
ORDER BY remaining ASC
```

CREATE TABLE file_index (

SELECT

### Кейс 9: Периодические отчёты

**Шаблон универсального отчёта с параметрами:**
```sql
-- Расходы за произвольный период (замени placeholders)
SELECT 
  category,
  SUM(amount) as total,
  COUNT(*) as count,
  MIN(amount) as min_amount,
  MAX(amount) as max_amount,
  ROUND(AVG(amount), 2) as avg_amount
FROM expenses
WHERE date BETWEEN ? AND ?
GROUP BY category
ORDER BY total DESC
```

**Сравнение с прошлым периодом (period-over-period):**
```sql
WITH current_period AS (
  SELECT category, SUM(amount) as total
  FROM expenses
  WHERE date BETWEEN date('now', '-30 days') AND date('now')
  GROUP BY category
),
previous_period AS (
  SELECT category, SUM(amount) as total
  FROM expenses
  WHERE date BETWEEN date('now', '-60 days') AND date('now', '-30 days')
  GROUP BY category
)
SELECT 
  COALESCE(c.category, p.category) as category,
  COALESCE(c.total, 0) as current_total,
  COALESCE(p.total, 0) as previous_total,
  ROUND((COALESCE(c.total, 0) - COALESCE(p.total, 0)) * 100.0 / 
    NULLIF(p.total, 0), 1) as percent_change
FROM current_period c
FULL OUTER JOIN previous_period p ON c.category = p.category
ORDER BY ABS(COALESCE(c.total, 0) - COALESCE(p.total, 0)) DESC
```

## C.4 Дата и время в SQLite

OpenClaw использует SQLite, и вся работа с датами — через встроенные функции `date()`, `time()`, `datetime()`, `strftime()`, `julianday()`.

| Задача | SQL | Результат |
|--------|-----|-----------|
| Сегодня | `date('now')` | 2024-01-15 |
| Сейчас | `datetime('now')` | 2024-01-15 14:30:00 |
| Вчера | `date('now', '-1 day')` | 2024-01-14 |
| 7 дней назад | `date('now', '-7 days')` | 2024-01-08 |
| 30 дней назад | `date('now', '-30 days')` | 2023-12-16 |
| Начало месяца | `date('now', 'start of month')` | 2024-01-01 |
| Конец месяца | `date('now', 'start of month', '+1 month', '-1 day')` | 2024-01-31 |
| Начало года | `date('now', 'start of year')` | 2024-01-01 |
| День недели | `strftime('%w', date)` | 0=воскресенье, 1=понедельник |
| Номер недели | `strftime('%W', date)` | 01-53 |
| Месяц | `strftime('%m', date)` | 01-12 |
| Год-месяц | `strftime('%Y-%m', date)` | 2024-01 |

**Фильтр "текущая неделя":**
```sql
WHERE date >= date('now', 'weekday 0', '-7 days')
```

**Фильтр "прошлый месяц полностью":**
```sql
WHERE date >= date('now', 'start of month', '-1 month')
  AND date < date('now', 'start of month')
```

**Фильтр "последние N дней с именованным параметром":**
```sql
WHERE date >= date('now', '-' || ? || ' days')
-- params: [30]
```

## C.5 Продвинутые паттерны

**CASE для категоризации на лету:**
```sql
SELECT 
  name,
  calories,
  CASE 
    WHEN calories < 200 THEN 'легкое'
    WHEN calories BETWEEN 200 AND 500 THEN 'среднее'
    WHEN calories BETWEEN 500 AND 800 THEN 'плотное'
    ELSE 'очень калорийное'
  END as calorie_class
FROM meals
WHERE date = date('now')
```

**COALESCE для значений по умолчанию:**
```sql
-- Если notes NULL — показать "нет заметок"
SELECT date, type, COALESCE(notes, 'нет заметок') as notes FROM workouts
```

**NULLIF для избежания деления на ноль:**
```sql
-- Процент изменения безопасно
ROUND((current - previous) * 100.0 / NULLIF(previous, 0), 1)
```

**GROUP_CONCAT для объединения строк:**
```sql
-- Все описания расходов за день одной строкой
SELECT date, GROUP_CONCAT(description, '; ') as all_descriptions
FROM expenses GROUP BY date
```

**LIMIT + OFFSET для пагинации:**
```sql
-- Страница 3, по 20 записей
SELECT * FROM meals ORDER BY date DESC LIMIT 20 OFFSET 40
```

**EXISTS для проверки наличия:**
```sql
-- Дни, когда были и тренировка, и запись о еде
SELECT DISTINCT w.date 
FROM workouts w
WHERE EXISTS (SELECT 1 FROM meals m WHERE m.date = w.date)
```

**CTE (Common Table Expression) для читаемости:**
```sql
WITH monthly_stats AS (
  SELECT 
    strftime('%Y-%m', date) as month,
    SUM(amount) as total,
    COUNT(*) as count
  FROM expenses
  GROUP BY month
)
SELECT month, total, count,
       ROUND(total * 1.0 / count, 2) as avg_per_transaction
FROM monthly_stats
WHERE total > 10000
ORDER BY month DESC
```

## C.6 Типичные ошибки и их исправление

| Ошибка | Причина | Исправление |
|--------|---------|-------------|
| `no such table` | Таблица не создана или опечатка в имени | Проверь `SHOW TABLES` через query_db, создай через insert_db |
| `no such column` | Опечатка в имени столбца | Проверь структуру: `PRAGMA table_info(table_name)` |
| `UNIQUE constraint failed` | Попытка вставить дубль по уникальному полю | Используй `INSERT OR REPLACE` или проверь перед вставкой |
| `CHECK constraint failed` | Значение не проходит проверку (например, intensity не из списка) | Проверь допустимые значения в CHECK |
| `division by zero` | Деление на NULL или 0 | Используй `NULLIF(знаменатель, 0)` |
| `near "something": syntax error` | Синтаксическая ошибка в SQL | Проверь запятые, скобки, кавычки |
| `readonly database` | Попытка CREATE/INSERT через query_db | Используй insert_db для write-операций |
| `database is locked` | Параллельный доступ (редко в OpenClaw) | Повтори запрос через секунду |

# Приложение D: Персоны — глубокое погружение и примеры диалогов

Ты уже знаешь, что в OpenClaw семь персон и что по умолчанию активен Резкий напарник. Но знать имена — не значит уметь использовать. Это приложение покажет, как одна и та же задача решается в разных стилях, и поможет выбрать персону под конкретную ситуацию.

## D.1 Сравнение семи персон

| Характеристика | Тихий дворецкий | Внимательный секретарь | Резкий напарник | Партнёр-эгалитарист | Дружелюбный компаньон | Ироничный ассистент | Строгий коуч |
|---|---|---|---|---|---|---|---|
| **Длина ответа** | 1-2 предложения | 3-5 предложений, уточнения | 2-3 предложения | 3-4, с вопросами | 4-6, развёрнуто | 3-5, с иронией | 2-3, команды |
| **Эмодзи** | Никогда | Редко | Никогда | Иногда | Постоянно | Часто, саркастичные | Никогда |
| **Инициатива** | Только по запросу | Уточняет детали | Предлагает следующий шаг | Совместное обсуждение | Поддержка, советы | Игривые подсказки | Требует действий |
| **Обращение** | Без обращений | Вежливое, по имени если знает | Ты / без обращения | Мы / давай | Ты, тёплое | Ты, с подколками | Ты, приказной тон |
| **Ошибки** | Молча исправляет | Переспросит перед действием | Скажет "сделай так" | Обсудит варианты | Извинится, исправит | Пошутит про ошибку | Укажет на ошибку, доведёт до результата |
| **Лучшее время** | Рутина, факты | Сложные задачи | Быстрые задачи | Планирование | Поддержка, стресс | Лёгкие задачи | Дисциплина, цели |
| **Худшее время** | Когда нужна поддержка | Когда нужна скорость | Когда нужна эмпатия | Когда нужно быстрое решение | Когда нужна краткость | Когда всё идёт не так | Когда нужен комфорт |

## D.2 Один запрос — семь ответов

Чтобы почувствовать разницу, взгляни, как разные персоны отвечают на одну и ту же просьбу: *"Сколько я потратил на еду в этом месяце?"*

### Тихий дворецкий (`silent_butler`)

**Ты:** Сколько я потратил на еду в этом месяце?

**Агент:**
```
query_db: SELECT SUM(amount) FROM expenses WHERE category = 'еда' AND strftime('%Y-%m', date) = strftime('%Y-%m', 'now')
Результат: 24 650 ₽
```
24 650 ₽. 14 транзакций. Средний чек: 1 761 ₽.

Всё. Два предложения. Факты. Никаких "как я могу помочь", никаких "хотите ли вы подробный отчёт". Сумма, количество, среднее. Если нужно что-то ещё — спросишь.

### Внимательный секретарь (`attentive_secretary`)

**Ты:** Сколько я потратил на еду в этом месяце?

**Агент:**
```
query_db: SELECT SUM(amount) as total, COUNT(*) as count FROM expenses WHERE category = 'еда' AND strftime('%Y-%m', date) = strftime('%Y-%m', 'now')
```

За текущий месяц на категорию "еда" потрачено 24 650 ₽ (14 транзакций). Средний чек составляет 1 761 ₽.

Уточните, пожалуйста:
- Вам нужен подробный отчёт по дням или по типам питания?
- Включать ли категории "кафе" и "продукты" отдельно или вместе?
- Показать сравнение с прошлым месяцем?

Три уточнения. Секретарь не хочет ошибиться — лучше переспросит, чем покажет не то.

### Резкий напарник (`sharp_partner`, default)

**Ты:** Сколько я потратил на еду в этом месяце?

**Агент:**
```
query_db: SELECT SUM(amount), COUNT(*), AVG(amount) FROM expenses WHERE category = 'еда' AND date LIKE '2024-01%'
```

24 650 ₽, 14 покупок, средний чек 1 761 ₽. Хочешь разбивку по неделям?

Кратко. По делу. Сразу предлагает следующий шаг — разбивку по неделям — потому что это логичное продолжение.

### Партнёр-эгалитарист (`egalitarian_partner`)

**Ты:** Сколько я потратил на еду в этом месяце?

**Агент:**
```
query_db: SELECT SUM(amount), COUNT(*) FROM expenses WHERE category = 'еда' AND strftime('%Y-%m', date) = strftime('%Y-%m', 'now')
```

Получается, 24 650 ₽ за месяц на еду, 14 транзакций. Давай подумаем — это больше или меньше, чем ты планировал? Если хочешь, мы можем вместе посмотреть динамику за последние три месяца и понять, куда тратится больше всего: продукты, доставка или кафе. Как тебе удобнее?

Не отвечает — вовлекает. "Давай подумаем" вместо "вот ответ". Предлагает варианты, но решает вместе с тобой.

### Дружелюбный компаньон (`friendly_companion`)

**Ты:** Сколько я потратил на еду в этом месяце?

**Агент:**
```
query_db: SELECT SUM(amount), COUNT(*), AVG(amount) FROM expenses WHERE category = 'еда' AND date >= date('now', 'start of month')
```

Ой, 24 650 ₽ на еду за месяц 🍕 14 походов в магазин или кафе, в среднем по 1 761 ₽ за раз. Это нормально для твоего бюджета или хочешь, чтобы мы вместе подумали, где можно сэкономить? Я могу показать самые крупные покупки — может, найдём что-то, что можно оптимизировать? 💪

С эмодзи. С заботой. Не просто отвечает — поддерживает. Предлагает помочь сэкономить, потому что тратить 25 тысяч на еду может быть стрессово.

### Ироничный ассистент (`ironic_assistant`)

**Ты:** Сколько я потратил на еду в этом месяце?

**Агент:**
```
query_db: SELECT SUM(amount), COUNT(*) FROM expenses WHERE category = 'еда' AND strftime('%Y-%m', date) = strftime('%Y-%m', 'now')
```

24 650 ₽. Четырнадцать раз ты пошёл есть вне дома. Средний чек 1 761 ₽ — хватило бы на премиум-подписку во что-нибудь полезное, но нет, мы едим 😏 Хочешь посмотреть, где конкретно сгорают деньги? Могу показать топ-3 самых дорогих ужинов — для мотивации или для виновных.

Сарказм лёгкий, не злой. "Хватило бы на подписку" — типичная ирония. Но всё равно предлагает полезное продолжение (топ-3 ужинов).

### Строгий коуч (`strict_coach`)

**Ты:** Сколько я потратил на еду в этом месяце?

**Агент:**
```
query_db: SELECT SUM(amount), COUNT(*), AVG(amount) FROM expenses WHERE category = 'еда' AND strftime('%Y-%m', date) = strftime('%Y-%m', 'now')
```

24 650 ₽. 14 транзакций. Средний чек 1 761 ₽. Если твой бюджет на еду 20 000 ₽ — ты превысил на 23%. Вот три шага прямо сейчас:
1. Открой отчёт по дням — найди самый дорогой день.
2. Определи, была ли это необходимость или импульс.
3. Поставь лимит 800 ₽ на одну покупку.

Действуй. Отчёт ждёт.

Без "хочешь", без "может быть". Команды. Шаги. Результат. Если у тебя цель — сэкономить — этот стиль не даст расслабиться.

## D.3 Матрица выбора персоны

Не знаешь, кого включить? Воспользуйся деревом решений:

**Тебе нужна скорость и точность?**
→ Тихий дворецкий. Он не будет переспрашивать и распыляться.

**Задача сложная, один неверный шаг — и всё сломано?**
→ Внимательный секретарь. Переспросит три раза, но сделает правильно с первой попытки.

**Обычная задача, хочешь быстрый результат без воды?**
→ Резкий напарник (default). Работает для 80% случаев.

**Нужно спланировать что-то вместе, обсудить варианты?**
→ Партнёр-эгалитарист. "Давай подумаем" — его фраза.

**Ты устал, стрессуешь, нужна поддержка?**
→ Дружелюбный компаньон. Не решит задачу быстрее, но сделает процесс приятнее.

**Рутинная задача, которую хочется пережить с юмором?**
→ Ироничный ассистент. Превратит скучный отчёт в развлечение.

**Нужна дисциплина, цель, дедлайн?**
→ Строгий коуч. Нет отговорок. Только шаги и результат.

## D.4 Персоны в цепочках задач

Персоны можно комбинировать. Не нужно выбирать одну на всё время — можешь переключать прямо в диалоге.

**Пример: подготовка к отпуску**

```
Ты: [Партнёр-эгалитарист] Давай спланирую отпуск на март
Агент: Отлично, давай вместе подумаем. Какие направления рассматриваешь? 
        Сколько дней? Бюджет примерно какой?
        (обсуждение вариантов, 5 сообщений)

Ты: [Тихий дворецкий] Собери всё в файл plan/trip_march.txt
Агент: Готово. plan/trip_march.txt создан. 12 пунктов.
        [write_file] — ok

Ты: [Внимательный секретарь] Напомни мне за неделю до вылета купить 
     страховку, за день — распечатать билеты, за 3 часа — вызвать такси
Агент: Уточни, пожалуйста:
        1. Дата вылета — 15 марта, верно?
        2. Напоминание о такси — за 3 часа до вылета или до прибытия в аэропорт?
        (уточнение деталей)
        [schedule_task] × 3 — ok

Ты: [Ироничный ассистент] Найди забавные факты о Токио
Агент: В Токио больше людей, чем в 38 странах мира вместе взятых. 
        И да, там есть музей паразитов 🪱 Твой отпуск обещает быть... познавательным.
```

**Ключевой инсайт:** начинай с эгалитариста для обсуждения, переключай на дворецкого для рутины, на секретаря для важных деталей, на ироничного для разгрузки.

## D.5 Персоны и tool trace

Tool trace — прозрачный лог вызовов инструментов — работает одинаково для всех персон. Но как агент *показывает* этот trace, зависит от стиля.

**После выполнения задачи:**

| Персона | Как показывает trace |
|---------|---------------------|
| Тихий дворецкий | Просто перечисляет: `[query_db] expenses — SUM: 24650 — ok`. Без комментариев. |
| Внимательный секретарь | Объясняет каждый шаг: "Выполнил запрос к таблице расходов, просуммировал по категории 'еда' за текущий месяц, получилось 24 650 ₽" |
| Резкий напарник | Коротко: `[query_db] expenses: 24650 ₽`. Сразу результат. |
| Партнёр-эгалитарист | "Мы посмотрели в таблицу расходов, отфильтровали еду за этот месяц — получилось 24 650 ₽. Это соответствует твоим ожиданиям?" |
| Дружелюбный компаньон | "Я заглянул в твою таблицу расходов 📊 и насчитал 24 650 ₽ на еду за месяц. Это нормально для тебя?" |
| Ироничный ассистент | "Проверил твои финансы 💸 24 650 ₽ ушло на еду. Таблица расходов не врёт, к сожалению." |
| Строгий коуч | "Факт: 24 650 ₽. Источник: таблица expenses. Запрос: SUM по категории 'еда'. Действуй на основе цифр." |

## D.6 Как переключать персоны быстро

**Постоянное переключение (на весь диалог):**
```
Ты: Переключись на Тихого дворецкого
Агент: [system: persona = silent_butler] Настроен.
Ты: Покажи задачи на сегодня
Агент: 3 задачи. [render_card] todo_list — ok. Без лишних слов.
```

**Одноразовое переключение (на один запрос):**
```
Ты: Как Дружелюбный компаньон: сколько у меня задач на сегодня?
Агент: (в стиле friendly_companion) Привет! У тебя сегодня 3 задачи 💪 
        Первая — позвонить маме, это так мило! 
        (default persona не изменился)

Ты: Покажи погоду  (ответит как Резкий напарник, default)
```

**Быстрые фразы для переключения:**

| Действие | Фраза |
|----------|-------|
| Переключить навсегда | "Переключись на [имя]", "Смени персону на [имя]" |
| Одноразово | "Как [имя]: ...", "Ответь как [имя]: ..." |
| Узнать текущую | "Какая сейчас персона?", "Кто ты?" |
| Вернуть default | "Верни Резкого напарника", "Сбрось персону" |

## D.7 Подводный камень: персона и точность

Важно понимать: персона влияет **только на стиль ответа**, но не на качество выполнения задачи. Если ты просишь посчитать сумму — `query_db` отработает одинаково под любой персоной. Разница только в том, как агент *пояснит* результат.

**Исключение:** Внимательный секретарь может переспросить уточняющие вопросы перед выполнением, что косвенно влияет на результат — но в сторону точности, а не скорости.

**Практический совет:** для критически важных операций (удаление данных, массовое обновление, финальные отчёты) используй Внимательного секретаря. Для рутины — Тихого дворецкого или Резкого напарника. Для творческих задач — Ироничного или Дружелюбного.

## D.8 Персоны и долговременная память

Агент сохраняет факты о тебе через `remember_fact` в семантическую память. Но вот что интересно: **персона может влиять на то, какие факты сохраняются**.

**Пример:**

```
Ты: [Дружелюбный компаньон] Я так устал на работе сегодня
Агент: Ой, ты так стараешься! Хочешь, я запомню что ты сейчас в 
        стрессовом периоде на работе? Тогда буду мягче с тобой 💙
        [remember_fact] context: emotional_state, fact: стресс на работе

Ты: [Строгий коуч] Я устал на работе
Агент: Усталость — не причина останавливаться. Но запомню: у тебя 
        высокая нагрузка. Адаптирую план. [remember_fact] 
        context: workload, fact: высокая нагрузка
```

Один факт — два разных контекста. Дружелюбный сохранил как "эмоциональное состояние", коуч — как "рабочую нагрузку". При поиске `search_memory("стресс")` найдёт оба, но контекст разный — и это влияет на будущие рекомендации.

# Приложение E: Скрытые фичи и профессиональные трюки

Это приложение — сборник мелочей, которые не вписались в основные кейсы, но делают работу с OpenClau заметно комфортнее. Некоторые из этих приёмов открываешь только после недель использования. Мы сэкономим тебе время.

## E.1 Файловая система: неочевидные возможности

**Относительные пути и подпапки.** OpenClaw поддерживает вложенные директории. Можно сразу писать `notes/2024/january/ideas.txt` — промежуточные папки создаются автоматически. Не нужно отдельно создавать каждую директорию.

**Поиск с wildcard.** `search_files(pattern = "*.txt", dir = "notes")` найдёт все текстовые файлы. `search_files(pattern = "report*", dir = "docs")` найдёт всё, что начинается на "report". Работает как в bash.

**Чтение части файла.** Если файл огромный и нужен только фрагмент, агент может прочитать конкретные строки через `read_file` с параметрами `offset` и `limit`. Например, пропустить первые 100 строк и прочитать следующие 50 — полезно для логов.

**Быстрый перезаписанный файл.** Нет `edit_file` — помнишь? — но есть паттерн "прочитай, измени, запиши целиком". Для маленьких файлов это мгновенно. Для больших — агент сам предложит переписать только нужную часть, если объяснишь, что именно изменить.

## E.2 База данных: оптимизации

**PRAGMA для диагностики.** Через `query_db` с `PRAGMA` можно получить служебную информацию:
- `PRAGMA table_info(meals)` — структура таблицы (столбцы, типы, дефолты)
- `PRAGMA index_list(expenses)` — список индексов
- `PRAGMA foreign_key_check` — проверка целостности

**Индексы для скорости.** Если таблица разрослась до тысяч записей и запросы тормозят, создай индекс:
```sql
-- Через insert_db!
CREATE INDEX IF NOT EXISTS idx_meals_date ON meals(date);
CREATE INDEX IF NOT EXISTS idx_expenses_category ON expenses(category, date);
```
Агент сам не создаёт индексы автоматически — это редко нужно на мобильном устройстве, но для больших таблиц (год+ данных) разница в скорости заметна.

**VIEW для частых отчётов.** Если каждый день смотришь одну и ту же статистику, создай представление:
```sql
-- Через insert_db
CREATE VIEW IF NOT EXISTS daily_summary AS
SELECT 
  date,
  (SELECT SUM(calories) FROM meals WHERE meals.date = d.date) as calories_in,
  (SELECT SUM(calories_burned) FROM workouts WHERE workouts.date = d.date) as calories_out
FROM (SELECT DISTINCT date FROM meals UNION SELECT DISTINCT date FROM workouts) d;
```
Потом просто: `query_db("SELECT * FROM daily_summary WHERE date = date('now')")`

## E.3 Напоминания: граничные случаи

**Минимальный интервал.** Android WorkManager ограничивает частые задачи. Минимум — 15 минут между запусками. Если поставишь `cron = "*/5 * * * *"` (каждые 5 минут), система всё равно сожмёт до 15-минутного интервала.

**Doze mode.** Когда телефон лежит неподвижно в тёмном месте, Android переходит в doze mode. Напоминания могут сдвигаться на 10-15 минут. Для критичных задач используй `setAlarmClock` через системное API — но OpenClaw пока работает через WorkManager, так что планируй с запасом.

**Cron без года.** В `schedule_task` используется cron-выражение без года. Формат: `минута час день_месяца месяц день_недели`. Примеры:
- `0 9 * * 1-5` — по будням в 9:00
- `0 */6 * * *` — каждые 6 часов
- `30 22 * * 0` — по воскресеньям в 22:30
- `0 8 1 * *` — первое число каждого месяца в 8:00

**Имена задач.** Имя в `schedule_task` должно быть уникальным. Если создашь задачу с тем же именем — старая перезапишется. Это фича: можно обновлять расписание, просто послав тот же `name` с новым `cron`.

**Отмена по имени.** `cancel_task(name = "check_email_daily")` — мгновенно. Если имя не найдено — тихая ошибка, ничего не сломается.

## E.4 Web: тонкости

**web_fetch vs web_search.** `web_search` возвращает список ссылок с заголовками и сниппетами. `web_fetch` загружает конкретную страницу целиком — и если страница тяжёлая, это займёт время и токены. Для быстрого поиска — `web_search`. Для чтения конкретной статьи — `web_fetch`.

**Фильтрация контента.** `web_fetch` возвращает текстовую версию страницы. Картинки, видео, скрипты — вырезаются. Это фича для скорости, но если нужно что-то из медиа — придётся открывать в браузере вручную.

**Ограничение по размеру.** Если страница огромная (100+ тысяч символов), агент может обрезать контент. Если нужен конкретный фрагмент — попроси агента найти нужную секцию через `browser_find` или уточни URL с якорем (`page.html#section`).

## E.5 Семантический поиск: калибровка

**Контексты matter.** `remember_fact` принимает три параметра: `context`, `fact`, `episodic`. Контекст — это категория факта. Примеры хороших контекстов: `preferences`, `work`, `health`, `finance`, `contacts`, `goals`. Контекст помогает агенту фильтровать при поиске.

**Эпизодическая память.** `recall_episodes` ищет по хронике взаимодействий — что ты делал, когда, в каком контексте. Это не факты, а события. "В прошлый понедельник ты просил найти рецепт пасты" — это эпизод, а не факт.

**Fallback работает автоматически.** Если NIM недоступен для embeddings, агент переключается на FTS4 (полнотекстовый поиск). FTS4 ищет по точным словам, не по смыслу — но работает без интернета. Если вернулся неожиданный результат — проверь в tool trace, не был ли fallback.

## E.6 Карточки: шесть шаблонов

Помни: только шесть шаблонов. Никаких кастомных. Но внутри каждого — гибкость:

- **`todo_list`** — чекбоксы с заголовком. Можно передать массив items с `text` и `checked`. Агент сам рендерит.
- **`weather_card`** — город, температура, описание, иконка. Данные можно подтянуть через `web_search` + `web_fetch` с сайта погоды, или ввести вручную.
- **`timer`** — обратный отсчёт. Удобен для помидоро-техники: "Поставь таймер на 25 минут".
- **`table`** — произвольные данные в таблице. Передаёшь `headers` и `rows`. Отлично для отчётов.
- **`chart_bar`** — столбчатая диаграмма. Только она. Никаких `chart_line` или `chart_pie`. Передаёшь `labels` и `values`.
- **`form`** — форма ввода с полями. Поля бывают `text`, `number`, `select`, `checkbox`, `date`.

**Pro tip:** комбинируй карточки. Например, сначала `table` с детальными данными, потом `chart_bar` с агрегатом. Агент может рендерить несколько карточек подряд.

## E.7 Multi-provider fallback: что видишь в trace

Когда провайдер падает, в tool trace появляются записи:

```
[LLM] Request to NIM... timeout
[fallback] NIM → Groq
[LLM] Request to Groq... ok
```

Или если Groq тоже отвалился:
```
[LLM] NIM: timeout
[fallback] NIM → Groq
[LLM] Groq: rate limit
[fallback] Groq → GitHub Models
[LLM] GitHub Models: ok
```

**Не паникуй** при слове "timeout" в trace — это не ошибка агента, это сеть. Fallback сработал, диалог продолжается.

## E.8 Безопасность: что хранится, что нет

- **Хранится локально:** файлы, SQLite, напоминания, факты в semantic memory, эпизоды.
- **Уходит в провайдера:** текст сообщений для генерации ответа. Никакие файлы, никакие базы данных, никакие факты — только текст диалога.
- **Не хранится нигде:** API-ключи хранятся в Android Keystore, зашифрованные. Даже root-доступ не достанет их легко.
- **Отключение провайдера:** если API-ключ удалить — агент переключится на следующий доступный. Если все ключи удалены — агент работает только с локальными инструментами (файлы, база, напоминания). LLM-ответы генерироваться не будут.
